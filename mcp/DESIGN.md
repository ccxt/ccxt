# ccxt-mcp — design & decision log

This document records what the official CCXT MCP server learned from prior art, the constraints that shaped it, and the decisions with their rationale. It is contributor-facing; user docs live in `README.md`.

## Goals / non-goals

**Goals:** keys stay local and invisible to the model; trivial install (`npx -y ccxt-mcp`); ALL ccxt exchanges (crypto + prediction), never a hardcoded subset; full read coverage of the unified API; user-owned opt-in gates for everything ccxt can do (orders, funds moves, raw endpoints); responses sized for LLM context windows.

**Non-goals (v1):** remote/hosted deployment (a remote server would have to custody keys), WebSocket streaming (v1.1 — see below), MCP data resources/prompts (tools + server instructions cover the need until hosts standardize resource UX). The one exception, added later: `ui://` resources for the MCP Apps views behind the render tools — see the decision log.

## Prior art (analyzed 2026-07-21)

Six community CCXT MCP servers plus the wider ecosystem (official Kraken/OKX/Coinbase MCP servers, single-exchange servers, MCP directories):

| lazy-dinosaur/ccxt-mcp (`@lazydino/ccxt-mcp`) | 91 | TS, stdio + deprecated SSE | 20 + 8 resources | plaintext JSON config, **named multi-account** | all, dynamic | none |

### Recurring failures this design explicitly avoids

1. **Credentials in model context** (doggybee): every private call carries apiKey/secret as tool arguments → secrets in transcripts. Here: structurally impossible — no tool schema has a credential parameter.
2. **Hardcoded exchange subsets** (doggybee 24, Nayshins 10): here everything validates against `ccxt.exchanges` at runtime.
3. **No response-size management** (all six): raw `fetchMarkets`/`fetchTickers` dumps are hundreds of KB–MB. Hosts cap tool results (~25k tokens Claude Code, ~150k chars claude.ai/Desktop) and silently replace over-cap results with a file pointer. Here: projections, `info` stripped, per-tool caps derived from those limits, in-band truncation notices, and no list-all-markets tool at all (search instead).
4. **Rails not at the execution point** (PelleNybe validates in a pre-flight tool; the execution tool re-checks nothing): here `guardOrder()` runs inside the write handler, under a per-account mutex.
5. **Per-call instance construction** (Nayshins closes all instances after every call; PelleNybe constructs per call; doggybee's trading path rebuilds + re-loads markets per order): defeats ccxt's token-bucket rate limiter and re-pays the markets cold start. Here: pooled instances for the process lifetime + disk-cached markets (24h TTL) + in-flight load dedup.
6. **stdout corruption** (pcriadoperez `print()`s in a stdio server): here `console.*` is rerouted to stderr before any import, and `exchange.log`/`verbose` are overridden (ccxt's `Exchange.log` defaults to `console.log`, and verbose mode prints signed request headers).
7. **README/tool drift** (doggybee documents ~10 tools that don't exist): here a schema test asserts the registered tool list, and the README lists tools from that same source of truth.

### Ideas adopted from prior art

- Named multi-account config + public-vs-authenticated instance pools (lazy-dinosaur).
- Trimmed DTOs, uniform `{ok, data|error}` envelope, intent-before-dispatch journal, explicit live-ack (Valet).
- Fail-closed symbol allowlist + notional cap from a live quote (PelleNybe) — enforced at execution here.
- Field-trimmed, paginated market search (pcriadoperez's `fetch_markets` was the one tool anywhere with the right instinct).
- Tiered capability posture (Kraken's official MCP: market/no-keys → read-only → opt-in trading).

## Constraints from MCP / Claude guidance

- **stdio, not localhost HTTP**: the MCP spec recommends stdio for local servers; a localhost HTTP port is reachable by other local processes and DNS-rebinding pages — pure attack surface for a key-holding server. The MCP transport is still stdio only. The account setup form is the one, deliberate, exception to "no listener": a loopback port that exists only while a setup session is open and serves nothing but that form — see "Account setup form" below for what answers each of those two threats.
- **Tool count**: schemas are injected into model context every turn; 1–15 is the sweet spot, 30+ demands search+execute. The server now registers 21 always-on tools (12 market, 3 market views, `setup_account`, 4 watch, `fetch_route`) and 20 tier tools (5 read + 3 account views, 7 trading + `execute_route`, 3 funds, `call_implicit_write`). All 41 are listed by default so the model can relay a clear "add an account" error (execution stays gated at the handler); `settings.hideDisabledTools` restores tiered registration, 21 tools with nothing configured and up to 41. That is past the comfortable range: each addition since the first 15 answers a request the existing tools could not (a view is not a row dump, a setup form is not a file edit), and `hideDisabledTools` is the lever for a lean deployment.
- **Read/write split is a hard review rule**: a catch-all `method`-param tool that can both read and write is rejected. `call_read_method`'s `^(fetch|load)` + not-`watch*`/`*Ws` gate makes the generic read tool *provably* read-only (every mutating unified method starts with `create|cancel|edit|withdraw|transfer|set|borrow|repay|close|sign`; prediction's `ethRpc`/`sendEvmTransaction` don't match either). Writes have dedicated tools.
- **Anthropic directory rejects money-moving connectors** — so the trading/funds tiers are npx/MCPB-installed, never directory-listed; a read-only listing remains possible.
- **Elicitation** (native confirm forms) shipped in Claude Code ≥ 2.1.76 but not all hosts: confirmation is elicitation-first with a preview + single-use HMAC confirm-token fallback (60s TTL, bound to the exact canonicalized payload).

| Decision | Rationale |
|---|---|
| TypeScript + official `@modelcontextprotocol/sdk`, stdio only | ccxt's source of truth is TS; npx is the lowest-friction install; stdio per spec security guidance |
| `mcp/` dir in the monorepo mirroring `cli/` (own npm package `ccxt-mcp`, manual publish, git tracks `ts/` only) | the `cli/` sub-package pattern already exists and works; in-repo keeps the server version-locked to ccxt metadata (`has`, `features`, JSDoc) |
| Deviations from `cli/`: `NodeNext` + `strict` tsconfig, config in the per-OS *config* dir (not cache dir), no cwd `keys.json` scanning | SDK needs NodeNext subpath resolution; greenfield code should be strict; an MCP host's cwd is unpredictable, so silently absorbing a credentials file from cwd is a security surprise (`CCXT_MCP_CONFIG` replaces it; the loader still accepts the legacy per-exchange shape) |
| Dual ccxt import (`import('ccxt')` → Function-eval `../../ts/ccxt`) | same trick as the CLI: published dep for users, live TS for contributors, tsc never crawls the monorepo |
| Tri-state `trading`/`funds`: `false` \| `true` (sandbox/demo only) \| `"live"` | `true` on a live account is a plausible accident; the string `"live"` cannot be produced accidentally and doubles as the explicit live-ack. Live additionally requires a user-authored cap decision (`maxOrderValue`/`maxTransferValue`: number or explicit `null`) — the default is *you must choose*, not a magic number |
| Everything ccxt offers is exposed behind user-owned switches; the only hard exclusions are structural | maintainer decision: it's the user's account and responsibility; the server provides gates, confirmation, and an audit trail rather than vetoes. Structurally impossible forever: credentials as tool params/output, config editing from the conversation (`setup_account` takes an exchange id, an account name and a sandbox flag as *prefill* and opens a form; what is saved is typed and confirmed by the human in their browser), disabling rate-limiting or enabling `verbose` |
| `call_write_method` allowlist excludes batch order placement | `createOrders` would bypass the per-order notional caps; orders go through `create_order` one at a time |
| Implicit API: GET via always-on `call_implicit_get`, non-GET via opt-in `call_implicit_write` | the HTTP verb is encoded in ccxt's implicit method names (first camel verb token after the API-section prefix), so GET-gating keeps the always-on tool honestly `readOnlyHint`; raw writes can't be validated, so they compensate with mandatory confirmation + journaling |
| Deposit addresses gated behind the funds tier | transcript-visible addresses invite address-substitution scams; near-zero value below that tier |
| `search_markets` takes `fields`, and its max limit follows row size: 100 full rows, or with `fields` as many rows as fit 55k chars (≥ 100, ≤ 1000) | a full market row is ~450 chars, so listing okx's 528 USDT-settled swaps took 6 calls and ~240k chars when the agent only wanted symbols (~15k chars). A fixed higher cap for any `fields` would let heavy fields (`limits` ≈ 170 chars/row) overflow the host limit, so the compact cap is measured on the actual projected page; 55k chars of rows keeps the whole response under 60k chars ≈ 20k tokens at 3 chars/token. Measurements under "search_markets sizing" below |
| `search_markets` meta is uniform: `returned`/`available`/`offset`/`hasMore` always, `nextOffset` when there is more, `limitClamped: {requested, applied}` when the limit was reduced, `marketTypes` on zero matches | a live agent run found no `hasMore` (only `available` + a prose notice that was null on the last page), a silent clamp of `limit: 500`, and `type: "perpetual"` answering `available: 0` with no hint — an agent could conclude okx has no perpetuals. A zero-match result now names the types the exchange actually has (and that perpetuals are `"swap"`) |
| `cancel_order` is non-destructive, never confirmed | cancels reduce risk; friction there pushes agents to leave stale orders live |
| Journal: append-only monthly JSONL, fsync'd intent-before-dispatch, no auto-delete | crash-safe audit trail; the rolling-24h daily-cap accumulator derives from it, so caps survive restarts; a 50 MB warning doubles as a runaway-loop detector |
| Doc manifest built by a small JSDoc parser over `ts/src/*.ts` (not jsdoc2md) | the doclets follow the repo's strict convention; a dependency-free parser at publish time ships 98 exchanges of per-method `params.*` docs + `@see` links in the tarball, with runtime introspection as fallback |
| Caps: search_markets 200, tickers 50 symbols, orderbook 100 levels/side, ohlcv 500 candles, trades/orders 200, global 80k-char truncation guard | each derives from the ~25k-token binding host cap (≈100k chars) with envelope headroom; the failing case is the host silently swapping the payload for a file pointer |
| `fetch_route` (market tier) + `execute_route` (trading tier) over ccxt's own `OrderRouter`, not a hand-rolled HTTP client | version-locked to the library. The read/write split holds: `fetch_route` is honestly `readOnlyHint` and never takes `balances` (holdings belong in a POST body from a configured account, not a model parameter). `execute_route` runs a cached route **by `routeId`** — exactly the route the agent quoted, never a model-supplied blob — and passes every execution choice (strategy, slippage, market fallback, freshness, retries) straight to `OrderRouter.execute`; the server adds only the user's rails. Because `OrderRouter.execute` calls `venue.createOrder` directly, each venue is handed over wrapped so every order it places is re-guarded (`guardOrder`) and journaled at the execution point, under all involved accounts' locks; a dispatch failure rethrows the original exception so OrderRouter's outcome-unknown logic still sees it. Router requests carry `User-Agent: ccxt-mcp/<v> (ccxt <v>)` for traffic attribution |
| No MCP data resources/prompts; UI resources (MCP Apps views) are the one exception | host resource UX is uneven (manual attachment in Desktop); everything a `ccxt://exchanges` resource would hold is served on demand by discovery tools; conventions ship once per session via server `instructions`. The `ui://ccxt/<view>.html` resources are different in kind: nobody attaches them — a host with MCP Apps support fetches one because a tool's `_meta.ui.resourceUri` points at it |
| Render tools `show_chart` / `show_orderbook` / `show_tickers` (market tier) implement MCP Apps (`io.modelcontextprotocol/ui`, spec 2026-01-26) | "show me the chart" is a request the data tools can only answer with rows in the transcript. Each render tool pairs a public fetch with a view: the model reads a compact summary as text (`meta.ui`: `displayed` \| `unsupported` \| `off`), the view receives the full dataset as `structuredContent`, so the dataset never enters the model context. They are read-only, need no account, and reuse the data tools' caps (500 candles, 100 levels/side, 50 symbols); `get_ohlcv`/`get_orderbook`/`get_tickers` stay the raw-data tools |
| Every render tool has a text fallback | a host without the extension ignores the `_meta` and shows the text content, so the tools stay usable as plain tools; `uiSupported()` reads the client's advertised `extensions` capability and the result says which case applied, so the model does not claim a chart the user cannot see. Terminal hosts have no surface to draw a view |
| The view payload (`structuredContent`) is attached only for hosts that advertise the MCP Apps extension; `CCXT_MCP_UI` = `auto` (default) \| `always` \| `off` overrides | only the extension makes `structuredContent` view-only: under the base protocol it is equivalent to the text content, and a host without the extension may hand it to the model instead of the compact summary (Claude Code does), which defeats the point of keeping the dataset out of the model context. So it is never sent on the off chance that something renders it. `always` is the escape hatch for a host that renders views without advertising the capability; `off` keeps the `show_*` tools listed but drops their `_meta` and answers with the text summary. Any other value (unset, a typo, an unsubstituted plugin template) is `auto`. `meta.ui` reports `displayed` \| `unsupported` \| `off` |
| `show_orderbook` states the amount unit: `meta.amountUnit` / `meta.contractSize` (also in the view payload), with base- and quote-currency depth totals in the summary | ccxt reports contract-market amounts in contracts, so with a `contractSize` other than 1 a level's amount is neither base nor quote currency, and a depth total read as base is wrong by that factor. Same convention as the notional math in `safety.ts`: a linear contract is `contractSize` of base, an inverse one `contractSize` of quote |
| `show_tickers` / `get_tickers` report `meta.missing` for requested symbols that returned no ticker | some exchanges serve one market type per call and silently drop the rest, so a shorter list would read as "those symbols do not exist"; the notice says to request spot and swap/future symbols separately |
| Views are self-contained single files with no network access | each view is one HTML document with `shared.css` and `bridge.js` inlined at read time (`/* @include */`); no `csp` block is declared, so the host applies its most restrictive default (no external origins). No external assets, no tracking; a view's only way to get new data is asking the host to re-run the same tool (refresh, timeframe switch). The view payload passes the same redaction choke point as text results |
| MCP Apps wire protocol is hand-rolled (`ui.ts` server side, `ui/bridge.js` view side), not `@modelcontextprotocol/ext-apps` | ext-apps 2.x needs the v2 SDK packages while this server is on `@modelcontextprotocol/sdk` 1.x; the server side is two constants and one `_meta` shape, so writing it by hand avoids carrying a second SDK major. The `_meta` also carries the deprecated flat `ui/resourceUri` key and the `openai/outputTemplate` alias, all pointing at the same resource |
| `setup_account` opens a loopback browser form for adding an account, instead of keys pasted in chat, an MCP Apps view, or MCP elicitation | The goal is a non-technical user who installs a plugin and has never edited a JSON file. Every in-protocol way to collect a key puts it where the model or the host transcript can see it: a tool parameter is model-authored by definition; a view posts through the host bridge; form-mode elicitation is relayed and rendered by the host, and the MCP spec tells servers not to request sensitive information through it. URL-mode elicitation (spec 2025-11-25) is the protocol's own answer — send the user to a URL out of band — and this is that idea without depending on host support for it, which is not universal: the server launches the browser itself. The keys travel browser → this process over 127.0.0.1 and nowhere else; the tool result says "a form was opened" and carries neither the URL nor anything typed. The tool is **not** annotated read-only, although the call saves nothing: it starts a browser window on the user's desktop and, with `restart: true`, throws away a form the user may be typing into — a host that auto-approves read-only tools must not run it unasked. See "Account setup form" below for the threat model |
| The form can add an account and enable trading on it; it cannot enable `funds` or `implicitWrites` | Without trading the guided flow dead-ends at "now edit a JSON file", which is the thing it exists to remove. The form therefore keeps the file's rule rather than relaxing it: testnet is the preselected environment, "allow placing orders" is off, sandbox/demo maps to `trading: true`, and live maps to `trading: "live"` only with a positive `maxOrderValue` **and** a confirmation tick — both validated server-side, not just in the page — and is saved with `confirm: "always"`, stricter than the file default. The submitted account goes through the same `validateAccount` as a file account. Withdrawals, transfers and raw write endpoints have no first-run use and the worst failure mode, so they stay file-only: a deliberate act with an editor, not a checkbox |
| The form writes the config file (atomic temp-file + rename, mode 0600, directory 0700 when created) and hot-applies the account | One store, not two: an account added by the form is the same record a hand-edited one is, shows up in `get_safety_status`, and survives a restart. Hot-apply (register its secrets with the redactor, put it in `ctx.config.accounts`, stop the private streams of an account that was replaced, evict the pooled instance) exists because "now restart your MCP host" is where a non-technical user gives up; the pools read the account map on every call, so no other state needs rebuilding. The streams are the exception that has to be handled: a private stream holds its own reference to the old client and would keep reconnecting with the old keys, on the old environment, under the same account name — so replacing an account stops that account's streams (they are not migrated; the new record may be another environment or another exchange). With `hideDisabledTools` the read and trading tiers a saved account newly enables are registered on the running server, which announces them with `notifications/tools/list_changed`; a host that does not refresh its tool list, or a registration that fails, leaves a restart as the fallback, and the form and the tool notice say so. Every save is journaled (names and modes, never values) |
| Account views `show_balance` / `show_orders` / `show_positions` (read tier) and `show_chart`'s optional `account` overlay | "Show me my balance" deserves a table for the same reason "show me the chart" deserves a chart. They are the read-tier twins of the market views: the same private fetches as `get_balance` / `get_orders` / `get_positions` (shared functions in `tools/read.ts`, so the caps and the status handling cannot diverge), `readOnlyHint`, the same `meta.ui` contract, the same redaction choke point, no raw `info`. The model gets totals and a few rows (ten holdings / ten orders / twenty positions, `meta.omitted` for the rest); the view gets the user's full data, which is the user's to look at. Valuation in `show_balance` is best effort by construction and may be partial: one cash currency per account (the candidate that values the most of what is held, so a USD account on a USD venue is not valued in USDT with its cash left out), prices from one `fetchTickers` call, never a request per holding. The result always names the quote it used, and a holding without a usable price (none listed, or a zero / negative ticker) is never summed as zero: it is counted (`unpricedCurrencies`), the total is flagged as partial (`totalValuePartial`) and a notice says so; a dollar currency counted 1:1 for want of a market is named too (`valuedAtPar`). An exchange without `fetchTickers` is not valued at all. `show_positions` totals unrealized PnL **per settle currency** — a single figure only together with its currency, a per-currency map when positions settle in several, and no figure for a currency in which a position reports none — because 150 USDT and -0.02 BTC are not 149.98 of anything. The chart overlay never blocks the chart: the account is resolved before anything is fetched (an unknown account, one on another exchange, or one in the other namespace of a dual crypto/prediction id is an error), but a failed open-orders read only adds a notice and the chart is still drawn. Candles and order lines have to describe the same market, and a testnet's prices are not the live market's: for a sandbox or demo account the candles are read from that account's environment, and when that environment cannot serve them the chart falls back to live candles and says so (`candlesEnvironment` next to `environment`, plus a notice) — the mismatch is never silent |
| The onboarding skill (`plugin/skills/ccxt-get-started`) is plugin-native: its only copy is in the plugin, and `sync-plugin` / `plugin.test.ts` declare skills as either synced or plugin-native | It is a script for the plugin's first run (which starter prompt, which form), not knowledge about the server, so it does not belong among the repo's `.claude/skills` that `npx skills add ccxt/ccxt` offers to people who never installed the plugin. With one copy there is nothing to keep byte-identical; the invariant that replaced it is that every directory under `plugin/skills` is declared as one kind or the other, and a plugin-native skill has no canonical twin. For OpenAI hosts it is wired as `extensions["com.openai"].onboardingSkill` (a path to the SKILL.md relative to the plugin root) in the portable manifest and, under the same key, in the Codex compatibility manifest: Codex CLI 0.171.0 resolves both through `plugin/read`, and ignores a top-level or `interface`-level key. The Agent Plugins 1.0.0 schema neither describes nor rejects it (it constrains `extensions.<namespace>` to "an object") |
| One plugin directory (`plugin/`) for Claude Code, OpenAI Codex / ChatGPT desktop and xAI Grok; the server is pinned (`npx -y ccxt-mcp@<plugin version>`) and the bundled skill is a real copy | Grok documents reading Claude Code marketplaces/plugins as-is, and Codex needs only its own manifest + marketplace file beside the Claude ones, so one directory with per-host manifests avoids three drifting copies. Pinning makes a plugin update the unit of server update; the cost is ordering — the pin follows `package.json`, so a change that adds server features the skill references must be followed by an MCP Release dispatch, and until then the plugin installs the previously published server (the skill tells the model to fall back to the `get_*` tools when `show_*` are absent). The skill is copied by `npm run sync-plugin` (checked in CI) rather than symlinked because ZIP uploads, Windows checkouts and non-Claude hosts do not reliably follow symlinks |

## Account setup form (threat model)

`ts/setup.ts` serves one page over loopback HTTP while a setup session is open. What it defends against, and what it does not claim:

- **Loopback bind, ephemeral port, short life.** The listener binds `127.0.0.1` on a port the OS picks, exists only while a session is open, and closes with it. A session ends on a successful save or after 10 minutes. Every request that does not prove it belongs to the session gets an identical empty 404, so a port scan learns nothing. There is deliberately no "close after N bad requests" switch: any web page can fire blind requests at a loopback port, so such a counter would protect nothing the token does not already protect, and would hand every open tab a way to close the form the user is typing into.
- **One form at a time, and a repeat call does not replace it.** `setup_account` while a form is live reuses it: a form a browser has already loaded is left exactly as it is (no new window, the call's prefill is ignored, the result says "already open"); one no browser has loaded yet is launched again. Only an explicit `restart: true` retires a live form and whatever was typed into it. The caller is a model that can be talked into calling again, and the user may be mid-paste.
- **The link is never on a command line.** The form's address carries a 128-bit random token (compared in constant time). Command lines are readable by every local user (`ps`, `/proc/<pid>/cmdline`) for as long as the process lives, so the browser is not launched on the address: it is launched on a local file — mode 0600, inside a fresh 0700 directory — that only redirects to it. The launcher gets that file's path as one argv element, no shell on any platform. The file is deleted on the first page load and never outlives the session. The token appears in no tool result, log line, journal record or error.
- **The session is bound to the first page load.** The first browser to load the form receives an `HttpOnly; SameSite=Strict` cookie scoped to the form's own path, and the URL token is consumed: from then on every request needs the cookie, and the URL alone — read from the address bar, from browser history, or from the launch file a moment too late — gets the same empty 404 as a wrong token. Before a browser is bound, nothing but the page itself is served.
- **Requests must come from the page this server served.** Every request is checked against a `Host` allow-list (`127.0.0.1:<port>` / `localhost:<port>`), which defeats DNS rebinding. State-changing requests additionally need `POST`, an `Origin` equal to that host (and `Sec-Fetch-Site: same-origin` when the browser sends it), an `application/json` body (which a cross-site form cannot produce without a preflight that is never answered — no CORS headers are sent at all), and a per-session CSRF nonce in a custom header. The page is served with a nonce-based CSP (`default-src 'none'`, `connect-src 'self'`), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
- **Nothing typed there is echoed anywhere.** The credential values a request puts to use are registered with the redactor, in the exact form sent to the exchange, before the connection test — so an exchange error that echoes a key is scrubbed before it reaches the page or the log. Values from a test that did not end in a save are unregistered again once the response is out, so a mistyped field cannot go on redacting unrelated output. The save is journaled and logged as names and modes only.
- **No funds tier, and live trading only with a cap and a second yes** (see the decision log) — enforced by the server on the submitted body, not by the page's controls. Replacing an existing account needs an explicit yes in the page, stops that account's private streams and is recorded as a replacement.
- **The honest limit: who the form protects against, and who it does not.** It protects against three things: a web page in the user's browser (it cannot read, submit or close the form), another OS user on the machine (the link is in no process list and the launch file is not theirs to read), and the model reading tool output (no result, log or error carries the link or a key, so a model limited to this server's tools cannot supply, read or change a credential or a tier). It does **not** protect against a process running as the same OS user — including an agent with an unrestricted shell or file access. Such a process can read the launch file in the moment before the browser does, and, more to the point, could always read or edit the config file directly: the form gives it nothing it did not already have, and nothing here claims it "cannot find" the form. That exposure is governed by the MCP host's permission model (deny rules for the config path, no unrestricted shell for an agent that trades), exactly as before. Exchange-side backstops (withdrawals disabled on the key, IP allow-list) remain the controls that hold when the machine itself is compromised.

## Review hardening (pre-release adversarial review, 2026-07-22)

A four-perspective adversarial review (security, ccxt correctness, MCP-spec usage, agent DX) with independent verification of every finding produced 19 confirmed issues, all fixed before release. The ones that are now load-bearing rules:

- **`params.cost`/`params.quoteOrderQty` are rejected by `guardOrder`** — ccxt market orders read a quote-side size from params, which would execute at that size while the caps valued only the positional amount. Quote-side spend must go through the top-level `cost` parameter, which `guardCost` values. Enforced at the guard, so `edit_order` is covered too.
- **Elicitation failure fails closed** — on an elicitation-capable host, a failed/timed-out human prompt returns `CONFIRM_UNAVAILABLE` and never falls back to the model-redeemable confirm token (which would let the model confirm its own write). The token flow is reserved for hosts without elicitation. Elicitation gets a 5-minute timeout (humans reading withdrawal previews are slower than the SDK's 60s default), and an accept-with-`confirm:false` counts as an explicit decline.
- **Address-material gating is a pattern, not an allowlist** — `/deposit.?address|withdraw.?address|withdrawal.?whitelist/i` gates both unified reads (`call_read_method`) and raw GET endpoints (`call_implicit_get`) behind the funds tier; an enumeration of method names would silently fall behind ccxt.
- **`maxDailyValue` is the combined rolling cap** over orders *and* fund moves (the journal accumulator counts both, so both are bound by it).
- **Valuation correctness**: inverse (coin-margined) contracts are valued `amount × contractSize` (price-independent); prediction outcomes are valued `amount × price` in USD (all prediction venues settle in USD-pegged collateral) — without this, any numeric `maxOrderValue` made prediction trading impossible since live trading *requires* a cap decision.
- **Sell-by-cost is refused** where the exchange lacks `createMarketSellOrderWithCost` — the buy-side emulation convention would sell `cost` units of *base*.
- Symbol allow/deny lists apply to every symbol-bearing write (`set_leverage`, `set_margin_mode`, `call_write_method` position/margin ops), not just orders; `isImplicitMethod` requires own-property status so verb-shaped base helpers (`handlePostOnly`, …) aren't callable; the stderr reroute passes through the redactor; two-phase confirm payloads are built from raw args so identical re-calls digest identically.

## First-time-agent DX passes (three rounds)

Three independent fresh agents drove the server through the wire interface only (tool list + JSON responses, no source), each hunting for what the prior rounds missed. Verdicts 8.5 → 7.5 → 8.0; safety held airtight in every round (notional cap unbypassable even via a `params` override, funds allowlist, tier-gated tool existence, token binding, zero credential leakage). Load-bearing fixes that came out of them:

- **`toContent` output is always valid JSON.** Oversized array data is tail-dropped; an oversized non-array payload (a raw implicit-endpoint response) has its `data` replaced by a `{truncated:true}` marker with `meta.truncated` — a byte-cut that yields unparseable JSON is never emitted. This is the single most important robustness invariant: an agent must always be able to `JSON.parse` a result.
- **No silent-wrong-answer traps at the input boundary**: malformed `since` → `BAD_REQUEST` (not a silently-defaulted recent window); a `marketType` that conflicts with an explicit symbol → `meta.notice` (not the wrong market's data); order-book levels normalized to the unified `[price, amount]` (some venues append a per-level timestamp an agent could misread); `includeInfo` dropped on multi-symbol calls says so.
- **Discovery isn't blind to the long tail**: `describe_method` keyword search defaults to binance's complete surface and matches on whitespace-split tokens, so "open interest" / "funding rate" resolve.
- **Envelope/hint consistency**: private-read error envelopes carry the account's `exchange`; no error ships an empty `hint`; `hasMore` is always a real boolean.

## WebSocket streaming (v1.1 — landed)

MCP hosts surface no model-visible push today, but the stdio server is long-lived — so streaming is **subscribe + poll**, implemented in `subscriptions.ts` + `tools/watch.ts`. Two access patterns fall out of ccxt.pro's per-channel cache and `newUpdates` mode: **state** streams — snapshots of current state: `watchTicker(s)`, `watchOrderBook(ForSymbols)`, `watchOHLCV(ForSymbols)`, `watchBalance`, `watchPositions`, `watchBidsAsks`, `watchMarkPrice(s)`, `watchFundingRate(s)`; **event** streams — logs of discrete events: `watchTrades`, `watchOrders`, `watchMyTrades`, `watch(My)Liquidations`. Under `newUpdates=true` a state `watch*` returns only the *changed subset* each cycle (one ticker of the set, the position that moved, the forming candle), so storing that as the snapshot would let a partial delta masquerade as the full set (e.g. `watchPositions` after one position moved would look like the only open position — the blocker this fixes). Instead each state subscription keeps a **merge accumulator** (see `accumulate()`): `replace` for single whole objects (ticker/book/balance), `mergeDict` by symbol (tickers/bidsAsks/markPrices), `upsertArray` by symbol+side (positions), `mergeBook` by symbol (orderBookForSymbols), and a timestamp-keyed `window` for ohlcv — so `watch_read` always returns the coherent full snapshot in `latest` (no history buffer, plus `updatesSinceRead` for freshness). Event streams accumulate in a ring buffer that `watch_read` drains oldest-first via a cursor. `streamKind` on subscribe/read tells the agent which it is. `watch_read(waitForChange:true, timeoutMs?)` blocks until the next update lands (or the stream stops/times out) — a long-poll that is the closest thing to a push in a request/response protocol, and the right fit for slow event streams (order fills, position changes) without spin-polling.
- `watch_subscribe` validates the `watch*` name (`/^watch[A-Z]/` + `has[method]`), starts a background loop, and returns a `subscriptionId`. Public streams use a **ref-counted stream pool** in `pools.ts` (separate from the LRU REST pool so a watched socket is never evicted); private streams (`watchOrders`/`watchMyTrades`/…) reuse the per-account instance. `newUpdates` mode is on, so watch\* return incremental updates.
- The loop `Promise.race`s each `watch*` call against a stop signal, so unsubscribe breaks it promptly; updates are trimmed (order-book depth, ohlcv/trade/order batches, `info` stripped) into a bounded ring buffer (200) with a monotonic seq.
- `watch_read` drains updates **oldest-first** since a cursor (capped at 50, projected) and returns `nextCursor` + `moreBuffered` so a client walks the buffer without skipping or replaying (a naive newest-first drain silently lost older buffered updates — caught in review); `watch_unsubscribe` stops + releases (closing the public socket on last ref, best-effort `unWatch*` on shared account instances, guarded so a sibling stream isn't torn down); `watch_list` shows active streams. An **idle TTL (10 min, unref'd timer)** auto-stops abandoned streams; there is **no subscription-count cap by default** (streaming is read-only and single-user; the idle TTL, shared sockets, and exchange-side stream limits are the real backstops) — `settings.maxSubscriptions` (default 0 = unlimited) is an optional runaway limit, reserved synchronously across the acquire when set; loops give up after 5 consecutive errors, **release the socket immediately** and set a 30s reaper (so a dead stream frees its slot), surfacing an actionable `{code, retryable, hint}` error on the next `watch_read`. Private streams (`watchOrders`/…) require an account (rejected up front). Verified live against Binance (concurrent `watchOHLCV`/`watchTicker`/`watchTrades`, cursor walk, private-account guard).
