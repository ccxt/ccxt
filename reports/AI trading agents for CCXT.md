# Give Agents Workflows and Rails, Not Alpha

The people who build AI trading agents have settled on one architecture. Agents gather data with tools, reason through specialised roles, emit a structured thesis, and then pass every order through a *deterministic* risk gate that the model cannot override. Only after that gate does a confirmed and journaled execution happen. The evidence says the scaffolding matters more than the model. Live and leakage-free benchmarks keep finding that frontier LLMs rarely beat simple baselines once costs and regime changes are counted, and that **architecture and risk control drive results more than the choice of backbone**. CCXT is unusually well placed here. Every major exchange shipped a single-venue agent kit in 2026, and the official `ccxt-mcp` server is already the most safety-hardened venue-neutral trading MCP in the ecosystem: 34 tools, opt-in capability tiers, notional and daily caps, fail-closed confirmation and an append-only journal. What CCXT lacks is everything *around* order placement. There are no workflow skills (brief → size → gate → execute → journal → review), no simulated-fill paper tier, no kill switch, no position, leverage, loss or order-rate limits, no cross-venue scanners or portfolio view, and no point-in-time replay or evaluation harness, although `examples/mcp-arena` already holds most of one. The highest-leverage builds are the rails and the paper tier in the MCP server, a small set of script-backed workflow skills modelled on `tradermonty/claude-trading-skills`, and cross-venue analytics that no single-exchange kit can offer. Backtesting engines and "AI alpha" agents should stay out of scope.

## Seven patterns recur from hedge-fund graphs to SKILL.md packs

The flagship open-source design is **TauricResearch/TradingAgents** (about 122.7k stars), which simulates a trading firm. Parallel fundamentals, sentiment, news and technical analysts feed a bull/bear researcher debate. A trader agent proposes timing and size, and a risk-management team plus a portfolio manager approve or reject the proposal before it reaches a *simulated* exchange. It runs on LangGraph with per-node checkpoints, separate "deep-think" and "quick-think" LLM tiers to control cost, configurable debate and risk rounds, and a structured decision log ([GitHub](https://github.com/TauricResearch/TradingAgents)). Its changelog is instructive. Versions 0.4 through 0.7 (Aug–Oct 2026) were largely look-ahead fixes, point-in-time SEC EDGAR data, and scoring each decision from the *next* close, which suggests the early backtests were contaminated ([GitHub](https://github.com/TauricResearch/TradingAgents)). The paper's headline of ≥23% cumulative return on three large-cap stocks did not model slippage ([stork.ai](https://stork.ai/blog/this-ai-argues-its-way-to-profit)). Crypto is supported only through Yahoo tickers such as `BTC-USD`, with no exchange connectivity. Community forks such as TradingAgents-CryptoA and the Go/MCP project CryptoFunk add exchange access by plugging in **CCXT** ([awesome-trading-agents](https://github.com/LLMQuant/awesome-trading-agents)).

**Trading-R1** goes the opposite way and distils that multi-agent analysis into one Qwen3-4B model. The model is trained with an easy-to-hard SFT+GRPO curriculum that rewards, in order, a well-formed thesis, evidence-grounded claims and finally market-aligned decisions. Its corpus is a 100k-sample, five-source dataset covering 14 equities ([Emergent Mind](https://www.emergentmind.com/papers/2509.11420); [The Moonlight](https://www.themoonlight.io/en/review/trading-r1-financial-trading-with-llm-reasoning-via-reinforcement-learning)). The public repo is now a terminal app that needs a Tauric API key, so for CCXT the reusable part is the output contract rather than weights: a sectioned thesis whose claims cite evidence and which ends in a discrete decision ([GitHub](https://github.com/TauricResearch/Trading-R1)). The **LLMQuant/awesome-trading-agents** catalogue shows the wider field splitting into four camps. The first is academic memory and reflection agents: FinMem's layered memory, FinAgent's dual-level reflection, FinCon's manager–analyst hierarchy with CVaR risk control, and CryptoTrade's reflection agent over on-chain data and news. The second is popular "AI hedge fund" graphs, such as virattt/ai-hedge-fund with investor-persona analysts and a risk manager that sets position limits. The third is code-generating quant R&D loops such as Microsoft RD-Agent(Q), which runs hypothesis → factor code → backtest → bandit feedback. The fourth is a 2026 wave of exchange-issued MCP servers and SKILL.md packs ([awesome-trading-agents](https://github.com/LLMQuant/awesome-trading-agents); [FinCon](https://arxiv.org/html/2407.06567v2); [CryptoTrade](https://aclanthology.org/2024.emnlp-main.63/); [RD-Agent(Q)](https://papers.nips.cc/paper_files/paper/2025/hash/ac5c2b6e423883cbcacbcccf88491b78-Abstract-Datasets_and_Benchmarks_Track.html)).

On the "assist the trader" side, **tradermonty/claude-trading-skills** is the clearest template for what CCXT skills could become. It has 74 skills in nine groups. Most of them are a SKILL.md wrapped around a deterministic Python script that writes a schema-versioned JSON plus a Markdown report to `reports/`. Skills are chained through YAML workflow manifests such as `swing-opportunity-daily`, which runs screener → `drawdown-circuit-breaker` → technical analysis → `position-sizer` → `trader-memory-core` → `pre-trade-discipline-gate` ([GitHub](https://github.com/tradermonty/claude-trading-skills)). Its `position-sizer` is a good model. It is stdlib-only, supports fixed-fractional, ATR and half-Kelly modes, lets the strictest constraint win, follows a "floor, never round up" rule, and reports which constraint was binding ([SKILL.md](https://raw.githubusercontent.com/tradermonty/claude-trading-skills/main/skills/position-sizer/SKILL.md)). The repo **never executes trades**; its furthest step is an "order template". Anthropic's **financial-services plugins** draw the same line. Commands such as `/morning-note`, `/thesis`, `/catalysts` and `/screen` produce drafts for human review, and the agents "do not make investment recommendations or execute transactions" ([GitHub](https://github.com/anthropics/financial-services-plugins)).

Broker and data MCPs add the execution-side patterns. Alpaca's official server defaults to paper trading and enforces a server-side toolset allowlist ([GitHub](https://github.com/alpacahq/alpaca-mcp-server)). The community Schwab server is read-only by default. It routes approval out-of-band through Discord or Signal and binds `place_previewed_order` to a `preview_id`, so the model cannot swap the order after review ([GitHub](https://github.com/jkoelker/schwab-mcp)). Massive (formerly Polygon) shrinks a huge API to three meta-tools, `search_endpoints`, `call_api` and SQL over cached results, and OpenBB hides tools behind discovery categories to save context ([GitHub](https://github.com/massive-com/mcp_massive); [OpenBB docs](https://docs.openbb.co/python/extensions/interface/openbb-mcp)). QuantConnect's MCP closes the research loop from strategy files to backtest, optimisation and paper deployment ([GitHub](https://github.com/QuantConnect/mcp-server)). In crypto, Hummingbot's **Condor** harness pairs a trading MCP with a separate MCP for skills, memory and journals, keeps one strategy file per agent, and states that "risk guardrails cannot be bypassed by the agent" ([Condor docs](https://condor.hummingbot.org/trading-agents/overview); [MCP tools](https://condor.hummingbot.org/trading-agents/mcp-tools)).

Taken together, the sources converge on seven reusable patterns:

| Pattern | Exemplars | What CCXT has today |
|---|---|---|
| Role-specialised analysts (by data type or persona) | TradingAgents, ai-hedge-fund, QuantAgent | Data methods only; no analyst templates |
| Adversarial debate and manager approval gate | TradingAgents, FinCon, ContestTrade | None |
| Structured thesis/decision output | Trading-R1, TradingAgents v0.2.4+ | None |
| Deterministic risk gate outside the LLM | nofx, Condor, tradermonty gates, Alpaca/Schwab | `guardOrder()` notional/daily caps in ccxt-mcp |
| Preview → human confirm → journal | Schwab `preview_id`, OKX approvals, Valet | Elicitation-first confirm + HMAC token + JSONL journal |
| Reflection memory and post-mortems | FinMem, FinAgent, CryptoTrade, trader-memory-core | Order-intent journal only; no rationale or outcomes |
| Paper first, then evaluation harness | Kraken CLI paper engine, Alpaca paper default, QuantConnect | `examples/mcp-arena/paper-broker.mjs` (example only) |

## Benchmarks reward scaffolding and risk control, not model IQ

The case for building rails and workflows rather than "smarter" agents rests on a consistent body of evaluation results. **LiveTradeBench** ran 21 LLMs for 50 live days across US stocks and Polymarket. High LMArena scores did not predict trading results, and performance in the two markets was almost uncorrelated ([arXiv](https://arxiv.org/abs/2511.03628)). **Agent Market Arena** concluded that "agent architecture affects profitability more than the choice of LLM backbone" ([arXiv](https://arxiv.org/abs/2510.11695)). **AI-Trader**, which trades live across US stocks, A-shares and crypto, found that general intelligence "does not automatically translate to effective trading capability" and that risk control drove robustness across markets ([arXiv](https://arxiv.org/abs/2512.10971v1)). **FINSABER** backtested from 2000 to 2024 with delisted stocks included. It found that LLM advantages "often vanish under broader and longer evaluations": agents were too timid in bull markets and lost disproportionately in bear markets ([arXiv](https://arxiv.org/html/2505.07078v2)). **StockBench** found agents modestly ahead of buy-and-hold in a short post-cutoff window but failing in the downturn ([arXiv](https://arxiv.org/html/2510.02209v1)).

Real money tells the same story more loudly. In **Alpha Arena Season 1**, six frontier LLMs each traded $10k on Hyperliquid perps for about two weeks. Qwen3-Max finished roughly +22%, while GPT-5 and Gemini 2.5 Pro posted heavy losses and most models ended in the red ([Decrypt](https://decrypt.co/345006/ai-crypto-trading-showdown-deepseek-grok-winning-gemini-implodes); [Forklog](https://forklog.com/en/four-out-of-six-ai-models-suffer-losses-in-trading-tournament/)). Post-mortems blame overtrading into fees, excessive leverage and poor sizing ([iweaver](https://iweaver.ai/blog/alpha-arena-ai-trading-season-1-results)). Nof1's founder concluded it is "not yet feasible to directly hand over money to an LLM and let it trade on its own" ([KuCoin news](https://www.kucoin.com/news/flash/ai-trading-models-struggle-in-live-market-tests-majority-of-systems-report-losses)). CCXT's own arena gave nine models $100 for an hour against a realistic paper broker, and its README cautions readers to treat the results "as behaviour, not as a leaderboard" ([examples/mcp-arena/README.md](../examples/mcp-arena/README.md)).

Contamination is the second lesson. Backtests leak through inputs (future data, revised news) and through **weights**, because the model has memorised what happened. Look-Ahead-Bench reports severe alpha decay for standard LLMs once they are tested past their knowledge cutoff ([arXiv](https://arxiv.org/pdf/2601.13770)). The FinCAD paper names "parametric look-ahead" and shows that existing defences mostly address inputs only ([arXiv](https://arxiv.org/abs/2605.24564)). Live forward tests and post-cutoff windows are the only robust remedies.

Security research adds a third lesson. "AI Agents in Cryptoland" hijacked ElizaOS trading agents (managing over $25M) through **memory injection** delivered via Discord, triggering unauthorised leveraged trades and transfers. Prompt-level defences were weak ([arXiv](https://arxiv.org/abs/2503.16248v3)). Regulated markets reached the same conclusion long ago. SEC Rule 15c3-5 requires pre-trade controls under the broker's "direct and exclusive control" ([FINRA](https://finra.org/industry/market-access)), and FIA guidance treats localised pre-trade limits and a **kill switch** that disables trading and cancels resting orders as baseline safeguards ([FIA 2024](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)).

The implication for CCXT is direct. Most of the field has learned to stop trusting the model's judgment. What helps end users is better data, enforced limits, simulated practice, and honest evaluation with costs, baselines and multiple regimes.

## Exchanges ship single-venue kits; the cross-venue lane is open

Every major venue now courts agent order flow with its own tooling. Binance has Agent OS with a hosted MCP and a Skills Hub backed by `binance-cli`. OKX has the Agent Trade Kit, an MCP plus CLI with roughly 80 tools and approval on writes. Kraken has an open-source CLI with a built-in MCP and a local paper-trading engine on live data. Bitget has its Agent Hub. Coinbase has AgentKit, Agentic Wallets with spend caps, and Coinbase for Agents ([crypto.news](https://crypto.news/binance-launches-agent-os-and-mcp-trading-server/); [okx/agent-trade-kit](https://github.com/okx/agent-trade-kit); [Kraken blog](https://blog.kraken.com/news/industry-news/announcing-the-kraken-cli); [Cointelegraph](https://cointelegraph.com/news/coinbase-launches-crypto-wallets-built-ai-agents)). Together these set a 2026 baseline of **CLI + MCP + skills bundle + local paper engine**. Each kit is confined to one exchange, so none can compare funding across venues, route an order, aggregate a portfolio or normalise schemas. Those cross-venue jobs are CCXT's native strengths, and its `fetch_route`/`execute_route` tools over the OrderRouter already point that way ([wiki/OrderRouter.md](../wiki/OrderRouter.md)).

The community CCXT MCP servers have mostly squandered that advantage. CCXT's own prior-art review of six servers found credentials passed as tool parameters (and so leaked into transcripts), hardcoded exchange subsets, unbounded responses, rails that could be bypassed at execution, and READMEs describing tools that do not exist. Only Valet, with dry-run by default, a live acknowledgement, caps and an intent journal, earned a "best-in-class" rating ([mcp/DESIGN.md](../mcp/DESIGN.md)). The official `ccxt-mcp` was built against that list, and on the safety axes it matches or exceeds the exchange kits.

## CCXT's assets stop at the order ticket

The in-repo inventory shows a sharp asymmetry. The nine first-party skills in `.claude/skills/` are seven language skills, `ccxt-cli` and `ccxt-mcp`, and every one is documentation-only Markdown with no scripts. They teach *how to call the API*, and none teaches *how to run a trading workflow* ([.claude/skills/README.md](../.claude/skills/README.md)). The third-party Binance skills in the same folder already use the richer pattern of scripts plus `preflight` and `security` references. Some of them (`trading-signal`, `crypto-market-rank`, `meme-rush`) also bring social-derived, untrusted text into the agent's context, which is the injection surface described above. The CLI explicitly "does not ask for a confirmation", so it has no rails at all ([wiki/CLI.md](../wiki/CLI.md)).

The MCP server is the strong asset. It runs local stdio only, references accounts by name, redacts every output, and exposes five tiers that only the config file can enable ("there is no tool that edits config, so a conversation can never grant itself permissions"). Live trading requires `"live"` plus a user-authored `maxOrderValue`. `guardOrder()` runs at the execution point under a per-account mutex and rejects `cost`/`quoteOrderQty` bypasses. `maxDailyValue` is a rolling 24-hour cap rebuilt from the journal, confirmation is elicitation-first and fails closed, and batch `createOrders` is deliberately excluded so per-order caps cannot be dodged ([mcp/README.md](../mcp/README.md); [mcp/DESIGN.md](../mcp/DESIGN.md)). The library underneath also exposes most of the market-structure data an agent needs. Approximate counts of `has` flags: `fetchFundingRates` in 29 exchanges, `fetchOpenInterest` 28, `fetchFundingRateHistory` 42, `fetchLedger` 38, `fetchLeverageTiers` 12, `cancelAllOrdersAfter` (an exchange-side dead-man switch) 14, and `fetchOptionChain`/`fetchLiquidations` 4 each ([ts/src](../ts/src)).

The gaps line up almost one-for-one with what the research says matters:

| Capability the field relies on | CCXT status | Evidence / inspiration |
|---|---|---|
| Kill switch the model cannot clear | Missing; `cancel_all_orders` and `cancelAllOrdersAfter` exist but only the model can call them | FIA kill switch; Glama Hyperliquid emergency stop |
| Position / leverage / drawdown / order-rate limits | Missing; caps are notional and daily only, with no `maxLeverage` despite an allowlisted `set_leverage` | Alpha Arena leverage and overtrading losses; nofx, Condor |
| Paper trading with simulated fills | Partial: `dryRun` returns a preview and sends nothing, but never simulates a fill ([mcp/ts/tools/trade.ts](../mcp/ts/tools/trade.ts)); a realistic broker exists only in `examples/mcp-arena/paper-broker.mjs` | Kraken paper engine, Alpaca paper default |
| Workflow skills (brief, size, gate, journal, review) | Missing | tradermonty manifests; Anthropic FS `/morning-note`, `/thesis` |
| Decision/rationale memory and post-mortems | Missing; the journal records order intents only | FinMem, CryptoTrade, trader-memory-core, tradememory-protocol |
| Cross-venue scanners and portfolio NAV | Missing; portfolio aggregation is on the v2 roadmap | Single-venue kits cannot do this |
| Point-in-time replay and agent evaluation | Missing; the arena is an example, not a product | LiveTradeBench, FINSABER, TradingAgents v0.5+ |
| Discoverability | `llms.txt` never mentions the MCP server | [llms.txt](../llms.txt) |

One default deserves attention. The `ccxt-mcp` skill itself warns that under the default `live` confirm policy, "sandbox/demo orders execute immediately without a preview, and `maxOrderValue: null` means no cap" ([.claude/skills/ccxt-mcp/SKILL.md](../.claude/skills/ccxt-mcp/SKILL.md)). That is reasonable for testing. It does mean, however, that practice runs do not rehearse the constraints a live run will face, and any paper or eval workflow should set explicit caps.

## Prioritized build list for end users and agents

The ordering follows three rules drawn from the evidence. Rails come before features, because risk control is what separates surviving agents. Simulation comes before analytics, because users need a safe place to run anything else. Cross-venue features come before single-venue duplicates, because that is where CCXT is uniquely positioned. Effort is my own estimate for one experienced contributor (XS < 1 day, S ≈ 2–4 days, M ≈ 1–2 weeks, L ≈ 3–6 weeks). "Skill" means a SKILL.md, ideally with a deterministic script that emits schema-versioned JSON. "MCP" means a change to `mcp/`.

Some candidates are deliberately left out. A native backtesting engine would duplicate Freqtrade, Jesse, LEAN and NautilusTrader, which CCXT's own comparison pages already position as complements ([wiki/comparisons](../wiki/comparisons)). Alpha-generating or "autonomous trader" agents are excluded for the reasons in the benchmark section. Any agent-facing `withdraw` workflow is excluded too: it already sits behind the `funds` tier, and the repo's own rules forbid live withdraw testing ([CLAUDE.md](../CLAUDE.md)). A first-class integration of social-signal feeds should also wait until research and execution contexts are separated as described in P0-4, given the memory-injection results.

Two uncertainties should shape sequencing. First, the maintainers' appetite for policy-style limits is untested. DESIGN.md frames the server as providing "gates… rather than vetoes", so every P0-2 limit should be an optional, user-authored config switch rather than a hard-coded rule ([mcp/DESIGN.md](../mcp/DESIGN.md)). Second, there is no demand data for any single workflow. Shipping P0-4, P0-5 and P1-7 as cheap skills first, and watching usage, is a lower-risk way to learn than building the replay harness up front.

## Conclusion

The research turns the usual framing upside down. The scarce resource in agentic trading is not a model that predicts prices. Benchmarks show none does so reliably, and live arenas show what happens when one is trusted. The scarce resource is a trustworthy *operating environment*: enforced limits, a kill switch, realistic simulation, honest evaluation and a memory of why trades were made. CCXT has already built the hardest and least glamorous part of that environment in `ccxt-mcp`. The remaining work is mostly composition: promoting an existing paper broker, adding a handful of config-owned limits, and writing script-backed skills that chain the unified methods CCXT already exposes.

That composition also makes strategic sense. Each exchange's agent kit is locked to its own venue, while CCXT's comparative advantage (one schema across 100+ venues) is exactly what cross-venue scanners, portfolio aggregation, routing and venue-neutral paper trading need. If CCXT ships the P0 rails and simulation alongside a few cross-venue workflow skills, it becomes the default safe substrate that TradingAgents-style frameworks, Freqtrade-style bots and single-user Claude workflows all plug into, without CCXT having to claim that any agent can trade profitably.
