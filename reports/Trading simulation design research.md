# Build the simulator inside CCXT, own the clock

CCXT should build its premium simulation module as **an in-process simulated exchange that exposes the same unified methods (B), driven by an explicit virtual clock and event queue (C)**. A server (A) should come later, only as a thin lockstep façade over that same core, and it should speak the CCXT unified API, not 100+ emulated exchange-native APIs. Every serious engine surveyed already works this way. NautilusTrader, LEAN, OctoBot, Freqtrade, Jesse, hftbacktest and Barter all run the simulator in the strategy's process and swap components rather than endpoints. The only production "server that acts as the exchange" systems are real-time paper and testnet endpoints, which simulate fills crudely and cannot replay history, and tardis-machine, which replays market data only and never executes orders. Time control is the deciding factor. In every system that gets reproducibility right (Nautilus `VirtualClock`, ABIDES' kernel, TigerBeetle's VOPR), the simulator owns a forward-only clock. "Rewind" means restoring a snapshot and re-simulating deterministically. Nobody runs a clock backwards. CCXT currently reads the host wall clock directly (`const now = Date.now; const milliseconds = now;` in [time.ts](../ts/src/base/functions/time.ts)). So the first deliverable, whichever architecture is chosen, is a clock seam through the base class, the throttler and the WebSocket client. Past that seam, CCXT has advantages no competitor has: unified structures across 100+ venues, per-market fees and precision, `features` metadata, an existing WS frame-replay harness and a precedent for hand-mirrored cross-language modules. Together these make a bar-, trade- and L2-capable simulator that is transpilable, deterministic and parity-preserving a realistic multi-phase project rather than a rewrite.

## Every mature engine simulates in-process; servers only appear for real-time plumbing

Industry practice splits cleanly along the A/B/C axis. The "same API, different base URL" server model (A) exists almost entirely as real-time paper trading and testnets. **Alpaca paper** uses the live API at `paper-api.alpaca.markets` and fills an order only when it becomes marketable against the NBBO. It gives **random partial fills 10% of the time**, and it explicitly does not simulate market impact, queue position, latency slippage or quantity versus displayed NBBO size ([Alpaca docs mirror](https://github.com/alpacahq/alpaca-docs/blob/master/content/trading/paper-trading.md)). **IBKR paper** fills from top of book with no market impact, and "always simulates" stops and complex orders, which "may behave differently from production" ([IBKR guides](https://www.ibkrguides.com/clientportal/aboutpapertradingaccounts.htm)). The **Binance spot testnet** runs order books that are independent of production and not synchronized with it, and it is wiped roughly monthly without notice ([Binance testnet](https://developers.binance.com/docs/binance-spot-api-docs/testnet/general-info)). **CME's Certification and New Release environments** are protocol-certification endpoints, and New Release carries "significantly lower data rates than production" ([CME wiki](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457319776)). None of these can start at a historical time or run faster than wall clock. They validate plumbing (auth, request shapes, error codes, order lifecycle), and CCXT already covers that through `setSandboxMode`, which swaps `urls.api` for `urls.test`.

The closest real instance of a historical exchange server is **tardis-machine**. Its `/ws-replay` endpoint accepts each exchange's native subscribe messages, maps them through per-exchange `SubscriptionMapper`s for about 40 venue families, merges sessions by local timestamp, and streams recorded frames as fast as the socket drains, with no pacing parameter ([tardis-machine replay.ts](https://github.com/tardis-dev/tardis-machine/blob/master/src/ws/replay.ts), [subscriptionsmappers.ts](https://github.com/tardis-dev/tardis-machine/blob/master/src/ws/subscriptionsmappers.ts)). Existing WS clients work "just by changing URL" ([tardis-machine README](https://github.com/tardis-dev/tardis-machine)). But it is **market data only**. It has no order entry, no account state, and it drops disconnect markers in native mode. Commercial vendors such as Esprow go further, with configurable price-time or pro-rata matching, trading phases, preloaded book states, latency injection and FIX log replay "at any speed" ([Esprow ETP GEMS](https://www.esprow.com/products/exchange-simulation/etp-gems.php), [FIX Log Replay](https://www.esprow.com/products/fix-testing/fix-log-replay-manager.php)). They are per-venue certification tools, not strategy research engines.

Research and trading engines chose (B) almost unanimously. **NautilusTrader** runs backtest, sandbox and live on one `NautilusKernel`, and the sandbox reuses the same `OrderMatchingEngine` against live data ([architecture.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/architecture.md), [sandbox lib.rs](https://github.com/nautechsystems/nautilus_trader/blob/develop/crates/adapters/sandbox/src/lib.rs)). **LEAN** swaps `IDataFeed`, `ITransactionHandler` and `IRealtimeHandler` by config. Its "live-paper" environment is literally live data plus `PaperBrokerage` plus the backtesting transaction handler ([LEAN config.json](https://github.com/QuantConnect/Lean/blob/master/Launcher/config.json)). **OctoBot** runs "the exact same process as with the real trading mode", with a simulator twin for every live data feed ([OctoBot Simulator docs](https://github.com/Drakkar-Software/OctoBot-Docs/blob/stable/Usage/Simulator.md)). **Freqtrade** intercepts `create_dry_run_order` inside its ccxt-backed `Exchange` object while public calls still hit the venue ([freqtrade exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)). **Hummingbot** wraps the real connector's order-book tracker in a `<exchange>_paper_trade` connector ([paper_trade/__init__.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/connector/exchange/paper_trade/__init__.py)). Even hftbacktest, which does run a separate live connector process over shared memory, runs its backtest in-process ([connector README](https://github.com/nkaz001/hftbacktest/blob/master/connector/README.md)).

The same survey shows where parity breaks. It holds up best where one matching engine serves every mode (Nautilus, OctoBot, LEAN paper). It breaks down where the backtest has its own execution code. Freqtrade's separate backtest loop evaluates "stoploss before ROI", which produces more stoploss exits than dry-run and live ([backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)), and the issue tracker carries years of divergence reports, from "No trades in dryrun – hundreds in backtest" ([#1198](https://github.com/freqtrade/freqtrade/issues/1198)) to a backtest showing 1% drawdown and 70% win rate against dry-run's 10% and 35% ([#8451](https://github.com/freqtrade/freqtrade/issues/8451)). Hummingbot v2 backtests controllers with vectorized executor simulators that differ from the live executors ([backtesting_engine_base.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/backtesting_engine_base.py)). The lesson for CCXT is that **the unit of parity is the matching engine, not the strategy API**.

| Architecture | Real instances | Strength | Decisive weakness for CCXT |
|---|---|---|---|
| (A) exchange-native server | Alpaca/IBKR paper, testnets, tardis-machine (data only), Esprow | Unchanged client code, language-agnostic | Re-implements 100+ venues' REST/WS/sign/error schemes in reverse; wall-clock leaks in client; per-call round trips; no execution in the only historical example |
| (A′) unified-API server | none found | One protocol, shareable | Clients need a "sim" exchange class anyway, so the URL-swap benefit disappears |
| (B) in-process sim exchange | Nautilus, LEAN, OctoBot, Freqtrade, Hummingbot, Barter | Fast, deterministic, same unified structures | Fidelity limited by matching model; exchange-specific `params` and implicit API methods not simulated |
| (C) explicit time control | Nautilus `VirtualClock`, ABIDES kernel, VOPR, Jest/.NET/Go fake clocks | Reproducibility, fault injection, look-ahead safety | Needs clock and async-timer integration in every runtime |

## The clock decides everything, and CCXT's is currently the host's

Reproducible simulators converge on one pattern: **inject a clock, advance it only through an event queue, never read wall time, and implement "rewind" as reset plus deterministic re-run.** Nautilus's `VirtualClock.advance_time` returns due timer events in timestamp-then-name order and **panics if asked to go backwards** ([virtual.rs](https://github.com/nautechsystems/nautilus_trader/blob/develop/crates/common/src/clock/virtual.rs)). `BacktestEngine.reset()` clears orders, positions and timestamps but keeps loaded data for parameter sweeps ([apis-and-runs.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/apis-and-runs.md)). ABIDES's kernel is a priority message queue parameterized by start and end time, agents, a latency model and a PRNG seed. It models nanosecond time and per-agent computation delay ([ABIDES paper](https://arxiv.org/pdf/1904.12066)). TigerBeetle's VOPR reproduces failures exactly from seed plus commit and runs "one minute of VOPR time" as days of real time ([VOPR docs](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)). Antithesis implements time-travel by snapshotting and branching, not by reversing ([Antithesis blog](https://antithesis.com/blog/deterministic_hypervisor/)). .NET's `FakeTimeProvider` also moves only forward ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/extensions/timeprovider-testing)). Barter is the counter-example. Its `HistoricalClock` adds `Utc::now()` deltas to the last event time, and its mock latency uses real `tokio::sleep`, so results depend on machine load ([clock.rs](https://github.com/barter-rs/barter-rs/blob/develop/barter/src/engine/clock.rs)). That is the anti-pattern to avoid.

LEAN supplies the look-ahead half. Its single "Time Frontier" emits each datum at its `EndTime`, which for bars is open plus period. It groups everything at or before the frontier into one `Slice`, fills bars forward but never ticks, and warns that free providers stamping bars at open time make research "prone to look ahead bias" ([Time Frontier](https://github.com/QuantConnect/Documentation/blob/master/03%20Writing%20Algorithms/01%20Key%20Concepts/05%20Time%20Modeling/02%20Timeslices/02%20Time%20Frontier.html), [Start and End Time](https://github.com/QuantConnect/Documentation/blob/master/03%20Writing%20Algorithms/01%20Key%20Concepts/05%20Time%20Modeling/01%20Periods/03%20Start%20and%20End%20Time.html)). This matters directly for CCXT, whose OHLCV rows are open-stamped. A simulated `fetchOHLCV` must not return the current bar until the frontier passes its close, unless the user explicitly asks for a forming candle. Nautilus applies the same rule, requiring `ts_init` at the interval close for bars used in execution ([bar-execution.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/bar-execution.md)). Freqtrade shows the cost of not building this in. Its vectorized indicators need a `shift(1)` convention plus after-the-fact `lookahead-analysis` and `recursive-analysis` detectors, and a 2026 issue reports divergence that the detector missed ([lookahead-analysis.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/lookahead-analysis.md), [#12894](https://github.com/freqtrade/freqtrade/issues/12894)).

The codebase check turned up an important detail. The instance property `milliseconds` on `Exchange` ([Exchange.ts:470](../ts/src/base/Exchange.ts)) is used for nonces, `lastRestRequestTimestamp` and caches, and **84 exchange files call `this.milliseconds ()`**, so an overridable instance clock reaches most per-exchange logic. But the throttler imports `now` and `sleep` straight from `time.ts` ([throttle.ts](../ts/src/base/functions/throttle.ts)), and the WS `Client` calls the module-level `milliseconds ()` for connection and keep-alive timestamps ([Client.ts](../ts/src/base/ws/Client.ts)). Swapping the instance property alone would leave rate limiting and WS liveness on wall time, so they would either stall or race in a simulation. This also undercuts architecture (A). A historical server cannot be used coherently unless the client's clock is injected anyway, because CCXT would otherwise sign requests, compute `since` defaults and pace the throttler at 2026 wall time against 2022 data. **Clock injection is therefore a prerequisite for every option**, and once it exists, (B)+(C) is the cheaper path.

Per-language fake-timer libraries are not a substitute. Go's `testing/synctest` auto-advances only when every goroutine is "durably blocked", and mutex waits don't count ([pkg.go.dev](https://pkg.go.dev/testing/synctest), [Inside synctest](https://internals-for-interns.com/posts/inside-go-synctest)). Jest and .NET advance only on explicit calls ([Jest](https://jestjs.io/docs/timer-mocks)). Relying on them would give seven languages seven semantics. The clock has to be a CCXT object that the simulator owns.

## Modelling the time between calls: every await is an event on the virtual timeline

The question of timing between calls has a concrete answer drawn from hftbacktest and Nautilus: **treat each unified call as a message with its own latency legs, let the strategy's awaits pull the clock forward, and never let an action see state from after its arrival time.** hftbacktest separates three legs: feed latency (from dual `exch_ts`/`local_ts` stamps), order-entry latency and order-response latency. Its `IntpOrderLatency` interpolates recorded `req_ts, exch_ts, resp_ts` rows collected by "submitting unexecutable orders regularly" ([latency_models.rst](https://github.com/nkaz001/hftbacktest/blob/master/docs/latency_models.rst)). The strategy advances time explicitly with `elapse`, `wait_next_feed` and `wait_order_response`, and `elapse_bt` charges compute time only in backtest because "`elapse()` exclusively manages time during backtesting, meaning that factors such as computing time are not properly accounted for" ([types.rs](https://github.com/nkaz001/hftbacktest/blob/master/hftbacktest/src/types.rs)). The author names latency and queue modelling as the two main sources of backtest-versus-live discrepancy ([debugging discrepancies](https://github.com/nkaz001/hftbacktest/blob/master/docs/debugging_backtesting_and_live_discrepancies.rst)). Nautilus adds two subtle rules. A per-timestamp contract runs in three phases: the exchange consumes the data and matches resting orders, then strategies react, then venues settle until quiescent, so "resting orders see the incoming market before newly submitted orders do". And an inflight command is released only by data **for the same instrument**, a timer or a funding point, so an order never executes against another instrument's stale book ([execution-flow.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/execution-flow.md)).

Mapped onto CCXT's async API, this gives a clean timing model. When a strategy calls `await sim.createOrder(...)` at virtual time *t*, the order arrives at the matcher at *t + entry latency*. It is matched against book state as of that instant, after that instrument's data at that timestamp has been applied. The promise resolves at *t + entry + response*, and the clock advances to that time. `fetch*` calls resolve after a configurable REST round trip and return data that satisfies both `exchangeTs ≤ now − feedLatency` and the time frontier. `watch*` calls resolve on the next queued event whose local timestamp is due, which is the natural "strategy pulls time" loop. Rate limits run on the virtual clock through the existing throttler, so a burst of calls either delays in simulated time or raises `RateLimitExceeded`, exactly as live. Strategy compute time is a policy choice. The deterministic default charges zero, like `elapse`. An opt-in mode measures wall time per callback and charges it, like `elapse_bt`, trading reproducibility for realism. Random elements, such as probabilistic fills or latency jitter, draw from per-model seeded RNGs, as in Nautilus's `random_seed` and ABIDES, and IDs are derived from (venue, sequence, timestamp) like Nautilus's FNV-based trade IDs ([dst.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/dst.md)). Scheduled and injected events share the same queue: candle closes, funding settlements, liquidation checks, maintenance windows, WS disconnects, `ExchangeNotAvailable`. That queue is where option (C) lives: `advance(ms)`, `advanceTo(ts)`, `runUntil(predicate)`, `schedule(ts, event)`, plus `snapshot()`/`restore()` for seek and walk-forward.

## Fill fidelity follows data granularity, and nobody models market impact

Across the frameworks, **fill realism is bounded by the data tier**, and each tier has a well-documented best practice. At the bar tier, everyone fills limit orders fully once the bar touches the price. Freqtrade uses `low ≤ rate ≤ high` with "low before high for stoploss" ([backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)). Jesse splits the 1m candle along O→L→H→C or O→H→L→C by candle color and fills gap-throughs at the open, so "a stop-loss at 98 … Monday's open at 94 fills at 94" ([Jesse traditional-markets backtesting](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md)). Nautilus converts bars to four synthetic ticks, with an optional adaptive high/low ordering it calls "a deterministic heuristic, not a reconstruction" ([bar-execution.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/bar-execution.md)). MultiCharts and TradeStation use the same OHLC path heuristic, then drill into finer data with Bar Magnifier or Look-Inside-Bar. Users report "radically different" results depending on these settings ([MultiCharts assumptions](https://www.multicharts.com/trading-software/index.php?title=Intra-bar_Price_Movement_Assumptions), [Markplex](https://markplex.com/free-tutorials/tutorial-147-look-inside-bar-back-testing-and-intra-bar-order-generation-and-calculation/)). Backtrader names the same-bar-close shortcut "cheating" and makes it an explicit opt-in ([bbroker.py](https://github.com/mementum/backtrader/blob/master/backtrader/brokers/bbroker.py)). Slippage models are primitive: Zipline and LEAN share `VolumeShareSlippage` (2.5% volume cap, 0.1 impact, quadratic) ([zipline slippage.py](https://github.com/stefan-jansen/zipline-reloaded/blob/main/src/zipline/finance/slippage.py)). Defaults are optimistic. **LEAN defaults crypto to zero fees and zero slippage and assumes complete fills** ([Fees default](https://github.com/QuantConnect/Documentation/blob/master/03%20Writing%20Algorithms/24%20Reality%20Modeling/04%20Transaction%20Fees/01%20Key%20Concepts/03%20Default%20Behavior.html), [Partial Fills](https://github.com/QuantConnect/Documentation/blob/master/03%20Writing%20Algorithms/24%20Reality%20Modeling/02%20Trade%20Fills/01%20Key%20Concepts/05%20Partial%20Fills.html)).

At the trade and L2 tier, two engines set the bar. Nautilus never decrements the recorded book, offers an optional `liquidity_consumption` ledger, fills passive orders from trade prints capped at `min(leaves_qty, trade.size)`, and tracks queue position by snapshotting size ahead at acceptance and draining it with same-price trades ([fill-prices-and-matching.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/fill-prices-and-matching.md), [trade-execution.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/trade-execution.md)). hftbacktest provides the queue maths: a risk-averse model that advances only on trades, and probabilistic models with power or log functions following Rigtorp, where on a level decrease `est_front = front − (1−p)·chg + min(back − p·chg, 0)` ([queue.rs](https://github.com/nkaz001/hftbacktest/blob/master/hftbacktest/src/backtest/models/queue.rs)). Both authors state the ceiling plainly: "your order cannot make any changes to the simulated market, no market impact is considered" ([order_fill.rst](https://github.com/nkaz001/hftbacktest/blob/master/docs/order_fill.rst)). Hummingbot's team goes further for market making, calling backtests a "parameter research tool rather than a prediction engine" because one different fill makes everything after it diverge ([Bot Pod ep. 4](https://hummingbot.substack.com/p/the-bot-pod-episode-4-backtesting)). A CCXT simulator should therefore make every assumption a named configuration (book type, bar path, queue model, consumption, latency legs, fee model) and record the active set in each run's result. Honest labelling is a feature here, not a disclaimer.

Perpetuals separate the leaders from the rest. Freqtrade applies historical funding from downloaded funding and mark candles and computes liquidation prices, but not liquidation fees ([leverage.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/leverage.md)). Jesse sets funding to **0** in backtests ([Jesse API docs](https://github.com/jesse-ai/docs/blob/master/docs/docs/strategies/api.md)). OctoBot uses a single configured constant ([exchange_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchanges/implementations/exchange_simulator.py)). Nautilus settles funding from `FundingRateUpdate` data at `next_funding_ns` and offers opt-in maintenance-margin liquidation, but it does not model tiered maintenance margin ([accounts-and-margin.md](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/accounts-and-margin.md)). CCXT already exposes `fetchFundingRateHistory`, mark-price OHLCV and `fetchLeverageTiers`, so it can supply tiered liquidation that none of the surveyed engines has.

## Data is the moat, but hosting raw exchange data is legally off-limits

Backfilling practice is mature at the OHLCV tier and thin everywhere else. Freqtrade is the best CCXT-based reference. It fans out `fetch_ohlcv` pages concurrently in batches of 100, sorts because pages return "in async order", appends and `--prepend`s incrementally, includes delisted pairs on request, downloads mark and funding candles for futures, and stores Feather by default. Its benchmark on BTC/USDT 1m was feather at 115 MB in 1.6 s against json at 265 MB in 17.1 s ([data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md), [exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)). Jesse imports only 1m candles and derives higher timeframes, which gives one canonical series ([Jesse docs](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md)). None of the four crypto bot frameworks stores historical order books for backtesting, and **none records point-in-time market metadata**. Freqtrade admits it has "no information about historic limits" and infers tick size from observed prices ([backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)). LEAN's flat-file layout `securityType/marketName/resolution/ticker/date_tradeType.zip` already uses `marketName` to separate BTCUSDT across brokerages, and it pairs price files with map files for renames and delistings ([LEAN folder structure](https://github.com/QuantConnect/Documentation/blob/master/06%20LEAN%20Engine/03%20Data%20Format/01%20Key%20Concepts/02%20Folder%20Structure.html), [MapFile.cs](https://github.com/QuantConnect/Lean/blob/master/Common/Data/Auxiliary/MapFile.cs)). That maps almost one-to-one onto CCXT's `type/exchangeId/timeframe/marketId`.

Professional capture adds a second timestamp and treats replay as re-invoking the live handler. Databento records carry `ts_event`, `ts_recv`, `ts_in_delta`, a venue `sequence`, and flags such as `MAYBE_BAD_BOOK` rather than deleting bad data ([dbn record.rs](https://github.com/databento/dbn/blob/main/rust/dbn/src/record.rs), [flags.rs](https://github.com/databento/dbn/blob/main/rust/dbn/src/flags.rs)). One DBN format serves historical and live, and live subscriptions can start up to about 24 h in the past ([databento-python live client](https://github.com/databento/databento-python/blob/main/databento/live/client.py)). Tardis stores raw frames with 100 ns arrival stamps and needs date-versioned parsers because venues change schemas, for example a hard-coded Bybit V5 switch date ([tardis-node ARCHITECTURE.md](https://github.com/tardis-dev/tardis-node/blob/master/ARCHITECTURE.md), [subscriptionsmappers.ts](https://github.com/tardis-dev/tardis-machine/blob/master/src/ws/subscriptionsmappers.ts)). kdb+/tick logs every message as an `upd` call and replays with `-11!`, so a simulator only redefines `upd` ([tick.q](https://github.com/KxSystems/kdb-tick/blob/master/tick.q), [r.q](https://github.com/KxSystems/kdb-tick/blob/master/tick/r.q)). CCXT already has the kdb-style hook. Its static WS tests replay canned frames into each exchange's `handleMessage` through a mocked transport, with 26 exchange fixtures under [ts/src/test/static/ws/](../ts/src/test/static/ws/). Recording raw `watch*` frames with a local receive time and replaying them through that path exercises CCXT's own checksum, sequence-gap and resync logic, delivering tardis-machine's exchange-native fidelity in-process with no server.

Two constraints shape the data strategy. The first is volume. Full L2 for a top perp runs about **1–2 GB per symbol-day compressed** ([cryptostruct guide](https://cryptostruct.com/guides/order-book-dataset-for-machine-learning)), and Tardis and CoinAPI describe archives of hundreds of terabytes ([tardis.dev](https://tardis.dev/), [CoinAPI](https://www.coinapi.io/products/flat-files)). The second is licensing. Binance forbids commercial "data feeding or streaming services" built on its market data without consent, and Coinbase forbids redistributing market data or derived works to third parties ([Binance terms](https://www.binance.com/en/terms), [Coinbase Market Data Terms](https://www.coinbase.com/legal/market_data)). A CCXT-hosted public archive is therefore not viable without per-exchange agreements. The workable model is tardis-machine's: open software, with users bringing their own data. That means their own ccxt.pro recordings, exchange-published dumps such as Binance's checksummed daily files (trades, aggTrades, klines, funding, mark and index klines, but **no full-depth deltas**, and files are retroactively replaced ([binance-public-data](https://github.com/binance/binance-public-data))), and adapters for licensed vendors (Tardis, Databento, Crypto Lake, CoinAPI) that already use the "daily partition, snapshot then deltas" layout.

## Phased recommendations for CCXT

The architecture is **(B)+(C) at the core, and (A) as an optional façade**. The work splits along the precedent CCXT already has. Pure logic (matcher, fill, fee, margin and funding models, event queue, simulated `Exchange` subclass) belongs in `ts/src/` and transpiles to all languages, which keeps one matching engine per mode across seven runtimes. Anything that touches the async runtime (the virtual `sleep`, driving `Future` resolution for `watch*`, the throttler's timers) needs a small hand-written layer per language. [OrderRouter.ts](../ts/src/base/OrderRouter.ts) is the precedent: hand-written and mirrored method for method in six languages under explicit determinism rules (no hash-map iteration for ordered output, fixed arithmetic order). The simulator should adopt the same rules verbatim, because a golden-output test that differs between Python and Go is a parity bug, not noise.

| Phase | Deliverable | Design anchors | Exit criterion |
|---|---|---|---|
| 0. Clock seam | A `clock` object on `Exchange` (`milliseconds`, `sleep`, `setTimer`) defaulting to wall time; route `throttle.ts` and `ws/Client.ts` through it instead of module-level `now()`/`milliseconds()` | Nautilus `LiveClock`/`VirtualClock` split; .NET `TimeProvider` | Base tests in all languages pass with a frozen clock; zero behaviour change live |
| 1. Data layer | `ccxt.data` backfiller (OHLCV, trades, funding, mark/index, OI) built on `paginate`, with gap reports; LEAN-style partitioned Parquet/CSV store; **point-in-time `markets` snapshots**; a `watch*` recorder writing raw frames plus local receive time plus connect/disconnect markers; importers for Binance dumps and vendor files | Freqtrade backfill, LEAN layout, Databento dual timestamps, Tardis raw frames | Reproducible dataset hash; recorder output replays through the static-WS harness |
| 2. Bar/trade simulator | `SimulatedExchange` implementing `createOrder`, `cancelOrder`, `fetchOrder(s)`, `fetchBalance`, `fetchPositions`, `fetchMyTrades` and `fetch*`/`watch*` market data over the virtual clock; time frontier with bars emitted at close; explicit bar-path modes (pessimistic, OHLC heuristic, magnifier via 1m or trades); gap-at-open fills; fees from `market.maker/taker`; historical funding; tiered liquidation via leverage tiers; order validation from `precision`, `limits` and `features`; seeded RNG and deterministic IDs; `advance`/`schedule`/`snapshot`/`restore` | Jesse, Freqtrade, Nautilus bar execution, LEAN frontier, Backtrader "cheat" opt-ins | Identical results across all languages on golden runs; published "what is and isn't simulated" list in Alpaca's style |

Premium layer | Parameter sweeps via reset/restore, rolling and anchored walk-forward, purged CV, PSR and deflated Sharpe, neutral result export (equity, orders, fills, assumptions); optional lockstep server exposing the CCXT unified API with explicit `advance` (Gym-style) for cross-process, notebook and hosted use | LEAN optimizer, VectorBT PRO CV, ABIDES-Gym | Hosted service reuses the identical core |

Three guardrails apply across all phases. First, **never mutate recorded data, and never read wall time in backtest mode**. Second, **one matcher for backtest and paper**, so any divergence comes only from the data. Third, keep venue behaviour data-driven from CCXT metadata rather than hand-written per-venue model classes. LEAN still ships fee models for FTX and GDAX ([LEAN Fees](https://github.com/QuantConnect/Lean/tree/master/Common/Orders/Fees)), which is the staleness CCXT's `describe()` avoids. One open question remains. No surveyed source benchmarks in-process against HTTP-based backtest throughput, and exchange-specific `params` and implicit endpoints will stay out of simulation scope. The docs should state both plainly.

## Conclusion

The research reframes the A/B/C question. These are not rival architectures but layers, and the order in which to build them is forced. A server cannot be coherent without client clock injection. Clock injection without an event queue is just a frozen timestamp. And an event queue is only trustworthy with a single in-process matcher behind it. So CCXT gets (C) first as a seam, then (B), and gets (A) almost for free as a lockstep wrapper once the core is deterministic. The exchange-native flavour of (A) comes cheapest of all, by replaying recorded frames into the `handleMessage` code CCXT already maintains for 100+ venues, rather than by re-implementing those venues server-side.

CCXT's competitive opening is also clearer than the "no backtester" line in its own Freqtrade comparison suggests ([ccxt-vs-freqtrade.md](../wiki/comparisons/ccxt-vs-freqtrade.md)). The gaps every incumbent admits to are gaps CCXT's existing metadata closes directly: point-in-time markets and limits, historical funding with tiered liquidation, exchange-accurate order validation, and one engine identical across seven languages. The premium value is not a cleverer fill model, since nobody can simulate market impact from replay. It is **honest, reproducible, cross-venue simulation whose assumptions are explicit and whose code path is the one users run live**.
