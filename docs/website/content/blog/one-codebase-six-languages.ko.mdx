CCXT는 100개 이상의 암호화폐 거래소를 위한 통합 트레이딩 API를 JavaScript/TypeScript,
Python, PHP, C#, Go, Java로 제공합니다. 거래소 API는 매주 바뀝니다 — 엔드포인트가 옮겨지고, 서명 방식이
바뀌고, 새로운 마켓이 생겨납니다. 여섯 개의 독립적인 포트를 손으로 동기화하는 것은 불가능하며,
버려진 "거래소 API 래퍼" 라이브러리들의 무덤이 지난 수년간 그 사실을 증명해 왔습니다.

우리의 답은 독특합니다. **구현은 정확히 하나만 존재합니다**. 모든 거래소 클래스는
`ts/src/` 아래에 TypeScript로 단 한 번만 작성됩니다. 나머지 전부 — PyPI의 Python 패키지, Packagist의 PHP
패키지, NuGet의 C# 패키지, Go 모듈, Maven Central의 Java 아티팩트 — 는
이 단일 소스에서 기계적으로 생성됩니다.

## 파이프라인

`ts/src/binance.ts`에 가한 변경은 다음과 같이 흘러갑니다.

- **JavaScript** — 평범한 `tsc`입니다. npm 패키지는 컴파일된 TypeScript입니다.
- **C#, Go, Java** — 우리가 오픈소스로 공개한 AST 기반 트랜스파일러
  [`ast-transpiler`](https://github.com/ccxt/ast-transpiler)가 TypeScript 구문 트리를 각 대상
  언어로 변환합니다. 현재 CCXT의 대부분의 언어가 이 경로를 거칩니다.
- **Python과 PHP** — 원조 정규식 기반 트랜스파일러(`build/transpile.ts`)가
  수백 개의 치환 규칙으로 소스를 한 줄씩 다시 씁니다.

두 가지 생성 기법은 따로 짚어 볼 만합니다. Python의 **동기(sync)** API는 비동기
API에서 생성됩니다 — `await` 표현식을 제거하고 aiohttp 전송 계층을
`requests` 스타일 호출로 바꾸는 방식이라, 동기와 비동기 Python API가 서로 어긋나는 일이 결코 없습니다. PHP는
반대 방향으로 동작합니다. **비동기(async)**(ReactPHP) 버전이 동기 버전에서 생성됩니다.

## AST 트랜스파일러

[`ast-transpiler`](https://github.com/ccxt/ast-transpiler)는 TypeScript 컴파일러 API를 사용해
각 파일을 추상 구문 트리로 파싱한 뒤, 트리를 순회하며 대상 언어로 된 동등한 코드를
출력합니다. 타입은 매핑되고(`string` → `string`/`str`/`String`), `async/await`는
C#의 `Task`, Java의 future, 또는 `(value, error)`를 반환하는 평범한 Go 호출이 되며,
JavaScript 관용구는 각 언어의 표준 라이브러리에 맞게 다시 작성됩니다.

텍스트가 아닌 AST 위에서 작업하기 때문에 C#, Go, Java 출력은 정규식 치환보다 훨씬
견고합니다. 트랜스파일러는 어떤 것이 메서드 호출인지 프로퍼티 접근인지를 *이해하므로*,
서식, 줄바꿈, 중첩이 있어도 깨지지 않습니다. 그래도 각 언어에는
CCXT 저장소 안에 얇은 드라이버(`build/csharpTranspiler.ts`, `build/goTranspiler.ts`,
`build/javaTranspiler.ts`)가 있어 언어별 접착 코드를 처리합니다. 타입이 지정된 시그니처를 가진
래퍼 클래스, 패키지 레이아웃, 언어별 표준 라이브러리 심(shim)이 여기에 해당합니다.

정규식 트랜스파일러는 그보다 먼저 만들어졌고 여전히 Python과 PHP를 생성합니다. 이 트랜스파일러는 깨지기 쉽기로 유명합니다 —
TypeScript 소스의 정확한 서식에 의존하기 때문입니다 — 하지만 수년에 걸쳐 수백만
줄을 처리해 왔고, 이것이 강제하는 제약은 버그가 아니라 오히려 기능이었음이 드러났습니다.

## 우리는 TypeScript를 쓰지 않습니다 — CCXT 방언의 TypeScript를 씁니다

하나의 코드베이스가 다섯 번의 변환을 견디려면, 모든 백엔드가 처리할 수 있는 방언 안에
머물러야 합니다. 기여자들은 첫 번째 풀 리퀘스트에서 다음 규칙들과 마주칩니다.

- **데이터에 대한 점(dot) 프로퍼티 접근 금지.** 항상 `order['price']`이며, 절대 `order.price`가 아닙니다 —
  트랜스파일러는 대괄호 접근을 딕셔너리, 배열, 맵으로 변환합니다.
- **가격이나 수량에 대한 네이티브 산술 금지.** 모든 숫자 연산은 문자열 기반
  `Precise` 클래스를 거칩니다 — `Precise.stringAdd (a, b)` — 부동소수점 동작이 언어마다
  다르기 때문입니다(그리고 부동소수점은 돈을 잃게 만듭니다. 자세한 내용은
  [일곱 가지 실수](/ko/blog/seven-mistakes-crypto-exchange-api-developers-make)를 참고하십시오).
- **어디서나 타입이 지정된 safe 접근자 사용.** `||` 폴백을 쓰는 원시 접근 대신 `this.safeString (obj, 'key')`,
  `this.safeInteger (...)`, `this.safeDict (...)`을 사용합니다.
  원시 접근은 Python이나 PHP에서 다르게 동작할 수 있기 때문입니다.
- **문법의 부분집합만 사용.** `Array.includes` 금지(`indexOf (x) !== -1`로 바뀝니다), 거래소 클래스 안에서 화살표
  콜백 금지, 삼항 연산자는 항상 괄호로 감싸기, 한 줄에 하나의 문장.

ESLint 설정이 이 대부분을 기계적으로 강제합니다. 결과물은 TypeScript 순수주의자에게는
조금 낯설게 읽히지만, 여섯 개 언어로 컴파일됩니다.

## 트랜스파일되지 *않는* 것

전송 계층과 암호화는 생성할 수 없습니다 — 바로 그 지점에서 언어들이 진정으로 다르기 때문입니다.
각 언어에는 손으로 작성한 기반 계층이 있습니다. HTTP 클라이언트(fetch, aiohttp, curl,
HttpClient, net/http, OkHttp 스타일), WebSocket 전송 계층, 그리고 암호화 프리미티브
(HMAC, RSA, ECDSA, EdDSA 서명)입니다. 그 계층 *위에* 놓이는 통합 기반 클래스 로직 —
심볼 해석, 주문 파싱, 정밀도 처리, rate limiting — 은
`ts/src/base/Exchange.ts`에서 모든 언어로 트랜스파일되어, 각 파일의 표시 줄 아래에 위치합니다.

## 여섯 개 언어를 한 번에 테스트하기

테스트하지 않는 생성 코드는 신뢰할 수 없는 생성 코드입니다. 모든 거래소 메서드는
**정적 픽스처**로 커버됩니다. 저장소에 체크인된, 기록된 요청 URL과 응답 페이로드를
CI가 실행될 때마다 여섯 개 구현 모두에 대해 오프라인으로 재생합니다. Python 빌드가
Binance 주문을 Go 빌드와 다르게 파싱하면, 릴리스 전에 CI가 실패합니다. 그 위에
언어별 라이브 스모크 테스트가 실제 공개 엔드포인트를 호출하고, 전체 매트릭스 — 트랜스파일,
컴파일, 테스트 — 가 머지마다 모든 언어에 대해 병렬 CI 파이프라인에서 실행됩니다.

## 그만한 가치가 있었을까요?

트레이드오프는 실재합니다. 기여자는 방언을 배워야 하고, 디버깅은 때때로
TypeScript에서 고칠 버그를 찾기 위해 생성된 Python을 읽는 일을 의미하며, 트랜스파일러 자체도
유지보수해야 할 코드베이스입니다. 하지만 그 대가로 하나의 수정이 하나의 리뷰, 하나의 diff로 **여섯 개 패키지 레지스트리에
동시에** 반영됩니다. 뒤처지는 포트는 없고, 새 거래소의
"이류" 버전을 받는 언어도 없습니다.

이 아이디어가 마음에 드신다면, [`ast-transpiler`](https://github.com/ccxt/ast-transpiler)는 MIT
라이선스이며 CCXT 밖에서도 사용할 수 있습니다 — 그리고 이 방언이 실제로 어떻게 쓰이는지 보고 싶다면,
[`ts/src/`](https://github.com/ccxt/ccxt/tree/master/ts/src)에 있는 아무 거래소 파일이나 열어 보십시오. 그것이 바로
실물입니다.
