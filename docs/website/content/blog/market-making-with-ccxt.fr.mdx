Chaque transaction a besoin d'une contrepartie, et la plupart du temps cette contrepartie est un market maker :
quelqu'un qui cote en continu à la fois un prix d'achat et un prix de vente, en gagnant l'écart entre les deux.
Les exchanges veulent tellement cette liquidité qu'ils facturent aux makers des frais plus bas qu'aux takers — souvent zéro,
parfois négatifs (un rebate). Cet article explique les mécanismes et construit une boucle de cotation
minimale avec CCXT — un **squelette pédagogique**, pas un système de production, et le market making avec
de la taille réelle est un métier véritablement difficile et compétitif.

## Le modèle économique

Un market maker place un achat limite sous le prix courant et une vente limite au-dessus. Quand
les deux sont exécutés — quelqu'un vend dans votre bid, quelqu'un d'autre achète à votre ask — vous avez acheté bas
et vendu haut, capturé le spread, et vous voilà de retour à plat. Répétez des milliers de fois.

Trois nombres gouvernent le P&L :

- **Le spread capturé** par aller-retour (votre spread coté, moins le mouvement de prix adverse).
- **Les frais maker** — négociez le palier ; les makers vivent et meurent par les grilles de frais. Consultez
  `exchange.markets[symbol]['maker']`.
- **Les pertes d'inventaire** — la raison pour laquelle ce n'est pas de l'argent gratuit, et le sujet de la plupart de la
  littérature.

## L'inventaire : le véritable ennemi

Si le prix baisse en tendance, vos bids continuent d'être exécutés et vos asks non — vous accumulez l'actif
tout au long de la descente. C'est la **sélection adverse** : les gens qui tradent avec vous savent quelque chose
(ou sont simplement le front d'un mouvement), et vous êtes systématiquement du mauvais côté.

Tout modèle sérieux de market making est au fond une politique de contrôle de l'inventaire. La référence
classique est Avellaneda–Stoikov (2008) : coter autour d'un **prix de réservation** qui s'éloigne
de votre inventaire — un inventaire long pousse les deux cotations vers le bas (pressé de vendre, réticent à
acheter), un inventaire short les pousse vers le haut. Notre squelette ci-dessous utilise la version la plus simple de cette
idée : un biais linéaire.

## Une boucle de cotation minimale

```javascript tab="JavaScript"
import ccxt from 'ccxt';

const SYMBOL = 'BTC/USDT';
const SPREAD = 0.002;            // spread coté de 20 bps, frais inclus
const ORDER_SIZE = 0.001;
const MAX_INVENTORY = 0.005;     // borne stricte de position, en devise de base
const REFRESH = 5000;            // ms entre deux re-cotations

const exchange = new ccxt.pro.binance({ apiKey: '...', secret: '...' });
exchange.setSandboxMode(true);   // apprenez sur le testnet
await exchange.loadMarkets();
let inventory = 0;               // à suivre via watchMyTrades dans du vrai code
try {
    while (true) {
        const book = await exchange.watchOrderBook(SYMBOL);
        const mid = (book.bids[0][0] + book.asks[0][0]) / 2;
        // incliner les cotations contre l'inventaire (Avellaneda-Stoikov du pauvre)
        const skew = -(inventory / MAX_INVENTORY) * (SPREAD / 2);
        const bid = exchange.priceToPrecision(SYMBOL, mid * (1 - SPREAD / 2 + skew));
        const ask = exchange.priceToPrecision(SYMBOL, mid * (1 + SPREAD / 2 + skew));
        await exchange.cancelAllOrders(SYMBOL);
        if (inventory < MAX_INVENTORY) {
            await exchange.createOrder(SYMBOL, 'limit', 'buy', ORDER_SIZE, bid, { postOnly: true });
        }
        if (inventory > -MAX_INVENTORY) {
            await exchange.createOrder(SYMBOL, 'limit', 'sell', ORDER_SIZE, ask, { postOnly: true });
        }
        await exchange.sleep(REFRESH);
    }
} finally {
    await exchange.cancelAllOrders(SYMBOL);   // ne jamais quitter avec des cotations en attente
    await exchange.close();
}
```

func toFloat(v any) float64 {
    f, _ := strconv.ParseFloat(v.(string), 64)
    return f
}

func main() {
    exchange := ccxtpro.NewBinance(nil)
    exchange.ApiKey = "..."
    exchange.Secret = "..."
    exchange.SetSandboxMode(true) // apprenez sur le testnet
    exchange.LoadMarkets()

    defer func() {
        exchange.CancelAllOrders(ccxt.WithCancelAllOrdersSymbol(symbol)) // ne jamais quitter avec des cotations en attente
        exchange.Close()

    for {
        book, err := exchange.WatchOrderBook(symbol)
        if err != nil {
            panic(err)

                ccxt.WithCreateOrderPrice(bid), ccxt.WithCreateOrderParams(params))
        }
        if inventory > -maxInventory {
            exchange.CreateOrder(symbol, "limit", "sell", orderSize,
                ccxt.WithCreateOrderPrice(ask), ccxt.WithCreateOrderParams(params))
        }

    }

public class MarketMaker {

    static final long REFRESH = 5000;             // ms entre deux re-cotations

                        mid * (1 - SPREAD / 2 + skew)));

                var params = Map.<String, Object>of("postOnly", true);
                if (inventory < MAX_INVENTORY) {
                    exchange.createOrder(SYMBOL, "limit", "buy", ORDER_SIZE, bid, params);
                }

                    exchange.createOrder(SYMBOL, "limit", "sell", ORDER_SIZE, ask, params);
                }
                Thread.sleep(REFRESH);
            }

            exchange.close().join();
        }

Ce que font les briques CCXT :

- **`watchOrderBook`** diffuse le carnet en streaming via WebSockets (voir
  [l'article sur les WebSockets](/fr/blog/realtime-market-data-with-websockets)) — coter à partir de données REST
  interrogées par polling, c'est coter sur des prix périmés.
- **`postOnly: true`** garantit que votre ordre reste en attente en tant que maker. S'il devait traverser le spread
  et s'exécuter en taker (en payant des frais taker et en prenant le mauvais côté), l'exchange le rejette
  à la place. Non négociable pour une stratégie maker.
- **`cancelAllOrders` + replacer** est la re-cotation simple. Là où l'exchange le prend en charge
  (vérifiez `exchange.has['editOrder']`), `editOrder` modifie le prix sur place — moins d'allers-retours,
  et vous conservez souvent votre position dans la file sur les exchanges qui la préservent pour les modifications
  à la baisse de taille.
- **`priceToPrecision`** parce que les cotations à des ticks invalides sont rejetées — voir
  [l'erreur n°1](/fr/blog/seven-mistakes-crypto-exchange-api-developers-make).

Ce qui manque délibérément : un vrai suivi de l'inventaire (abonnez-vous à `watchMyTrades` et
mettez à jour `inventory` à chaque exécution), un dimensionnement du spread tenant compte de la volatilité, des signaux
de déséquilibre de l'order book, et une cotation multi-niveaux. C'est votre feuille de route, dans cet ordre.

## Des contrôles de risque qui ne sont pas optionnels

- **Des bornes d'inventaire strictes** — le squelette arrête de coter un côté à la borne. Les vrais systèmes
  se ramènent aussi activement vers le plat.
- **Un kill switch que vous avez testé** — une commande qui annule tout et aplatit la position.
  `cancelAllOrders` existe dans l'API unifiée exactement pour cela. Certains exchanges prennent aussi en charge
  une sémantique de dead-man's-switch (annulation automatique à la déconnexion) via des paramètres spécifiques à l'exchange —
  cela vaut la peine de la brancher là où elle est disponible.
- **Des planchers de spread pendant la volatilité.** Quand le carnet s'amincit ou que les transactions commencent à
  traverser les niveaux, élargissez ou retirez vos cotations. Les makers qui survivent aux événements d'actualité sont ceux qui
  ne cotaient pas pendant.
- **Un spread tenant compte des frais.** Votre spread coté doit dépasser les frais aller-retour plus la sélection adverse
  attendue. Si vos frais maker sont de 0,02 % par côté, un spread de 0,1 % rapporte net 0,06 % *avant* sélection
  adverse — qui en réclamera l'essentiel.

## Et ensuite

Faites tourner le squelette sur un testnet sur une paire liquide et observez ce qui arrive à `inventory`
pendant une tendance — cette leçon vaut plus que n'importe quel réglage de paramètres. Lisez ensuite
Avellaneda–Stoikov et la littérature sur la position dans la file, et regardez comment les bots de market making
open source structurent la même boucle. La plomberie — carnets, cotations, annulations, exécutions —
est la même API unifiée en six langages du début à la fin, ce qui signifie que votre premier market maker peut être
construit dans le langage que votre équipe parle déjà.
