CCXT는 단일 TypeScript 소스에서 여섯 개 언어로 트랜스파일된 *동일한* 트레이딩 API를 제공합니다.
자연스러운 질문: **어떤 언어를 고르느냐가 성능을 바꿀까요?** PHP 봇은 Go 봇보다 느릴까요?
Python은 메모리를 더 쓸까요? 컴파일 언어가 항상 가장 빠를까요?

답은 세 개의 계층으로 나뉘고, 그 셋은 서로 일치하지 않습니다. 그래서 세 계층 모두를, 여섯 개
언어 — JavaScript(Node), Python, PHP, C#, Go, Java — 전부에 대해 측정했고, 진행 중인 Rust
포트도 처음으로 살펴봤습니다.

1. **REST 지연 시간** — `fetchOrderBook` 호출이 어떤 언어에서 다른 언어보다 느린가?
2. **네트워크를 제거한 라이브러리 자체의 속도** — 각 언어는 실제로 order book을 얼마나 빨리
   *파싱*하는가?
3. **메모리** — 각 런타임은 얼마나 무거운가?

코드는 저장소
([`examples/benchmarks/`](https://github.com/ccxt/ccxt/tree/master/examples/benchmarks))에 있으며
모든 숫자를 직접 재현하실 수 있습니다.

## 1. REST 지연 시간: 라이브러리가 아니라 네트워크입니다

짧은 버전부터, 그리고 이 글에서 가장 재미없는 결과입니다. **REST 호출에서는 어떤 언어를 고르든
상관없습니다.** "조금 상관있다"가 아니라, 그 차이를 보려면 뚫고 측정해야 하는 노이즈보다 차이가
더 작습니다.

![언어별 REST 지연 시간 분포: p01–p99 수염, p25–p75 상자, 중앙값 표시](/images/benchmarks/rest-latency-variability.png)

인터리브 실행에서 나온 모든 호출을 단일 숫자가 아닌 분포로 그린 것입니다(언어당 210회 호출).
PHP를 제외한 다섯 언어의 중앙값은 **21 ms** 범위 안에 들어갑니다. 한 언어 자체의 p01–p99는
**106–300 ms**에 걸쳐 있는데, 중앙값이 약 270이므로 언어 간 격차의 약 **13배**입니다. Go의
p99는 314 ms입니다. 가장 빠른 언어에서 운 나쁜 호출 한 번이 가장 느린 언어의 평범한 호출보다
느립니다.

이 중 CCXT 자체가 기여하는 몫은 언어에 따라 2–7 ms입니다. 그러니 언어를 골라서 최적화하려는
양은 그 언어 자체의 실행 간 편차의 대략 10분의 1입니다. 모든 요청에서 밀리초 단위를 세고 있는
것이 아니라면, 팀이 이미 알고 있는 언어를 고르세요.

**PHP는 예외인데, 이것은 언어가 아니라 버그입니다.** 222 ms 중앙값은 매 라운드마다 다른 모든
언어의 약 4배입니다. 이것이 노이즈가 아니라 실제라는 것을 깔끔하게 확인하는 방법: PHP의
*1퍼센타일* — 210회 중 최고의 호출 — 이 209 ms로, 다른 모든 언어의 p75보다 높습니다. 꼬리는
겹치지만, 분포의 본체는 서로 근처에도 오지 않습니다. 원인은 ReactPHP 커넥터가 요청마다 새
연결을 열기 때문에 모든 호출이 TCP+TLS 핸드셰이크 비용을 치른다는 것입니다. 고칠 수 있는
문제이며, §6을 참고하세요.

이 절의 나머지는 우리가 그것을 어떻게 알게 되었는지에 대한 이야기입니다. 첫 번째 측정 시도가
틀렸고, 틀린 방식이 교훈적이기 때문입니다.

### 어떻게 알았는가 — 그리고 처음에 어떻게 틀렸는가

명백한 접근법은 CCXT를 계측하는 것입니다. `fetch()`(HTTP 계층)와 `parseJson()`(그 안의 디코드)을
감싸고, 그 차이를 "네트워크"라 부르고, 남는 것을 "처리"라 부르는 것입니다. 그렇게 했고, 각
언어를 차례로 실행했고, C#이 Python보다 네트워크에 약 20 ms를 더 쓴다는 표를 얻었습니다. 그
결과는 두 가지 면에서 틀렸습니다.

**첫째, 실행이 인터리브되지 않았습니다.** 어떤 한 머신에서의 지연 시간은 분 단위로 흔들리며,
꼬리가 두껍습니다. 100–200 ms 이상치는 모든 언어, 모든 실행에서 나타납니다. 연속된 여섯 개
시간 창에서 측정한 여섯 언어는 서로 비교할 수 없습니다.

**둘째, 더 중요하게, `fetch() − decode`는 와이어 시간이 아닙니다.** 그 안에는 해당 언어의
HTTP 계층이 호출 내부에서 하는 다른 모든 일도 포함되어 있고, 그 경계는 여섯 개의 독립적인
구현 사이에서 같지 않습니다.

그래서 대조군을 추가했습니다. **CCXT를 전혀 쓰지 않고** 같은 엔드포인트에 보내는 순수한
keep-alive HTTPS GET을 언어당 하나씩, CCXT 자체 클라이언트와 라운드로빈으로 번갈아 실행해
둘이 같은 네트워크 창을 공유하도록 했습니다. 여섯 라운드:

| 언어 | 순수 클라이언트 | CCXT "네트워크" 구간 | 차이 |
|---|---|---|---|
| C# | 54.0 ms | 69.7 ms | **+15.6 ms** |
| JavaScript | 61.5 ms | 47.3 ms | −14.2 ms |
| Python | 61.4 ms | 46.3 ms | −15.1 ms |
| Java | 63.0 ms | 57.2 ms | −5.7 ms |
| Go | 62.0 ms | 44.9 ms | −17.1 ms |

순수 클라이언트들은 **8.9 ms** 이내에서 일치합니다. 모든 런타임의 HTTP 스택이 거의 같은
속도라는 것이며, 예상대로입니다. CCXT 구간은 **24.7 ms**에 걸쳐 퍼져 있고, 각각이 자기 언어의
순수 클라이언트와 서로 다른 방향으로 다릅니다. Go, JavaScript, Python의 경우 구간이 해당 언어
자체의 맨 HTTP GET보다 14–17 ms *아래*로 나오며, 여섯 라운드 중 여섯 번 모두 그렇습니다.
와이어 시간으로는 불가능하므로, 그 구간들은 단순히 요청 전체를 담고 있지 않은 것입니다.

C#은 과소 측정하지 않는 유일한 언어이고, 그래서 느려 보였습니다. 이를 임시 로컬 패치 — CCXT의
C# 내부에 와이어 전용 타이머 — 로 추적해 보니 시간이 정말로 `SendAsync`와 본문 읽기에
쓰이고 있었습니다(68.72 ms 구간 중 68.48 ms이므로 라이브러리 부기 비용이 아닙니다). 그리고
네 가지 핸들러 비교 — `SocketsHttpHandler`와 `HttpClientHandler`, 각각 자동 gzip 유무, 모두
한 프로세스에서 인터리브 — 에서 CCXT의 정확한 구성은 69.8 ms, 대안들은 63.4–71.0 ms였습니다.
CCXT의 C# 클라이언트는 평범한 C# 클라이언트입니다. 같은 실행에서 거의 동일한 두 구성이
7.6 ms 차이가 났는데, 그것이 우리가 설명하려던 효과의 크기입니다.

따라서 이 분할은 **언어 간에 비교할 수 없으며**, 우리는 이를 폐기했습니다. 비교 가능한 것은
`fetchOrderBook` 주변의 벽시계 시간 — 어디서나 같은 정의 — 을 인터리브, 라운드로빈으로 측정해
모든 언어가 같은 네트워크를 보게 한 것입니다.

![CCXT 없는 순수 HTTP 대조군과 비교한 언어별 REST 총 지연 시간](/images/benchmarks/rest-trace-waterfall.png)

![각 언어에서 추적한 fetchOrderBook 호출 한 번: 공통 로그 축 위의 중첩 구간](/images/benchmarks/rest-trace-compare.png)

위의 추적은 여전히 언어별 내부 구간을 보여 줍니다. 한 구현 안에서 시간이 *어디로* 가는지 보는
데 유용하기 때문입니다. 다만 네트워크 막대를 언어 간 동일 조건 비교로 읽지는 마세요. 다음
절에서는 네트워크를 완전히 제거하는데, 거기서 언어들이 진짜로 갈라집니다.

## 2. 네트워크를 제거한 지연 시간 — 언어가 실제로 갈라지는 곳

네트워크는 흥미로운 모든 것을 가립니다. 그래서 두 번째 테스트는 네트워크를 완전히 제거합니다.
합성한 1,000레벨 order book을 파싱 — 모든 응답의 CPU 집약적 핵심인 `parseJson` +
`parseOrderBook` — 하는 것을 촘촘한 오프라인 루프에서 돌리고, 파싱 한 번에 걸리는 시간을
측정합니다. 데이터가 이미 손에 있을 때의 지연 시간 하한입니다. 과거 데이터로 백테스트하거나
깊은 book을 재생하는 경우입니다.

![네트워크를 제거한 파싱 지연 시간, 여섯 개 언어와 Rust 프리뷰](/images/benchmarks/load-parse-latency.png)

이제 언어들은 **6배 이상** 벌어지고, 순서는 "컴파일 대 인터프리트"가 예측하는 것과 다릅니다.

- **JavaScript와 Java가 최상위에서 동률(각 ~0.44 ms)** — 성숙한 JIT가 핫 루프를 특화된
  기계어로 바꿉니다.
- **PHP(1.67 ms)**는 중간에 있습니다.
- **Python(2.20 ms), Go(2.62 ms), C#(2.77 ms)이 바닥에 모입니다.** 그렇습니다, *컴파일*
  언어 두 개가 인터프리트 언어인 Python *아래*에 있습니다.

### 보너스: Rust 포트 첫 인상

Rust 구현이 [PR #28627](https://github.com/ccxt/ccxt/pull/28627)에서 진행 중입니다. 그
브랜치의 스냅샷에 같은 벤치마크를 돌렸습니다. **~1.01 ms, 3위** — JavaScript와 Java 뒤,
Go와 C# 앞입니다. Rust 역시 트레이싱 JIT 없이 AOT 컴파일되므로, 이 순서는 아래의 박싱 비용이
컴파일이 아니라 코드가 생성되는 방식에 관한 것이라는 힌트입니다.

이는 움직이는 표적 — 어느 한 시점에 측정한 머지되지 않은 브랜치, 방법론에 적힌 주의 사항 포함
— 이므로, 결과가 아니라 대략적인 초기 신호로 받아들이세요.

Python의 표준 라이브러리 `json`을 빠른 Rust 파서 [`orjson`](https://github.com/ijl/orjson)으로
바꿔 보기도 했습니다. 별도의 행(`BENCH_ORJSON=1`)으로 표시되어 있습니다. 약 3%(2.20 → 2.13 ms)를
깎을 뿐 그 이상은 아닙니다. JSON 디코딩이 병목이 아니기 때문입니다. 지배적인 비용은 CCXT의 통합
`parseOrderBook`이고, 더 빠른 바이트 리더가 손댈 수 있는 부분이 아닙니다. 다음 절이 그 이유 —
그리고 컴파일 언어들이 그 자리에 놓이는 이유 — 입니다.

## 3. 왜 컴파일 언어 두 개가 가장 느릴까?

이 결과가 놀라워서 Go를 파고들었습니다. 답은 측정 오류가 아니라 트랜스파일 모델이며, C#도 같은
이야기입니다.

Go의 2.63 ms 파싱을 나누면 `parseJson`이 0.87 ms, `parseOrderBook`이 1.83 ms입니다.
`parseOrderBook` 내부에서 비용은 약 2,000개 가격 레벨 각각을 파싱하는 데 고르게 퍼져 있고,
한 곳의 핫스팟이 아닙니다. 이유는 CCXT의 Go가 JavaScript의 *동적* 시맨틱을 그대로 반영하기
때문입니다.

- 모든 가격과 수량은 `interface{}` 박스(Go의 `any`)이며, `json.UseNumber`와 재귀적 재정규화
  패스를 통해 디코딩됩니다.
- 모든 필드 읽기(`GetValue`), 모든 append(`*any`에 대한 `AppendToArray`), 모든 숫자
  변환(`SafeFloat` → type switch)은 제네릭한 런타임 타입 헬퍼입니다.
- `SortBy`의 숫자 비교자는 심지어 모든 비교의 두 피연산자에 대해 `reflect.TypeOf(...).Kind()`를
  호출합니다. 실시간 order book이 이미 정렬된 채 도착하기 때문에 저렴하게 유지되고 있을 뿐인
  잠재 비용입니다.

C#은 Go 바로 옆에 있는데(362 ops/s), AST 트랜스파일러가 동일한 `object` 박싱 패턴을 내보내기
때문입니다. `dynamic`은 쓰지 않으므로 이는 순수한 박싱과 가상 디스패치입니다.

그렇다면 왜 Java와 JavaScript는 *같은* 박싱된 동적 코드에서 약 6배 빠를까요? **트레이싱/티어드
JIT**입니다. V8과 HotSpot은 핫 루프를 관찰하고, 객체 형태에 특화하고, 런타임에 박싱을
제거합니다. Go의 AOT 컴파일러와 .NET의 JIT는 이 `any`/`object` 패턴을 그만큼 공격적으로
특화하지 않으므로, 박싱과 type switch가 매 반복마다 실행됩니다. 그것이 컴파일 언어 두 개가
인터프리트 언어인 Python과 PHP보다 느려지는 경위입니다.

이 숫자는 진짜이며, 단일 소스 트랜스파일의 의도적인 트레이드오프입니다. `[]float64`와
`sort.Slice`를 쓰는 손으로 작성한 Go 파서는 한 자릿수 배 더 빠르겠지만, 그러면 여섯 언어를
일치시켜 주는 단일 TypeScript 소스에서 생성되지 않게 됩니다. 네트워크에 묶인 REST 경로(§1)에서는
아무 비용도 들지 않고, 촘촘한 파싱 루프에서는 그것이 이야기의 전부입니다.

| 언어 | 런타임 | 파싱 지연 시간 | 처리량 |
|---|---|---|---|
| JavaScript | Node 22 | 0.44 ms | 2,293 /s |
| Java | OpenJDK 21 | 0.44 ms | 2,280 /s |
| Rust \* | rustc 1.94 | 1.01 ms | 988 /s |
| PHP | 8.4 | 1.67 ms | 598 /s |
| Python (orjson) | 3.11 | 2.13 ms | 469 /s |
| Python | 3.11 | 2.20 ms | 454 /s |
| Go | 1.25 | 2.62 ms | 381 /s |
| C# | .NET 8 | 2.77 ms | 362 /s |

\* *Rust는 머지되지 않은 [PR #28627](https://github.com/ccxt/ccxt/pull/28627)의 프리뷰로,
다른 머신에서 측정한 뒤 같은 머신의 JavaScript 기준 실행으로 정규화했습니다(원시값: 800 /s;
기준 머신은 23% 느리게 벤치마크됨). 방법론을 참고하세요.*

## 4. 메모리

파싱된 book들과 런타임 기준선을 함께 담고 있을 때의 최대 상주 메모리는 런타임에 따라 갈리고,
순위는 다시 뒤집힙니다.

![파싱 부하 하에서의 최대 메모리, 여섯 개 언어와 Rust 프리뷰](/images/benchmarks/load-memory.png)

**JavaScript가 가장 가볍고(425 MB)**, **Rust 프리뷰가 525 MB로 2위**입니다. Go, Python, C#은
675–690 MB 근처에 모이고, PHP의 연관 배열은 966 MB까지 밀어 올리며, **큰 힙을 미리 예약하는
Java의 JVM이 약 1.8 GB로 가장 무겁습니다.** 마지막 수치는 기준선에 의한 것이며 — `-Xmx`를
제한한 프로덕션 JVM이라면 훨씬 낮을 것입니다 — 그래도 기본 설정에서의 정직한 OS 점유량이고,
가장 빠른 파서가 가장 배고픈 이유이기도 합니다. 호스트당 수백 개 인스턴스를 돌린다면 Node와
Go가 가장 작은 점유량을 유지합니다.

지연 시간 수치와 달리 이 메모리 숫자들은 머신 간 조정이 필요 없었습니다. JavaScript 기준
실행이 두 번째 머신에서 원래의 book당(145 KB) 및 최대 RSS(425 MB) 값을 1% 이내로 재현했으므로
메모리는 그대로 옮겨집니다.

## 5. WebSocket: 실시간 order book 유지하기

REST 경로는 네트워크에 묶여 있고 부하 테스트는 순수 연산입니다. WebSocket 경로는 그 사이에
있습니다. Coinbase의 book은 약 43,000레벨이고, 초당 여러 번 갱신되며, 모든 델타가 그 안으로
병합됩니다. `watchOrderBook`으로 이를 감시하고(JavaScript, Python, PHP, Go) 델타당
**정상 상태** CPU를 측정합니다. 첫 번째 갱신은 전체 스냅샷을 구축하는 큰 일회성 비용이므로
따로 측정하고 여기서는 제외합니다.

![언어별 order book 갱신당 WebSocket CPU](/images/benchmarks/ws-cpu-per-update.png)

- **Python: 0.6 ms** — 압도적으로 가장 저렴합니다.
- **JavaScript(11.0 ms)와 PHP(11.7 ms)**는 중간입니다.
- **Go: 18.7 ms** — 델타당 가장 비쌉니다.

정말로 마이크로초가 아니라 밀리초입니다. 델타 하나에 많은 CPU이고, 이유는 규모입니다. book이
약 45,500레벨이고, 새 가격 레벨이 들어올 때마다 그 크기의 배열이 이동합니다. 검산으로,
JavaScript는 오프라인에서 2,000개 book 항목을 0.44 ms에 파싱하므로 약 45,500개 항목은 대략
10 ms가 되고, 측정된 델타당 11.0 ms와 정확히 맞아떨어집니다.

이 18배 편차는 사과와 오렌지의 비교가 아닙니다. 확인해 보니 모든 언어가 같은 book(스냅샷 이후
약 45,500레벨)을 들고 있었습니다. 차이는 각 언어가 거기에 *삽입*하는 방식에 있습니다. 모두
사이드를 정렬된 채로 유지하며 이진 탐색 후 이동을 수행하고, 이는 새 가격 레벨당 O(n)입니다.
그러나 상수 계수가 크게 다릅니다. CPython의 `list.insert`는 C 수준의 `memmove` 한 번입니다.
CCXT의 JavaScript 쪽은 삽입당 **두 번**의 이동을 하는데, 그중 하나 —
`this.index.copyWithin(index + 1, index, this.index.length)` — 는 활성 부분만이 아니라
*할당된 전체* 인덱스 버퍼(`length × 2` 크기)를 훑으며, 그것도 V8의 fast-elements 처리를 받지
못하는 `Array` 서브클래스 위에서 그렇게 합니다. Go와 PHP는 박싱된 값에 대해 같은 O(n) 이동
비용을 치릅니다.

다시 말해, 이 격차는 언어 자체가 아니라 언어별 order book 구현의 속성이며, JS 삽입 경로는
진짜 최적화 기회로 보입니다.

이 중 무엇도 데이터의 신선도를 바꾸지는 않습니다(그것은 거래소의 푸시 속도가 정하며, 네 언어
모두 갱신 간격 약 50 ms를 따라갑니다). 이것이 결정하는 것은 book이 최신 상태로 유지되는 동안
여러분의 전략에 남는 CPU 여유입니다. 일회성 스냅샷 구축은 약 1초(Python, JavaScript, Go)에서
PHP의 약 9초까지 걸린다는 점을 참고하세요.

| 언어 | 스냅샷 구축 | 정상 상태 간격 p50 | 갱신/s | 갱신당 CPU (정상 상태) | 최대 RSS |
|---|---|---|---|---|---|
| Python | 0.97 s | 49.7 ms | 19.8 | 0.6 ms | 162 MB |
| JavaScript | 1.69 s | 49.2 ms | 20.7 | 11.0 ms | 180 MB |
| PHP | 8.97 s | 49.8 ms | 16.7 | 11.7 ms | 116 MB |
| Go | 1.33 s | 50.1 ms | 17.4 | 18.7 ms | 105 MB |

## 6. 앞으로 살펴볼 것들

자기 라이브러리를 벤치마크하는 것은 유용한 방식으로 불편합니다. 위의 여러 숫자는 언어에 대한
사실이 아니라 우리가 고칠 수 있는 것들입니다. 여기 우리가 얻은 목록을 가치가 큰 순서대로
대략 정리하고, 그 숫자를 만들어 내는 코드와 함께 적었습니다.

**PHP의 REST 클라이언트는 연결을 풀링해야 합니다.** 이번 작업 전체에서 가장 큰 단일
개선점입니다. 모든 REST 호출에서 다른 모두의 약 52 ms 대 약 220 ms인데, ReactPHP 커넥터가
요청마다 새 연결을 열고 매번 TCP+TLS 핸드셰이크 비용을 치르기 때문입니다. PHP의 그 무엇도
그것을 요구하지 않습니다. keep-alive 풀이 있으면 나머지 다섯과 같은 수준이 될 것입니다.

**JavaScript의 order book 삽입은 필요 이상으로 이동합니다.**
[`ts/src/base/ws/OrderBookSide.ts`](https://github.com/ccxt/ccxt/blob/master/ts/src/base/ws/OrderBookSide.ts)에서
가격 레벨 삽입은 두 번의 이동을 하는데, 둘의 범위가 같은 방식으로 제한되어 있지 않습니다.

```js
this.index.copyWithin (index + 1, index, this.index.length)  // 할당된 버퍼 전체
this.index[index] = index_price
this.copyWithin (index + 1, index, this.length)              // 활성 항목만
```

`this.index`는 두 배씩 늘어나는 `Float64Array`(`existing.length = this.length * 2`)이므로,
첫 줄은 둘째 줄보다 최대 두 배 멀리 훑을 수 있습니다. 그것이 복사하는 꼬리는 `Number.MAX_VALUE`
패딩입니다. 아래 줄이 이미 그렇게 하듯 `this.length`로 제한하는 것은 안전해 보입니다. 약
45,500레벨 book에서 초당 약 20회 갱신이라면 그 이동이 델타당 11 ms CPU의 대부분입니다.

**Go의 `SortBy`는 비교자 안에서 포매팅 작업을 합니다.**
[`go/v4/exchange_generic.go`](https://github.com/ccxt/ccxt/blob/master/go/v4/exchange_generic.go)에서
문자열 키 분기는 이렇게 비교합니다.

```go
return fmt.Sprintf("%v", a) < fmt.Sprintf("%v", b)
```

O(n log n) 정렬의 *모든 비교*마다 두 번의 할당과 리플렉션 기반 포매팅입니다. 정수 키 분기는
같은 이유로 비교마다 `reflect.TypeOf(list[i]).Kind()`를 두 번 호출합니다. 둘 다 비교마다가
아니라 정렬 전에 한 번만 타입을 결정할 수 있습니다. 문자열 분기는 숫자도 사전순으로 정렬하는데,
그것만으로도 다시 볼 가치가 있습니다. 모든 값의 자릿수가 같은 13자리 밀리초 타임스탬프에는
괜찮지만, 다른 곳에서는 분명히 괜찮다고 할 수 없습니다.

**Go는 JSON을 두 번 디코딩합니다.** `ParseJson`은 `decoder.UseNumber()`를 실행한 다음
`normalizeNumbers`에서 디코딩된 트리 전체를 다시 걸으며 모든 `json.Number`를 변환합니다.
2,000레벨 book이라면 구조 전체를 두 번째로 완전히 순회하는 것입니다. 디코딩 중에 변환하면 이를
없앨 수 있습니다. Go의 `parseJson`은 2.63 ms 파싱 중 0.87 ms로 측정됩니다.

**Go와 C#의 박싱 비용은 구조적인 것입니다.** 모든 가격이 `interface{}`/`object`이고, 모든
필드 읽기, append, 변환이 제네릭한 런타임 타입 헬퍼를 거칩니다. 그것이 §2에서 컴파일 언어 두
개를 인터프리트 언어인 Python 뒤에 놓는 것이며, 하나의 소스에서 여섯 언어를 생성하는 데 따르는
의도적인 대가입니다. 하지만 자연법칙은 아닙니다. 가장 뜨거운 헬퍼(`GetValue`, `AppendToArray`,
`SafeFloat`)에 타입이 지정된 빠른 경로를 두면 트랜스파일 모델을 바꾸지 않고도 일부를 회복할 수
있을 것입니다. 목록에서 가장 큰 작업이자 가장 불확실한 작업입니다.

이 모든 것에 대한 주의 사항 하나: 밀리초 수치는 한 머신, 한 네트워크 경로에서 나온 것이므로
상금의 크기가 아니라 *어디를* 볼지 가리키는 것으로 받아들이세요. 재현 가능한 부분은 메커니즘 —
추가 핸드셰이크, 추가 순회, 비교자 안의 할당 — 이고, 그것들은 어느 한 번의 실행이 무엇을
측정하든 고칠 가치가 있습니다.

벤치마크 자체에 대한 교훈도 얻었는데, §1이 설명합니다. 라이브러리를 제거한 대조군 실행 없이
지연 시간을 언어 탓으로 돌리지 마세요. 우리의 첫 초안은 그렇게 했고, 틀렸습니다. 대조군은 이제
[`examples/benchmarks/net-baseline/`](https://github.com/ccxt/ccxt/tree/master/examples/benchmarks/net-baseline)에
있습니다.

## 요점 정리

- **REST라면 좋아하는 언어를 고르세요.** 왕복 시간이 지배적이고, PHP를 제외한 다섯 언어는
  네트워크 자체의 분 단위 흔들림 안에 들어가는 약 20 ms 대역에 있습니다. CCXT 없는 순수 HTTPS
  GET은 모든 언어에서 똑같이 빠르므로(8.9 ms 편차), 언어 선택이 무언가를 가져다주는 곳이
  아닙니다. PHP의 약 4배 벽시계 시간이 예외인데, 라이브러리가 아니라 HTTP 클라이언트(요청마다
  새 연결)의 문제입니다.
- **대량으로 파싱할 때는 런타임의 JIT가 전부입니다.** JavaScript와 Java는 PHP, Python, Go,
  C#보다 약 6배 빠르게 파싱하고, 컴파일 언어 두 개인 Go와 C#이 *가장 느립니다*. 트랜스파일된
  코드가 박싱 위주이고, 성숙한 트레이싱 JIT만이 이를 특화해 없애기 때문입니다.
- **메모리는 Node와 Go에 유리합니다.** 가장 작은 점유량을 유지하며, JVM은 기본 설정에서 가장
  빠르지만 가장 배고픕니다.
- **진행 중인 Rust 포트는 유망해 보입니다.** 초기 스냅샷에서 Go와 C#보다 빠르지만, 머지되지
  않은 브랜치이며 앞으로 바뀔 것입니다.
- **고빈도 WebSocket book에서는 Python이 놀랍도록 저렴하고**(델타당 약 0.6 ms CPU) Go가 가장
  비쌉니다(약 19 ms). PHP의 진짜 비용은 델타가 아니라 일회성 스냅샷 구축입니다.
- **대역폭은 차이가 없습니다.** 같은 프로토콜, 같은 바이트, 모든 언어가 동일합니다.
- **이 비용 중 여럿은 언어가 아니라 우리 것입니다.** §6이 PHP의 빠진 연결 풀부터 JavaScript
  order book의 과도하게 긴 배열 이동까지, 앞으로 살펴볼 것들을 나열합니다.

단일한 "가장 빠른 CCXT"는 없습니다. *여러분의 워크로드에* 가장 빠른 CCXT가 있고, 이제 여러분의
것을 찾기 위해 돌려 볼 수 있는 여섯 언어 벤치마크가 있습니다.

## 방법론과 주의 사항

- **네트워크/처리 분할은 의도적으로 보고하지 않습니다.** `fetch`와 `parseJson`을 계측하면
  언어별 구간이 나오지만, §1의 대조군은 그 구간들이 각 구현에서 같은 작업을 담고 있지 않음을
  보여 줍니다. 그중 셋은 해당 언어 자체의 맨 HTTP GET보다 14–17 ms 낮게 읽힙니다. 따라서 REST
  숫자는 `fetchOrderBook` 주변의 벽시계 시간만입니다.
- **REST 실행은 순차가 아니라 인터리브입니다.** 각 라운드는 여섯 언어를 라운드로빈으로
  실행하여 같은 네트워크 창을 공유하게 합니다. §1의 분포는 30회씩 7라운드(언어당 210회)의 모든
  호출을 모은 것이며, 하네스가 `latencySamplesMs`를 내보내므로 원시 데이터로부터 어떤
  퍼센타일이든 다시 계산할 수 있습니다. 언어별 순차 실행이 애초에 잘못된 분할을 만들어 낸
  원인이었습니다. `examples/benchmarks/net-baseline/`에 순수 클라이언트 대조군 프로그램이
  있습니다.
- **웜업은 15회 호출입니다**(`BENCH_REST_WARMUP`). 이전의 1–3회 웜업은 티어드 JIT를 차갑게
  남겨 두었습니다. Java의 처리 시간은 콜드 상태에서 약 23 ms, 웜 상태에서 약 3.3 ms로
  측정되었습니다.
- **부하 테스트는 오프라인이며 결정적입니다.** 같은 합성 1,000레벨 book(정수 값, 언어 간
  동일)을 8초로 시간 제한하여 순수 파싱 처리량을 측정합니다. `getrusage` CPU는 모든 스레드를
  세므로, 멀티스레드 런타임(Go의 GC, JVM)에서는 연산당 CPU가 아닌 단일 스레드 벽시계 처리량이
  공정한 숫자입니다.
- **WebSocket CPU는 정상 상태입니다.** 첫 `watchOrderBook`은 전체 스냅샷을 구축하는 큰
  일회성 비용이므로 따로 측정하고 그 이후에만 CPU 카운터를 시작합니다. 보고된 갱신당 CPU는
  증분 델타 비용이지, 갱신들에 걸쳐 상각한 스냅샷 비용이 아닙니다.
- **메모리는 부하 실행 종료 시점의 최대 RSS**(파싱 루프 + 보유한 2,000개 book)입니다. 런타임
  기준선을 포함하며, 그것이 핵심입니다. JVM의 큰 기본 힙은 실제 메모리입니다. 힙을 미리
  커밋하는 런타임에서는 객체별 델타가 신뢰할 수 없으므로 OS 최대치를 보고합니다.
- **Rust 수치는 정규화된 스냅샷이지 동등한 측정이 아닙니다.** 머지되지 않은
  [PR #28627](https://github.com/ccxt/ccxt/pull/28627)에서 나온 것으로, 프로젝트 도중 원래
  머신이 교체된 뒤 측정되었습니다. 처리량은 같은 머신의 JavaScript 기준 실행으로
  재조정했으며(그 머신은 23% 느리게 벤치마크됨; Rust의 원시 800 ops/s → 약 988), 크레이트는
  컴파일되도록 coinbase만 남기고 잘라 냈습니다. 메모리는 조정이 필요 없었습니다. JS 기준 실행이
  원래 숫자를 1% 이내로 재현했습니다. 원시값과 정규화값 모두 `results.json`에 있습니다.

## 결론

벤치마크가 아니라 워크로드에 맞춰 언어를 고르세요. REST 엔드포인트를 호출한다면 네트워크가
모든 것을 압도하므로 여섯 언어 중 어느 것이든 괜찮습니다. 대량으로 파싱하거나 깊은 order book을
병합한다면 런타임의 JIT와 생성된 코드의 형태가 결정하며, 그 순서는 언어가 컴파일되는지 여부와
거의 관계가 없습니다. 그리고 위의 비용 중 여럿은 언어가 아니라 우리가 고쳐야 할 것들이며, §6이
그것들을 지목합니다. CCXT 팀은 라이브러리를 지속적으로 개선하는 데 전념하고 있으므로, 이 글은
보고서인 만큼이나 로드맵이기도 합니다.
