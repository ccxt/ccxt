每篇 CCXT 教程的结尾都一样：`await exchange.fetchOrderBook(symbol)`。它们都没告诉你的是，
这一行的*代价*——字节返回之前要过去多少毫秒——与其说取决于交易所，不如说取决于**你的代码在
发问时正运行在哪里**。

我们测量了它。十家交易场所——七家现货交易所、一家永续合约 DEX（Hyperliquid），以及，既然 CCXT
现在[支持预测市场](/zh/docs)，一个预测市场（Polymarket）——每一家都从六大洲的八座城市访问其
公开的 order book 端点。差距并不微妙：同一个调用从正确的城市发出 **6 毫秒**就能返回，从错误的
城市发出则要超过**一秒**。

<LatencyMap />

在上面选一个交易场所，看看数据包想往哪里去。几个规律立刻跳了出来。

## 交易所都有自己的家，而且一眼就能看出来

按照它们响应最快的位置，这十家交易场所清晰地分成两个阵营：

- **托管在西方的**——**Coinbase**（从纽约*和*伦敦都是 10 毫秒）、**Kraken**（从伦敦 16 毫秒），
  以及有趣的 **Polymarket**（从伦敦 17 毫秒）位于美国/欧盟的基础设施上，测量点越往东就越慢。
- **托管在亚洲的**——**Binance、Bybit、Gate.io、OKX、KuCoin、Bitget** 以及 **Hyperliquid** 永续
  合约 DEX 都从东京、新加坡或香港响应最快（Hyperliquid 从东京只需 **6 毫秒**，是整个研究中最快
  的数字），而从美洲或欧洲调用时要付出 100–350 毫秒的代价。

不存在全球"快"的交易场所。只有*从你所在之处看很快*。从新加坡运行一个 Coinbase 策略，或者从
圣保罗运行一个 Binance 策略，你就悄悄地给每一个请求背上了四分之一秒的负担——在 rate limit
之前，在撮合引擎耗时之前，在你自己代码里任何可以优化的东西之前。

## 同一行代码，相差 10–100 倍

固定交易场所，只改变观测点：

| 交易场所 | 类型 | 最快城市 | 最慢城市 | 差距 |
|---|---|---|---|---|
| Coinbase | 现货 | 纽约 — 10 毫秒 | 悉尼 — 1109 毫秒 | ~111× |
| Hyperliquid | 永续合约 DEX | 东京 — 6 毫秒 | 伦敦 — 274 毫秒 | ~46× |
| Gate.io | 现货 | 东京 — 7 毫秒 | 圣保罗 — 281 毫秒 | ~40× |
| Binance | 现货 | 东京 — 8 毫秒 | 圣保罗 — 259 毫秒 | ~32× |
| Bybit | 现货 | 新加坡 — 10 毫秒 | 圣保罗 — 325 毫秒 | ~32× |
| Bitget | 现货 | 东京 — 16 毫秒 | 法兰克福 — 278 毫秒 | ~17× |
| Kraken | 现货 | 伦敦 — 16 毫秒 | 悉尼 — 268 毫秒 | ~17× |
| Polymarket | 预测市场 | 伦敦 — 17 毫秒 | 悉尼 — 264 毫秒 | ~16× |
| KuCoin | 现货 | 东京 — 21 毫秒 | 圣保罗 — 320 毫秒 | ~15× |
| OKX | 现货 | 香港 — 29 毫秒 | 圣保罗 — 353 毫秒 | ~12× |

从悉尼访问 Coinbase 是最突出的：首字节要**超过一秒**，而且这不是偶然——在五轮测量中中位数一直
保持在约 1.1 秒。Coinbase 的 API 在亚太地区没有接入点，所以来自澳大利亚的请求要横跨太平洋
折返到美国的基础设施再回来。如果你每秒轮询一次 order book，这个请求永远赶不及在下一次到期前
完成。

## "可他们不是在我附近有服务器吗？"

一个合理的反驳：大型交易所运营着全球基础设施——法兰克福附近肯定有一台 Binance 的机器吧？为了
回答这个问题，我们把 **TCP 握手**（*连接*需要多久）和**首字节时间**（order book *数据*到达需要
多久）分开计时。以 Binance 为例：

| 来源 | TCP 连接 | TTFB（数据） | 数据往返 |
|---|---|---|---|
| 东京 | 2 毫秒 | 8 毫秒 | ~6 毫秒 |
| 悉尼 | 1 毫秒 | 107 毫秒 | ~106 毫秒 |
| 伦敦 | 3 毫秒 | 229 毫秒 | ~226 毫秒 |
| 圣保罗 | 1 毫秒 | 259 毫秒 | ~258 毫秒 |

答案是**两者都对，而这个区别就是整个故事**。TCP 握手**从任何地方都是 1–3 毫秒**——你附近
*确实*有一个边缘接入点，在本地终结你的连接（一个 anycast/CDN 前门）。你并没有跟东京做 TCP
往返。但 order book 是实时的、按请求生成的数据——它无法由边缘缓存提供——所以前门只是把你的
请求转发到亚洲的源站，再把答案转回来。这个转发的跳数就是最后一列，而它随距离干净利落地增长。
本地 PoP 帮你省下的是*连接建立*的成本；它**并不能**省下*数据获取*的成本。对于你真正关心的
那件事，Binance 实际上总是从东京回答。（像 `exchangeInfo` 这样可缓存的端点表现不同——那些
*可以*来自边缘，在哪里看起来都很快。要为源站往返买单的是实时读取。）

## 不只是速度——还有访问权限

延迟的前提是你能连上。从我们纽约的探测点看，有两家交易场所不是慢，而是*墙*：

- **Binance 返回 HTTP 451**（"因法律原因不可用"）——众所周知的美国地理封锁。5 个样本中有 3 个
  被封锁；`api.binance.com` 不会为大多数美国 IP 提供服务，无论延迟多少。
- **Bybit 从数据中心 IP 段返回 HTTP 403**（5 个样本中有 4 个，在 DigitalOcean/M247 之类的网络
  上）。这一个取决于网络而不是全面的地理封锁——另一个美国探测点偶尔能拿到 200——但如果你部署到
  错误的美国云 IP 段，就会被拒绝。

它们在地图和表格里显示为 `blocked`。"我应该部署在哪个区域？"有时是由交易场所的合规规则*替你*
回答的，而不是由 ping 时间。（有趣的是，Polymarket——它封锁美国*交易者*——却愉快地在 87 毫秒
内把它的 order book 提供给了我们纽约的探测点。API 主机和交易许可是两道不同的门。）

## 我们是怎么测量的（以及你如何自己重做一遍）

整个研究是免费且可复现的——没有云账单，不需要启动一整队虚拟机。

**探测网络。** 我们使用了 [Globalping](https://globalping.io)，jsDelivr 免费的、社区运营的
测量探测网络，通过它的公开 HTTP API（不需要密钥）。它从每个目标城市的一个真实探测点发起
HTTPS `GET`，并返回各阶段的耗时：DNS、TCP 握手、TLS，以及**首字节时间（TTFB）**——也就是我们
报告的那个数字。

**请求。** 对每家交易场所，我们访问的是 CCXT 的 `fetchOrderBook` 在底层映射到的公开 order book
（深度）端点——例如 `api.binance.com/api/v3/depth`、`api.exchange.coinbase.com/products/BTC-USD/book`
和 `clob.polymarket.com/book`（带一个在运行时解析的实时 token id）。有两家需要加注：
**Polymarket** 的 order book 由一个轮换的市场 token 参数化，所以我们每次运行都获取一个当前的；
**Hyperliquid** 的数据 API 只接受 POST，所以我们计时的是一个其源站以 405 回应的 `GET /info`——
仍然是一次真实的往返，只是没有 order book 载荷。

**数字。** 每个交易场所 × 城市的组合都采样了五轮；我们报告的是**有效往返的 TTFB 中位数**，
这会平滑掉抖动。大多数样本被拒绝的单元格（那些 451 和 403）标记为 blocked，而不是给出一个
延迟值。

采集器是一个随本文一起提交到 CCXT 仓库的单个 Node 脚本：
[`docs/website/scripts/collect-latency.mjs`](https://github.com/ccxt/ccxt/blob/master/docs/website/scripts/collect-latency.mjs)。
它生成的快照也一并提交了
（[`latency-data.json`](https://github.com/ccxt/ccxt/blob/master/docs/website/src/data/latency-data.json)），
所以你既可以核对我们的数字，也可以重新生成它们。克隆仓库并重新运行以获得一次新鲜的读数——
除了 Node 18+ 之外没有其他依赖：

```bash
git clone https://github.com/ccxt/ccxt.git
cd ccxt/docs/website
node scripts/collect-latency.mjs 5   # 5 轮 -> src/data/latency-data.json
```

### 坦诚的注意事项

- **TTFB 包含服务器处理时间，而不仅仅是网络。** 它是真正对你重要的数字——数据到达之前的总
  时间——但它不是纯粹的网络 RTT。
- **长途单元格波动很大。** 跨太平洋路由起伏不定：Coinbase→悉尼在各轮之间从 328 毫秒到
  1119 毫秒不等。地图显示的是中位数；把鼠标悬停在表格单元格上可以看到范围。
- **交易所位于 CDN 和负载均衡器之后**，所以你测到的往往是最近的边缘 PoP，而不是单一的源站
  机器（见上面 TCP 与 TTFB 那一节）。这些是*访问*延迟，而不是托管距离。
- **探测点托管在数据中心**——在这里这是个优点：它反映的是交易机器人实际运行的地方
  （AWS/GCP 区域），而不是家庭 Wi-Fi。
- **这是一个时间点的快照。** 路由和 PoP 的布局会变化。把地图的形态当作持久的，把具体的毫秒数
  当作一次读数。

## 该拿这些做什么

1. **部署在你的交易场所附近，而不是你自己附近。** 大多数机器人能获得的最大延迟收益不是代码——
   而是选择离你的交易场所响应位置最近的云区域。对 Binance 或 Hyperliquid 来说那是东京；对
   Coinbase 来说是美国东部；对 Polymarket 来说是欧洲。
2. **多交易场所？有意识地选择你的折中方案。** 如果你在同一台机器上*同时*交易 Coinbase 和
   Binance，没有哪个区域对两者都好。接受这种拆分，把工作进程分布到多个区域，或者把 order book
   读取改走 [WebSocket](/zh/blog/realtime-market-data-with-websockets)，这样你只在订阅时付一次
   往返代价，而不是每次轮询都付。
3. **从你实际的部署区域测量。** 你笔记本的 ping 不是你的生产环境 ping。在你将要部署的那台机器
   上运行采集器（或者 CCXT 本身）。
4. **先确认访问权限再优化。** 地理封锁或 403 不是你能调优掉的延迟问题。先检查你的交易场所到底
   为不为你的区域提供服务。

CCXT 给你[一套覆盖 100 多家交易所的 API](/zh/docs)——现在还包括永续合约 DEX 和预测市场——
所以你只需改一个标识符就能把策略在交易场所之间迁移。这张地图是这个故事的另一半：代码是可移植
的，但*物理*不是。在决定你的机器人住在哪里之前，先弄清楚你的交易所住在哪里。
