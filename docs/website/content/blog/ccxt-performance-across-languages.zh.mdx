CCXT 从同一份 TypeScript 源码出发，转译成六种语言，提供*完全相同*的交易 API。于是一个显而易见的问题是：**你选择的语言会影响性能吗？** PHP 写的机器人比 Go 写的慢吗？Python 会占用更多内存吗？编译型语言一定最快吗？

答案分三个层面，而且三者并不一致。所以我们把这三个层面都测了一遍，覆盖全部六种语言——JavaScript（Node）、Python、PHP、C#、Go 和 Java——并且顺带看了一眼还在进行中的 Rust 移植版：

1. **REST 延迟**——同一个 `fetchOrderBook` 调用，在某种语言里会更慢吗？
2. **去掉网络之后库本身的速度**——每种语言实际*解析*一份 order book 到底有多快？
3. **内存**——每个运行时要背多大的包袱？

代码都在仓库里
（[`examples/benchmarks/`](https://github.com/ccxt/ccxt/tree/master/examples/benchmarks)），
文中每一个数字你都可以自己复现。

## 1. REST 延迟：瓶颈在网络，不在库

先说简短版本，这也是整篇文章里最无趣的结论：**对于 REST 调用，选什么语言无关紧要。** 不是"稍微有点关系"——语言之间的差异比你要穿透才能看到它的噪声还小。

![各语言 REST 延迟分布：p01–p99 须线、p25–p75 箱体、中位数标记](/images/benchmarks/rest-latency-variability.png)

交错运行中的每一次调用都以分布而非单一数字的形式画出来（每种语言 210 次调用）。五种非 PHP 语言的中位数之间只相差 **21 ms**。而单一语言自身的 p01–p99 区间就覆盖了 **106–300 ms**——中位数约 270，大约是语言间差距的 **13 倍**。Go 的 p99 是 314 ms：最快的语言里一次倒霉的调用，比最慢的语言里一次普通调用还慢。

CCXT 自身在这里面的贡献，视语言不同只有 2–7 ms。所以你为了优化而挑语言所争取的那个量，大致只是该语言自身运行间波动的十分之一。除非你在每一次请求上都要计较单个毫秒，否则就选你团队已经熟悉的语言。

**PHP 是例外，但那是一个 bug，不是语言的问题。** 它 222 ms 的中位数大约是其他所有语言的 4 倍，每一轮都是如此。要干净地证明这是真实差异而不是噪声：PHP 的*第一百分位*——210 次调用里最好的那一次——是 209 ms，比其他任何语言的 p75 都高。尾部有重叠，但分布的主体根本不接近。原因是 ReactPHP 连接器为每个请求都新开一条连接，所以每次调用都要付一次 TCP+TLS 握手的代价。可修复；见第 6 节。

本节余下的部分讲的是我们如何得出这个结论，因为我们第一次测量的方式是错的，而它错的方式很有启发。

### 我们如何得知——以及一开始如何搞错

最直观的做法是给 CCXT 打桩：包一层 `fetch()`（HTTP 层）和 `parseJson()`（其中的解码），把两者的差值叫作"网络"，剩下的叫作"处理"。我们就是这么做的，依次运行每种语言，得到一张表，显示 C# 在网络上比 Python 多花约 20 ms。这个结果错了两次。

**第一，各次运行没有交错。** 任何一台机器的延迟都会随分钟漂移，而且带有厚尾——100–200 ms 的离群值在每种语言、每次运行里都会出现。六种语言在六个连续时间窗里分别测量，彼此之间不可比。

**第二，也是更重要的一点，`fetch() − decode` 并不是线路时间。** 它还包含该语言的 HTTP 层在这次调用内部做的所有其他事情，而这些边界在六个独立实现之间并不相同。

于是我们加了一个对照组：对同一端点做一个普通的 keep-alive HTTPS GET，**完全不经过 CCXT**，每种语言一个，与 CCXT 自己的客户端轮流交错运行，让两者共享同一个网络时间窗。六轮下来：

| 语言 | 裸客户端 | CCXT "网络" span | 差值 |
|---|---|---|---|
| C# | 54.0 ms | 69.7 ms | **+15.6 ms** |
| JavaScript | 61.5 ms | 47.3 ms | −14.2 ms |
| Python | 61.4 ms | 46.3 ms | −15.1 ms |
| Java | 63.0 ms | 57.2 ms | −5.7 ms |
| Go | 62.0 ms | 44.9 ms | −17.1 ms |

裸客户端之间的差异在 **8.9 ms** 以内——每个运行时的 HTTP 栈都差不多一样快，这符合预期。CCXT 的 span 却分散了 **24.7 ms**，而且每一个与本语言裸客户端的偏差方向都不一样。对 Go、JavaScript 和 Python 来说，这个 span 比该语言自己的裸 HTTP GET 还*低* 14–17 ms，六轮里六轮都是——作为线路时间这不可能，所以这些 span 根本没有覆盖完整的请求。

C# 是唯一没有少测的那个，这反而让它看起来慢。我们用一个一次性的本地补丁追了下去——在 CCXT 的 C# 里加一个只计线路时间的计时器——结果显示时间确实花在 `SendAsync` 加上读取响应体上
（68.72 ms 的 span 里有 68.48 ms，所以不是库内部的簿记开销），再加一次四路 handler 对比
——`SocketsHttpHandler` 和 `HttpClientHandler`，各自开启与不开启自动 gzip，全部在同一进程内交错运行——CCXT 的具体配置是 69.8 ms，而其他几种是 63.4–71.0 ms。CCXT 的 C# 客户端就是一个普通的 C# 客户端；同一次运行里两个几乎相同的配置相差了 7.6 ms，而这正是我们试图解释的效应的大小。

所以这种拆分**在语言之间不可比**，我们已经把它去掉了。可比的是围绕 `fetchOrderBook` 的墙钟时间——各处定义相同——以交错、轮转的方式测量，让每种语言看到同样的网络：

![各语言 REST 总延迟与不带 CCXT 的裸 HTTP 对照组比较](/images/benchmarks/rest-trace-waterfall.png)

![每种语言里追踪一次 fetchOrderBook 调用：共享对数轴上的嵌套 span](/images/benchmarks/rest-trace-compare.png)

上面的追踪图仍然展示了每种语言的内部 span，因为它们对于观察单个实现里时间花在*哪里*很有用——只是不要把跨语言的网络条读作同等条件的比较。下一节会把网络完全移除，那才是各语言真正拉开差距的地方。

## 2. 去掉网络后的延迟——语言真正分化的地方

网络掩盖了所有有意思的东西。所以第二个测试把它彻底去掉：在一个紧凑的离线循环里解析一份合成的 1,000 档 order book——`parseJson` + `parseOrderBook`，也就是每个响应中受 CPU 限制的核心——并测量一次解析需要多长时间。当数据已经在手里时，这就是你的延迟下限：在历史数据上做 backtest，或者回放一份深度很大的盘口。

![去掉网络后的解析延迟，全部六种语言加 Rust 预览版](/images/benchmarks/load-parse-latency.png)

现在各语言之间拉开了**超过 6 倍**的差距，而且排序并不是"编译型 vs 解释型"所能预测的：

- **JavaScript 和 Java 并列第一（各约 0.44 ms）**——它们成熟的 JIT 把热循环变成了特化的机器码。
- **PHP（1.67 ms）** 位居中间。
- **Python（2.20 ms）、Go（2.62 ms）和 C#（2.77 ms）聚在底部**——是的，这意味着两种*编译型*语言排在解释型的 Python *之后*。

### 彩蛋：Rust 移植版初探

一个 Rust 实现正在 [PR #28627](https://github.com/ccxt/ccxt/pull/28627) 中推进。我们对该分支的一个快照跑了同样的基准：**约 1.01 ms，第三名**——落后于 JavaScript 和 Java，领先于 Go 和 C#。由于 Rust 同样是 AOT 编译且没有追踪式 JIT，这个排序暗示下文所说的装箱税与代码如何生成有关，而与是否编译无关。

这是一个移动的靶子——某一时刻测得的一个未合并分支，还带着方法论里的那些限定——所以把它当作粗略的早期信号，而不是结论。

我们还试着把 Python 标准库的 `json` 换成快速的 Rust 解析器
[`orjson`](https://github.com/ijl/orjson)——单独作为一行展示（`BENCH_ORJSON=1`）。它只省下约 3%（2.20 → 2.13 ms），再多就没有了：JSON 解码根本不是瓶颈。主要成本在 CCXT 统一的 `parseOrderBook` 上，更快的字节读取器碰不到它。下一节讲的就是原因——以及编译型语言为什么会落到那个位置。

## 3. 为什么两种编译型语言最慢？

这让我们很意外，所以我们深挖了 Go。答案不是测量误差——而是转译模型，C# 的故事也一模一样。

拆开 Go 那 2.63 ms 的解析：`parseJson` 占 0.87 ms，`parseOrderBook` 占 1.83 ms。在 `parseOrderBook` 内部，成本均匀地分布在解析约 2,000 个价格档位的每一个上——没有单一热点。原因在于 CCXT 的 Go 代码镜像了 JavaScript 的*动态*语义：

- 每个价格和数量都是一个 `interface{}` 装箱值（Go 的 `any`），通过 `json.UseNumber` 解码后再做一次递归的重新规范化；
- 每一次字段读取（`GetValue`）、每一次追加（对 `*any` 的 `AppendToArray`）、每一次数值强制转换（`SafeFloat` → 一个 type switch）都是通用的、运行时定型的辅助函数；
- `SortBy` 的数值比较器甚至会在每次比较时对两个操作数都调用 `reflect.TypeOf(...).Kind()`——这是一个潜在成本，只因为实时 order book 到达时已经排好序才显得便宜。

C# 紧挨着 Go（362 ops/s），因为 AST 转译器生成了完全相同的 `object` 装箱模式——而且它没有用 `dynamic`，所以这就是纯粹的装箱加虚分派。

那么为什么 Java 和 JavaScript 在*同样*装箱、同样动态的代码上能快约 6 倍？**追踪式/分层 JIT。** V8 和 HotSpot 会观察热循环，针对对象形状做特化，并在运行时消除装箱。Go 的提前编译器和 .NET 的 JIT 对这种 `any`/`object` 模式的特化远没有那么激进，所以装箱和 type switch 在每一次迭代里都会执行——这就是两种编译型语言最终慢于解释型 Python 和 PHP 的原因。

这个数字是真实的，而且是单一事实来源转译模式下有意为之的取舍：一个手写的、使用 `[]float64` 和 `sort.Slice` 的 Go 解析器会快一个数量级——但那样它就不再是从让六种语言保持同步的那份 TypeScript 源码生成的了。对于受网络限制的 REST 路径（第 1 节）它没有任何代价；对于紧凑的解析循环，它就是全部。

| 语言 | 运行时 | 解析延迟 | 吞吐量 |
|---|---|---|---|
| JavaScript | Node 22 | 0.44 ms | 2,293 /s |
| Java | OpenJDK 21 | 0.44 ms | 2,280 /s |
| Rust \* | rustc 1.94 | 1.01 ms | 988 /s |
| PHP | 8.4 | 1.67 ms | 598 /s |
| Python (orjson) | 3.11 | 2.13 ms | 469 /s |
| Python | 3.11 | 2.20 ms | 454 /s |
| Go | 1.25 | 2.62 ms | 381 /s |
| C# | .NET 8 | 2.77 ms | 362 /s |

\* *Rust 是来自未合并的 [PR #28627](https://github.com/ccxt/ccxt/pull/28627) 的预览版，在另一台机器上测得，并通过同机 JavaScript 参考运行做了归一化（原始值：800 /s；参考机器的基准成绩慢 23%）。见方法论。*

## 4. 内存

持有已解析的 order book 加上运行时基线，峰值常驻内存按运行时分层，而排名再一次翻转：

![解析负载下的峰值内存，全部六种语言加 Rust 预览版](/images/benchmarks/load-memory.png)

**JavaScript 最精简（425 MB）**，**Rust 预览版以 525 MB 位居第二**；Go、Python 和 C# 聚在 675–690 MB 附近；PHP 的关联数组把它推到了 966 MB；而 **Java 的 JVM 由于预先保留了一大块堆，以约 1.8 GB 排在最重的位置**。最后这个数字是基线驱动的——一个用 `-Xmx` 限制了堆的生产 JVM 会低得多——但它是开箱即用状态下诚实的操作系统足迹，也是最快的解析器同时也最能吃内存的原因。如果你在一台主机上跑成百上千个实例，Node 和 Go 的足迹最小。

与延迟数字不同，这些内存数字不需要跨机器调整：JavaScript 参考运行在第二台机器上把原来的单本盘口占用（145 KB）和峰值 RSS（425 MB）复现到了 1% 以内，所以内存数据可以直接迁移。

## 5. WebSocket：维护一份实时 order book

REST 路径受网络限制，负载测试是纯计算；WebSocket 路径介于两者之间——Coinbase 的盘口约有 43,000 档，每秒更新多次，每一个增量都要合并进去。我们用 `watchOrderBook`（JavaScript、Python、PHP 和 Go）监听它，并测量每个增量的**稳态** CPU——第一次更新会构建整个快照，那是一个很大的一次性成本，我们单独计时并在这里排除：

![各语言每次 order book 更新的 WebSocket CPU 消耗](/images/benchmarks/ws-cpu-per-update.png)

- **Python：0.6 ms**——遥遥领先地便宜。
- **JavaScript（11.0 ms）和 PHP（11.7 ms）** 位居中间。
- **Go：18.7 ms**——每个增量最昂贵。

那确实是毫秒，不是微秒。对一个增量来说这是很多 CPU，原因在于规模：盘口约有 45,500 档，每一个新价格档位都要挪动一个那么大的数组。作为合理性检查，JavaScript 离线解析 2,000 个盘口条目需要 0.44 ms，那么约 45,500 个条目大致是 10 ms——正好落在实测的每增量 11.0 ms 附近。

这 18 倍的差距并不是拿苹果比橘子：我们检查过，每种语言持有的都是同一份盘口（快照之后约 45,500 档）。差别在于每种语言如何往里*插入*。它们都保持每一侧有序，做一次二分查找加一次挪动，对每个新价格档位来说是 O(n)——但常数因子差异巨大。CPython 的 `list.insert` 是一次 C 级别的 `memmove`。CCXT 的 JavaScript 侧每次插入做**两次**挪动，其中一次——
`this.index.copyWithin(index + 1, index, this.index.length)`——遍历的是*整个已分配*的索引缓冲区（大小为 `length × 2`），而不只是活跃部分，而且是在一个得不到 V8 快速元素优化的 `Array` 子类上。Go 和 PHP 则在装箱值上付同样的 O(n) 挪动代价。

换句话说：这个差距是各语言 order book 实现的属性，而不是语言本身的属性，而且 JS 的插入路径看起来是一个货真价实的优化机会。

这些都不会改变数据的新鲜度（那由交易所的推送频率决定，四种语言都以约 50 ms 的更新间隔跟上了）；它决定的是在盘口保持最新的同时，还给你的策略留下多少 CPU 余量。注意一次性的快照构建从约 1 s（Python、JavaScript、Go）到 PHP 的约 9 s 不等。

| 语言 | 快照构建 | 稳态间隔 p50 | 更新/s | CPU/更新（稳态） | 峰值 RSS |
|---|---|---|---|---|---|
| Python | 0.97 s | 49.7 ms | 19.8 | 0.6 ms | 162 MB |
| JavaScript | 1.69 s | 49.2 ms | 20.7 | 11.0 ms | 180 MB |
| PHP | 8.97 s | 49.8 ms | 16.7 | 11.7 ms | 116 MB |
| Go | 1.33 s | 50.1 ms | 17.4 | 18.7 ms | 105 MB |

## 6. 我们接下来要研究的

给自己的库做基准测试，会让人以一种有益的方式感到不自在。上面的好几个数字并不是关于某种语言的事实——而是我们可以修的东西。下面是我们得出的清单，大致按价值排序，并附上产生这些数字的代码。

**PHP 的 REST 客户端应该做连接池。** 这是整个练习里最大的单项收益：每一次 REST 调用约 220 ms，而其他所有人约 52 ms，因为 ReactPHP 连接器为每个请求都新开一条连接，每次都付一次 TCP+TLS 握手。PHP 没有任何东西要求这样做。一个 keep-alive 连接池能让它与其他五种语言看齐。

**JavaScript 的 order book 插入挪动的范围超出了必要。** 在
[`ts/src/base/ws/OrderBookSide.ts`](https://github.com/ccxt/ccxt/blob/master/ts/src/base/ws/OrderBookSide.ts) 里，插入一个价格档位要做两次挪动，而两者的边界并不相同：

```js
this.index.copyWithin (index + 1, index, this.index.length)  // 整个已分配的缓冲区
this.index[index] = index_price
this.copyWithin (index + 1, index, this.length)              // 只有活跃条目
```

`this.index` 是一个按倍增扩容的 `Float64Array`（`existing.length = this.length * 2`），所以第一行遍历的距离最多可达第二行的两倍——它复制的尾部是 `Number.MAX_VALUE` 填充。像下面那行已经做的那样把它限制到 `this.length`，看起来是安全的。在一份约 45,500 档、约 20 更新/s 的盘口上，这次挪动占了每增量 11 ms CPU 的大部分。

**Go 的 `SortBy` 在比较器内部做格式化工作。** 在
[`go/v4/exchange_generic.go`](https://github.com/ccxt/ccxt/blob/master/go/v4/exchange_generic.go) 里，字符串键分支是这样比较的：

```go
return fmt.Sprintf("%v", a) < fmt.Sprintf("%v", b)
```

这是在一次 O(n log n) 排序的*每一次比较*中做两次分配和一次基于反射的格式化。整数键分支出于同样的原因，每次比较调用两次 `reflect.TypeOf(list[i]).Kind()`。两者都可以在排序前解析一次类型，而不是每次比较都解析。字符串分支还会按字典序给数字排序，这本身就值得再看一眼——对 13 位的毫秒时间戳来说没问题，因为每个值的宽度相同，但在其他地方就不见得没问题了。

**Go 把 JSON 解码了两遍。** `ParseJson` 先运行 `decoder.UseNumber()`，然后在 `normalizeNumbers` 里再次遍历整棵解码后的树，把每一个 `json.Number` 转换掉。对一份 2,000 档的盘口来说，这是对整个结构的第二次完整遍历。在解码过程中转换就能省掉它。Go 的 `parseJson` 在 2.63 ms 的解析中占了 0.87 ms。

**Go 和 C# 的装箱税是结构性的那个。** 每个价格都是一个 `interface{}`/`object`，每一次字段读取、追加和强制转换都经过一个通用的运行时定型辅助函数。这就是第 2 节里让两种编译型语言落后于解释型 Python 的原因，也是从一份源码生成六种语言有意付出的代价——但它不是自然法则。在最热的辅助函数（`GetValue`、`AppendToArray`、`SafeFloat`）里加入定型的快速路径，可以在不改变转译模型的前提下挽回一部分。这是清单上最大的一项工作，也是最不确定的一项。

对以上所有条目有一点要提醒：这些毫秒数字来自一台机器上的一条网络路径，所以把它们当作指出*该往哪里看*，而不是奖品的大小。可复现的部分是机制——一次多余的握手、一次多余的遍历、比较器里的一次分配——无论任何单次运行测出什么，这些都值得修复。

我们对基准测试本身也得到了一个教训，第 1 节已经描述过：在没有去掉库的对照运行之前，不要把延迟归因于语言。我们的初稿这么做了，而且是错的。对照组现在放在
[`examples/benchmarks/net-baseline/`](https://github.com/ccxt/ccxt/tree/master/examples/benchmarks/net-baseline)。

## 要点

- **对于 REST，选你喜欢的语言。** 往返时间占主导，五种非 PHP 语言落在约 20 ms 的区间内，而这个区间本身就在网络分钟级漂移之内。不带 CCXT 的裸 HTTPS GET 在所有语言里一样快（8.9 ms 的分散），所以这不是语言选择能给你带来任何好处的地方。PHP 约 4 倍的墙钟时间是例外，而那是它的 HTTP 客户端（每个请求新开连接）的问题，不是库的问题。
- **当你大量解析时，运行时的 JIT 就是一切。** JavaScript 和 Java 的解析速度比 PHP、Python、Go 和 C# 快约 6 倍——而两种编译型语言 Go 和 C# 排在*最慢*——因为转译出的代码装箱很重，只有成熟的追踪式 JIT 能把它特化掉。
- **内存方面 Node 和 Go 占优。** 它们保持最小的足迹；JVM 最快但开箱即用时最能吃内存。
- **进行中的 Rust 移植版看起来很有前景**——在早期快照中快于 Go 和 C#，不过它是一个未合并的分支，还会变化。
- **对于高频的 WebSocket 盘口，Python 便宜得惊人**（每增量约 0.6 ms CPU），Go 最昂贵（约 19 ms）；PHP 真正的成本在一次性的快照构建上，而不在增量上。
- **带宽方面没有差别**——同样的协议、同样的字节，每种语言都一样。
- **其中好几项成本是我们的，不是语言的**——第 6 节列出了我们要研究的内容，从 PHP 缺失的连接池到 JavaScript order book 里过长的数组挪动。

不存在单一的"最快的 CCXT"。只有*针对你的工作负载*最快的 CCXT——而现在有了一套六语言基准测试，你可以自己跑一遍找到属于你的那个。

## 自己跑一遍

完整的测试框架——`bench.mjs`、`bench.py`、`bench.php`，以及 Go、C# 和 Java 程序——都在
[`examples/benchmarks/`](https://github.com/ccxt/ccxt/tree/master/examples/benchmarks)：

```bash
# REST / WebSocket / 离线解析负载，按语言运行

python examples/benchmarks/bench.py  ws

dotnet run -c Release --project examples/benchmarks/cs load
gradle run --args=load                     # 在 examples/benchmarks/java 目录下

# ...或者运行所有语言和所有模式，并汇总成表格：
node examples/benchmarks/run.mjs
```

还有一个**交互式的动画追踪浏览器**——
[`examples/benchmarks/trace-explorer.html`](https://github.com/ccxt/ccxt/blob/master/examples/benchmarks/trace-explorer.html)
——你可以在里面回放每种语言的一次 `fetchOrderBook` 调用，切换线性/对数时间轴，并把鼠标悬停在任意 span 上查看它在追踪中的精确占比。

## 方法论与注意事项

- **我们有意不报告网络/处理的拆分。** 给 `fetch` 和 `parseJson` 打桩能得到每种语言的 span，但第 1 节的对照组表明这些 span 在各个实现里覆盖的工作并不相同——其中三个比该语言自己的裸 HTTP GET 还低 14–17 ms。因此 REST 数字只是围绕 `fetchOrderBook` 的墙钟时间。
- **REST 运行是交错的，不是顺序的。** 每一轮以轮转方式运行全部六种语言，让它们共享同一个网络时间窗。第 1 节的分布汇集了 7 轮、每轮 30 次的所有调用（每种语言 210 次）；测试框架会输出 `latencySamplesMs`，所以任何百分位都可以从原始数据重新计算。按语言顺序运行正是当初产生那个错误拆分的原因。`examples/benchmarks/net-baseline/` 存放着裸客户端对照程序。
- **预热为 15 次调用**（`BENCH_REST_WARMUP`）。此前 1–3 次的预热让分层 JIT 处于冷状态：Java 的处理时间冷态测得约 23 ms，热态约 3.3 ms。
- **负载测试是离线且确定性的。** 同一份合成的 1,000 档盘口（整数值，各语言完全相同），限时 8 s，所以它测量的是纯粹的解析吞吐量。`getrusage` 的 CPU 统计包含所有线程，所以对多线程运行时（Go 的 GC、JVM）来说，单线程墙钟吞吐量——而不是每操作 CPU——才是公平的数字。
- **WebSocket CPU 是稳态值。** 第一次 `watchOrderBook` 会构建整个快照——一个很大的一次性成本——所以我们单独计时，并且只在之后才启动 CPU 计数器；报告的 CPU/更新是增量的成本，而不是把快照摊到各次更新上。
- **内存是峰值 RSS**，在负载运行结束时测得（解析循环 + 保留的 2,000 份盘口）。它包含运行时基线，而这正是重点：JVM 巨大的默认堆是真实的内存。在预先提交堆的运行时上，按对象计算的增量并不可靠，所以我们报告操作系统层面的峰值。
- **Rust 的数字是归一化后的快照，不是同等条件的测量。** 它来自未合并的
  [PR #28627](https://github.com/ccxt/ccxt/pull/28627)，在我们原来的机器于项目中途被更换之后测得。吞吐量通过同机 JavaScript 参考运行做了重新缩放（那台机器的基准成绩慢 23%；Rust 原始的 800 ops/s → 约 988），并且 crate 被裁剪到只剩 coinbase 以便能编译。内存不需要调整——JS 参考运行把原来的数字复现到了 1% 以内。原始值和归一化值都在 `results.json` 里。

## 结论

按工作负载选语言，而不是按基准测试选。如果你在调用 REST 端点，网络会淹没一切，六种语言里任何一种都行。如果你在大量解析或合并深度盘口，决定胜负的是运行时的 JIT 和生成代码的形态——而这个排序与语言是否编译型关系不大。而且上面的好几项成本是我们要修的，不是语言的——第 6 节点了名。CCXT 团队致力于持续改进这个库，所以这既是一份报告，也是一份路线图。
