# Open-source crypto bot frameworks (Freqtrade, Jesse, OctoBot, Hummingbot): backfilling, backtesting and paper/dry-run simulation

Research date: 2026-09-27. Method: the Freqtrade and OctoBot websites (freqtrade.io, octobot.cloud) were blocked by the research sandbox's egress proxy, so claims come from the **source files of those same docs on GitHub** (freqtrade.io is built from `freqtrade/docs/*.md`) and from the **source code** at these commits: freqtrade `develop` @ d6c736fc1797; jesse `master` @ 1fc46f5fe273; jesse-ai/docs `master` @ dbd653d3dea5; OctoBot-Trading `master` @ 1ad2f4d6d296 (last commit 2026-02-01); OctoBot-Backtesting `master` @ 149a55afe1d7 (2026-01-03); OctoBot-Tentacles `master` @ f0ebe0c14db0; hummingbot `master` @ 9af100d6822d (2026-09-22); hummingbot-site `main` @ 31c98bf5358d; quants-lab `main` @ 3ea4e095d6cf (2025-11-04). Links point to GitHub blob paths, so line numbers may drift.

Which ones use CCXT: **Freqtrade** (all exchange I/O goes through ccxt) and **OctoBot** (ccxt connector). **Jesse** and **Hummingbot** do **not**: a search of both codebases found no `import ccxt`. Each uses its own per-exchange drivers or connectors.

## 1. Backfilling (history download, granularity, storage, incremental updates, gaps, point-in-time metadata)

### Takeaway
Freqtrade has the most complete backfill pipeline built on CCXT. It pages `fetch_ohlcv` concurrently, supports spot, futures, mark, funding-rate and open-interest candle types, stores Feather by default, and updates incrementally in both directions (append and `--prepend`). It has no historical market metadata, and approximates historical tick size from observed prices. Jesse imports **only 1m candles** into PostgreSQL through custom per-exchange drivers and builds every higher timeframe itself. OctoBot collects OHLCV through ccxt into per-run SQLite ".data" files. Its live collector can also record tickers, order books and trades, but its history collector cannot. Hummingbot's backtester uses candles from native candle feeds, and quants-lab caches them as parquet. None of the four stores historical order books for backtesting.

### Cited Findings

**Freqtrade**
- `download-data` downloads OHLCV. Default timeframes are `1m` and `5m`, and the default window is the last 30 days. — [freqtrade docs/data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Incremental update: "freqtrade will automatically calculate the missing timerange for the existing pairs and the download will occur from the latest available point until 'now'". `--new-pairs-days` sets the history length for newly added pairs, and "Given starting points are ignored if data is already available". — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Backwards extension: `--prepend --timerange 20210101-20220101` downloads data before the stored start. "Freqtrade will ignore the end-date in this mode if data is available". — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Delisted pairs: `--pairs ".*/USDT"` expands to active pairs, and "To also download data for inactive (delisted) pairs, add `--include-inactive-pairs`". — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Futures: futures mode "will automatically download the necessary candle types (e.g. `mark` and `funding_rate` candles)". Funding rate is stored as `date` plus `funding_rate` columns. Open interest is opt-in via `--candle-types open_interest` and stored as `open_interest_amount` and `open_interest_value`. Binance serves only about 30 days of OI history, and "Downloads reaching further back will silently return no data for the missing period". — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Storage formats: `feather` (Arrow), `json`, `jsongz`, and `parquet` ("OHLCV only"). Feather is the default for both OHLCV and trades. Benchmark on BTC/USDT 1m: feather 115 MB / 1.6 s, json 265 MB / 17.1 s, jsongz 83 MB / 23.6 s, parquet 149 MB / 2.5 s. `convert-data` and `convert-trade-data` convert between formats. — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- Trades (tick) data: `--dl-trades` downloads public trades, stores them as `<pair>-trades.feather`, and resamples them locally with `trades-to-ohlcv`. The docs say "You should not use this unless you're a kraken user (Kraken does not provide historic OHLCV data)". The method is slow because "it requires the result of the previous call to generate the next request". — [data-download.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/data-download.md)
- CCXT mechanics: `_async_get_historic_ohlcv` computes `one_call = timeframe_ms * ohlcv_candle_limit(...)`. It creates one coroutine per `since` in `range(since_ms, until_ms, one_call)`, which fans pages out concurrently instead of following a cursor. It gathers them "in batches of 100 to avoid overwhelming ccxt Throttling", logs failed pages as warnings (it raises only if `raise_`), then sorts the combined data because "above calls return in 'async order'". — [freqtrade/exchange/exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)
- Each page calls `self._api_async.fetch_ohlcv(pair, timeframe, since, limit, params)`. Mark and index candles pass `params={"price": candle_type}`. Funding rate and open interest go through dedicated `_fetch_funding_rate_history` and `_fetch_open_interest_history` helpers. The code re-sorts results because "Some exchanges sort OHLCV in ASC order and others in DESC". Trades use `fetch_trades` with a `trades_limit` of 1000, paginated by id or by time. — [exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)
- Gap handling at load time: `load_pair_history(..., fill_up_missing=True)` fills missing values "with 'No action'-candles". `validate_backtest_data` warns "%s has missing frames: expected %s, got %s". — [freqtrade/data/history/history_utils.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/data/history/history_utils.py)
- Point-in-time metadata: "Freqtrade has however no information about historic limits". Minimum-notional limits can therefore be inflated by historic prices (the docs example is $50 instead of $22). On precision: "These precision values are based on current exchange limits … as historic precision limits are not available". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Newer mitigation in code: the backtester builds `self.price_pair_prec[pair] = get_tick_size_over_time(data[pair])`, and `get_pair_precision(pair, current_time)` uses `precision_series.asof(current_time)`, which forces TICK_SIZE mode. The price tick size is inferred from observed historical prices and varies over time. Amount precision and limits still come from current markets. — [freqtrade/optimize/backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- Dynamic pairlists in backtests rely "on the current market conditions - which will not reflect the historic status of the pairlist". The docs recommend freezing a static list via `test-pairlist`. — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)

**Jesse**

The ML docs likewise say "Jesse requires 1m candles and resamples to any higher timeframe internally". — [docs/research/ml/regression.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/research/ml/regression.md)

- Storage is PostgreSQL through peewee (`PostgresqlExtDatabase`, `Candle` model). — [jesse/services/db.py](https://github.com/jesse-ai/jesse/blob/master/jesse/services/db.py), [jesse/models/Candle.py](https://github.com/jesse-ai/jesse/blob/master/jesse/models/Candle.py)
- Backtests can use spot candles in futures mode ("you can use candle data for your backtests from `Binance Spot` but run your backtests in the 'futures' mode … spot exchanges usually provide more data"). — [docs/strategies/futures-vs-spot.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/strategies/futures-vs-spot.md)

**OctoBot**
- Backtesting data files are SQLite databases (`BACKTESTING_DATA_FILE_EXT = ".data"`, read via `databases.SQLiteDatabase` / aiosqlite). — [OctoBot-Backtesting constants.py](https://github.com/Drakkar-Software/OctoBot-Backtesting/blob/master/octobot_backtesting/constants.py), [exchange_importer.py](https://github.com/Drakkar-Software/OctoBot-Backtesting/blob/master/octobot_backtesting/importers/exchanges/exchange_importer.py)

The collector probes the first available candle (`get_symbol_prices(..., limit=1, since=ideal_start)`), and each candle is saved with timestamp `candle_time + time_frame_sec`, i.e. its close time. — [OctoBot-Tentacles history_collector.py](https://github.com/Drakkar-Software/OctoBot-Tentacles/blob/master/Backtesting/collectors/exchanges/exchange_history_collector/history_collector.py)

- A separate live collector subscribes to the ticker, recent-trades, order-book, kline and OHLCV channels and saves each tick with `time.time()`. This is the only way to get non-OHLCV data into OctoBot backtests, and it is forward-recorded only. — [live_collector.py](https://github.com/Drakkar-Software/OctoBot-Tentacles/blob/master/Backtesting/collectors/exchanges/exchange_live_collector/live_collector.py)
- Market metadata in backtests comes from ccxt's cached `load_markets` (`_forced_market_statuses` via `ccxt_client_simulation.parse_markets` / `load_markets_from_cache`). - OctoBot's guide describes data files as SQLite files "that contain every historical candles the requested exchange is willing to give when using the regular data collector". — [octobot.cloud backtesting guide (search snippet; page fetch blocked)](https://www.octobot.cloud/en/guides/octobot-usage/backtesting)

### Inferences
- The Freqtrade page fan-out (all `since` windows at once, batched by 100) assumes that `since + limit` fully covers each window. This fails on exchanges that cap `limit` differently by timeframe or date. Freqtrade handles that with `ohlcv_candle_limit(timeframe, candle_type, since_ms)`, a per-exchange hook. A CCXT-native backfiller would need the same per-exchange "max candles per call by timeframe / by age" metadata.
- No framework records point-in-time market metadata (precision, limits, listing and delisting dates, contract size). Freqtrade infers tick size from prices. The others use current `load_markets`. A CCXT module that snapshots `markets` over time would be ahead of all four.
- Jesse stores only 1m candles and derives everything else, which gives one canonical base series. Freqtrade stores each timeframe separately, which can drift from exchange-served higher timeframes, but loads faster.

### Gaps
- I did not verify how OctoBot's `get_historical_ohlcv` paginates or handles rate limits beyond the single ccxt call. It is in OctoBot-Trading's `exchanges/util` and was not inspected in detail.
- I did not find the Freqtrade version that introduced `get_tick_size_over_time` (the changelog was not checked).
- The Hummingbot core repo has no documented persistent backfill format for the backtester outside quants-lab. The engine appears to fetch candles on demand.

## 2. Simulation clock (vectorized vs event-driven, time advancement, look-ahead prevention and detection, multi-pair sync)

### Takeaway
Freqtrade is a hybrid. Indicators and signals are computed **vectorized over the whole dataframe**, and signals are then **shifted by one candle** and replayed in an event loop over (time, pair), optionally subdivided with `--timeframe-detail`. Because vectorization makes look-ahead possible, Freqtrade ships detectors (`lookahead-analysis`, `recursive-analysis`). Jesse is a true **per-1m-candle event-driven** simulator: higher timeframes form bar by bar, and a timestamp-replay engine handles gapped or unequal series. It also has a "fast mode" that skips minutes with no activity. OctoBot is an **async, channel-based event simulation** driven by a backtesting time channel that pushes candles, synthetic trades and prices to the same consumers used live. Hummingbot v2 backtesting is a **per-row loop at a chosen resolution** that simulates each executor **vectorized over the future candles**.

### Cited Findings

**Freqtrade**
- "Backtesting initializes all timestamps (loads the whole dataframe into memory) and calculates all indicators at once. This means that if your indicators or entry/exit signals look into future candles, this will falsify your backtest." — [docs/lookahead-analysis.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/lookahead-analysis.md)
- Signal shift in code: "To avoid using data from future, we use entry/exit signals shifted from the previous candle". Each signal column is `.shift(1)`, the first row is dropped, and the data becomes lists "for performance reasons (Looping Pandas is slow.)". — [freqtrade/optimize/backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- Loop structure: `time_pair_generator` iterates main candles (`_time_generator` steps by `timeframe_td`). Inside each, `_time_pair_generator_det` iterates detail candles, and "Pairs that have open trades should be processed first". Per-pair row indexes are kept "so some pairs are allowed to have a missing start". A dynamic pairlist can refresh each candle (`self.pairlists.refresh_pairlist`). `bot_loop_start` is called per main candle. — [backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- `--timeframe-detail 5m` "will load 1h data (the main timeframe) as well as 5m data … The strategy will be analyzed with the 1h timeframe. Candles where activity may take place (there's an active signal, the pair is in a trade) are evaluated at the 5m timeframe". Callbacks run on each 5m candle, entries "still happen at the main candle's open", and slots can be freed intra-candle. — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Without detail data, "only the first `max_open_trades` signals per candle are evaluated, and the trade slots are only freed at the end of the candle". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- The dataprovider is capped during backtests (`_set_dataframe_max_index`, `_set_dataframe_max_date(current_time_det)`), so callbacks reading `dp` only see data up to the current time. — [backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- `lookahead-analysis` runs a baseline backtest, then "additional backtest runs for every entry and exit separately, with a pairlist of length 1", and compares "both dataframes (baseline and sliced) for any difference in columns' value". It forces cache off, max-open-trades ≥ pairs, a wallet of about 1e9, stake 10k, protections off, and market orders. — [docs/lookahead-analysis.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/lookahead-analysis.md)
- Caveats: the analysis only verifies signals that triggered (false negatives otherwise). It assumes a single pair behaves like the full pairlist, so cross-pair ranking strategies are reported as false positives. It defaults to 20 checked signals. — [docs/lookahead-analysis.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/lookahead-analysis.md)
- `recursive-analysis` recomputes indicators with different `startup_candle_count` values and reports the % variance of the last row. It targets recursive indicators (EMA, RSI) that differ between the full backtest history and the limited live history. It also notes that Binance returns 1000 candles per call and about 5 bulk calls, so "the max `startup_candle_count` you can have is 4999". — [docs/recursive-analysis.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/recursive-analysis.md)
- Common-mistake list: no `shift(-1)`, no `.iloc[-1]` in `populate_*`, and no whole-column aggregates like `.mean()` (use `rolling`). — [docs/strategy-customization.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/strategy-customization.md)

**Jesse**
- `simulator()` dispatches to `_step_simulator` (the dense 1m loop), `_skip_simulator` ("fast_mode"), or `_timestamp_simulator`. Timestamp replay is used "only when source rows cannot share the dense minute index … Real gaps or unequal instrument timelines require the timestamp engine so absent rows remain absent and same-time updates stay atomic". — [jesse/modes/backtest_mode.py](https://github.com/jesse-ai/jesse/blob/master/jesse/modes/backtest_mode.py)
- "Jesse will simulate every candle in the selected range and execute your strategy logic candle by candle." — [docs/backtest/index.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/backtest/index.md)
- Fast mode "speeds up the backtest process by orders of magnitude". Changelog 2.3.4 (6 Jun 2026) says "Fast Mode now produces exactly the same results as the standard mode", and backtests run through MCP default to Fast Mode. — [docs/research/backtest.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/research/backtest.md), [changelog.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/changelog.md)
- Higher-timeframe candles are generated from 1m data. `generate_candle_from_one_minutes` rejects incomplete buckets unless `accept_forming_candles=True`. The strategy is executed only when its own timeframe produces a new candle. — [jesse/services/candle_service.py](https://github.com/jesse-ai/jesse/blob/master/jesse/services/candle_service.py), [docs/traditional-markets/backtesting.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md)
- Look-ahead: multi-timeframe "data routes" are claimed to be handled without bias ("This issue **is completely taken care of** in Jesse"; "Jesse goes through expensive calculations to make extra candles work without the Look-Ahead Bias"). — [docs/routes.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/routes.md)
- Multi-route sync (added in 3.1.0, 2 Sep 2026): routes need not share timestamps. "the engine merges their candles into one timeline and executes each strategy only when its own instrument produced a candle". The constraints are one data source per run and a common start after all warm-ups. — [docs/traditional-markets/backtesting.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md), [changelog.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/changelog.md)

**OctoBot**
- `TimeManager` advances `current_timestamp += time_interval` between `starting_timestamp` and `finishing_timestamp`, with optional whitelist skipping of empty timestamps. — [OctoBot-Backtesting time/time_manager.py](https://github.com/Drakkar-Software/OctoBot-Backtesting/blob/master/octobot_backtesting/time/time_manager.py)
- `OHLCVUpdaterSimulator.handle_timestamp` subscribes to the time channel. For each pair and timeframe it reads candles between `last_timestamp_pushed+1` and `timestamp`, plus one extra "future candle" on the shortest timeframe. That future candle is registered in the exchange simulator (`get_current_future_candles()`) and is **not pushed** to strategies. If fewer than 2 candles come back, the exchange is marked `is_unreachable`, which means missing data is treated as downtime. — [ohlcv_updater_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchange_data/ohlcv/channel/ohlcv_updater_simulator.py)
- Every live data feed has a simulator twin (ticker, recent trades, order book, prices, funding, kline, markets, balance, orders, positions `*_updater_simulator.py`) feeding the same async channels. — [OctoBot-Trading exchange_data/](https://github.com/Drakkar-Software/OctoBot-Trading/tree/master/octobot_trading/exchange_data)

**Hummingbot (v2 backtesting)**
- `run_backtesting(start, end, backtesting_resolution="1m", trade_cost=0.0002)` loads candles at that resolution. `prepare_market_data` merges controller features onto them with `pd.merge_asof`. The engine then loops rows, calls `update_state(row)`, and for each create action calls `simulate_executor(config, processed_features.loc[i:max_ts], trade_cost)`, which passes the simulator the **future** slice of candles. — [hummingbot/strategy_v2/backtesting/backtesting_engine_base.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/backtesting_engine_base.py)
- Live Hummingbot is clock-driven. `c_tick(timestamp)` on the paper exchange processes queued market orders and crossed limit orders each tick. — [paper_trade_exchange.pyx](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/connector/exchange/paper_trade/paper_trade_exchange.pyx)

### Inferences
- Freqtrade's design (vectorized signals + shift(1) + event loop for fills) is fast enough for hyperopt, but look-ahead safety depends on user discipline. It therefore needs after-the-fact detectors. An event-driven design that feeds only past bars (Jesse, OctoBot) prevents look-ahead by construction, at CPU cost. Jesse recovers speed with fast mode, which skips inactive minutes.
- Hummingbot's per-executor vectorized simulation evaluates each executor independently. The future path is passed in, but only used to find barrier hits. Controller decisions do not see executor outcomes until they are "collected" at their close time, so interactions such as portfolio constraints and competing orders are approximated.
- OctoBot's "future candle" trick is look-ahead contained inside the exchange simulator. It is used only to generate the intra-candle trades that fill orders, not exposed to the strategy.

### Gaps
- The Freqtrade `--timeframe-detail` introduction version and the intra-detail ordering of multi-pair processing were not traced beyond the code shown.
- I did not verify whether Hummingbot's merge_asof uses `direction="backward"` (look-ahead safe), because the argument was not visible in the grep.

## 3. Fill model (OHLC rules, limit orders, stops/ROI inside a candle, slippage, fees, partial fills, funding, liquidation)

### Takeaway
All four assume **zero-queue, full fills when the price is touched**. None models partial fills or queue position from historical data. Freqtrade publishes the most explicit OHLC assumption list: entry at open, limit filled if the price is within [low, high], stoploss exactly at the stop price, stoploss evaluated before ROI, and low assumed before high. Jesse uses an implied intra-candle path, splitting the 1m candle at each order price, plus explicit opening-gap fills at the open. OctoBot creates two synthetic trades at the **next** shortest-timeframe candle's low and high and fills resting orders at their own price. Hummingbot v2 enters at **close** prices and uses close-based take profit and low/high-based stop loss, with a flat `trade_cost`. For futures, Freqtrade applies funding from downloaded funding-rate and mark candles and computes liquidation prices. Jesse simulates isolated-margin liquidation but sets funding to 0. OctoBot uses a configured constant funding rate.

### Cited Findings

**Freqtrade (backtest)**
- "Entries happen at open-price unless a custom price logic has been specified". "All orders are filled at the requested price (no slippage) as long as the price is within the candle's high/low range". "Exit-signal exits happen at open-price of the consecutive candle". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Code: `_get_order_filled(rate, row)` returns `row[LOW_IDX] <= rate <= row[HIGH_IDX]`. — [backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- Stoploss: "Stoploss exits happen exactly at stoploss price, even if low was lower, but the loss will be `2 * fees` higher". "Stoploss is evaluated before ROI within one candle", which gives more stoploss exits than dry/live. "Low happens before high for stoploss, protecting capital first". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- ROI: exits are compared to high but use the ROI value; "Exits are never 'below the candle'"; ROI steps that take effect mid-candle use the open. Trailing stop: "High happens first - adjusting stoploss" and then "Low uses the adjusted stoploss". Evaluation order within a candle: exit-signal, stoploss, ROI, trailing. Futures position reversals happen on the closing candle. — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Fees: "All profit calculations include fees, and freqtrade will use the exchange's default fees" (from ccxt market info). `--fee` overrides and "will be applied twice (once for trade entry, and once for trade exit)". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Per-candle loop order: 1) manage open orders (cancel or replace on timeout), 2) entries, 3) fill entry orders, 4) create exit orders, 5) fill exit orders. — [backtesting.py `backtest_loop`](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- Futures: funding fees are applied when `current_time.timestamp() % funding_fee_timeframe_secs == 0`, using `exchange.combine_funding_and_mark(funding_rates, mark_rates, futures_funding_rate)`. Liquidation exits use `trade.liquidation_price`, and `update_liquidation_prices` recomputes them after fills. — [backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- "Freqtrade is able to calculate liquidation prices, but does not calculate liquidation fees". `liquidation_buffer` sets a safety stop before liquidation. Cross-position influence "may not be fully simulated in dry-run or backtesting mode". When funding history is missing, you can set `futures_funding_rate` (0 is recommended), with the warning "This will mean your backtests are inaccurate". — [docs/leverage.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/leverage.md)

**Jesse**
- Fees are `fee_rate * notional` from `env.exchanges.<ex>.fee` in non-live modes. — [jesse/services/order_service.py](https://github.com/jesse-ai/jesse/blob/master/jesse/services/order_service.py)
- Intra-candle path: `split_candle(candle, price)` splits a 1m candle into an "earlier" and a "later" part at the order price. The branches assume bullish candles go O→L→H→C and bearish candles go O→H→L→C. The simulator repeatedly executes whichever active order lies in the remaining candle range (`candle_includes_price`), updates `current_price` to the partial candle's close, and re-sorts orders (`_sort_execution_orders`, grouped as on/above/below the open). — [candle_service.py](https://github.com/jesse-ai/jesse/blob/master/jesse/services/candle_service.py), [backtest_mode.py](https://github.com/jesse-ai/jesse/blob/master/jesse/modes/backtest_mode.py)
- Opening gaps: on an up-gap, sell limits and buy stops between the previous close and the open fill **at the open**. On a down-gap, buy limits and sell stops do. The requested price is kept in `order.vars['submitted_price']`, and fills are timestamped at the end of the 1m candle. "A stop-loss at 98 with Friday's close at 100 and Monday's open at 94 fills at 94". — [docs/traditional-markets/backtesting.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md), [backtest_mode.py](https://github.com/jesse-ai/jesse/blob/master/jesse/modes/backtest_mode.py)
- Liquidation: "for now, we only support the isolated mode". A liquidation fires if the candle or the previous-close-to-open gap includes `liquidation_price`, and a reduce-only market order is then executed at `p.bankruptcy_price`. — [backtest_mode.py `_check_for_liquidations`](https://github.com/jesse-ai/jesse/blob/master/jesse/modes/backtest_mode.py)
- There is no slippage model. The word "slippage" does not appear in the jesse Python package. The Sandbox `market_order` takes `current_price`. — [jesse/exchanges/sandbox/Sandbox.py](https://github.com/jesse-ai/jesse/blob/master/jesse/exchanges/sandbox/Sandbox.py). The docs' Rule Significance pages list "Fee and slippage modelling" among things the test does not cover. — [docs/rule-significance-testing/interpreting-results.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/rule-significance-testing/interpreting-results.md)
- Funding in backtests is 0 (see §1). Stock shorting is simulated only via the `perpetual_futures` model, and "there is no stock-borrow model". — [docs/traditional-markets/backtesting.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md)

**OctoBot**
- When no recorded trades exist, `_recent_trades_from_ohlcv_callback` builds exactly two synthetic trades per shortest-timeframe candle, at the **next ("future") candle's low and high**. The source comment says "Recent trades for this candle are between the next candle high price and the next candle low price". If the future candle is missing, it falls back to two trades at the close. Recorded trades from a live collector are used instead when available. — [recent_trade_updater_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchange_data/recent_trades/channel/recent_trade_updater_simulator.py)
- Limit orders register a price event (`price_events_manager.new_event(origin_price, time, trigger_above, allow_instant_fill)`) and fill when it fires, **at the order's own price** (`update_order_filled_values(self.origin_price)`). The fill is classified taker if the price had already crossed at creation (`_should_instant_fill`), otherwise maker. — [limit_order.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/personal_data/orders/types/limit/limit_order.py)
- Market orders fill instantly at `created_last_price`. — [market_order.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/personal_data/orders/types/market/market_order.py)
- Fees default to `CONFIG_DEFAULT_SIMULATOR_FEES` for taker, maker and fee, can be overridden in the simulator config, or come from ccxt market statuses when forced statuses are used. — [exchange_simulator_connector.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchanges/connectors/simulator/exchange_simulator_connector.py). The docs say fees are "deducted at simulated orders completion in simulated orders and backtesting". — [OctoBot-Docs Usage/Simulator.md](https://github.com/Drakkar-Software/OctoBot-Docs/blob/stable/Usage/Simulator.md)
- Funding in backtests: `ExchangeSimulator.get_funding_rate` returns `backtesting_exchange_config.funding_rate`, a single configured constant rather than historical funding. — [exchange_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchanges/implementations/exchange_simulator.py)

**Hummingbot v2 backtesting**
- `PositionExecutorSimulator`: a limit entry starts at the first candle where `close <= entry_price` (buy), and the entry price is that candle's **close**. A market entry starts at the first row. PnL is `cumprod(close.pct_change()) * side - 2*trade_cost`. Take profit triggers on close-based `net_pnl_pct > tp`. Stop loss triggers on `low <= sl_price` (buy) or `high >= sl_price` (sell). A trailing stop is tracked on close-based PnL. The close is the earliest of TP, SL, trailing stop and time limit. — [position_executor_simulator.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/executors_simulator/position_executor_simulator.py)
- There is one flat `trade_cost` (default 0.0002), with no maker/taker split, no slippage, no funding and no liquidation in that simulator. — [backtesting_engine_base.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/backtesting_engine_base.py), [position_executor_simulator.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/executors_simulator/position_executor_simulator.py)
- Separate simulators exist for DCA, grid and order executors. — [executors_simulator/](https://github.com/hummingbot/hummingbot/tree/master/hummingbot/strategy_v2/backtesting/executors_simulator)

### Inferences
- The recurring trade-off is whether to fill limit orders at their own price whenever the bar touches it (Freqtrade, OctoBot, Jesse), which is optimistic for maker strategies with no queue or partial fills. Jesse's gap-at-open rule and Freqtrade's "stoploss before ROI, low before high" are the two explicit conservative corrections found.
- OctoBot's synthetic-trade approach is the most CCXT-adjacent pattern. It turns OHLCV into a minimal `fetchTrades` stream and lets the unchanged live order engine match against it. A CCXT simulator could generalize this to N synthetic trades along an assumed O→L→H→C / O→H→L→C path (Jesse's convention), or replay real `fetchTrades` history when available.
- Hummingbot's close-based entries and TP differ from Freqtrade's intrabar assumptions. The same strategy can therefore produce systematically different results across frameworks even on identical data.

### Gaps
- I did not verify OctoBot's stop-loss fill price in backtests (trigger price vs. the synthetic trade price), or whether OctoBot simulates liquidation.
- I did not verify Freqtrade backtest partial-fill support. Per the loop, orders fill fully when touched, and `adjust_trade_position` models scaling in/out rather than partial fills.

## 4. Code parity (same strategy code across backtest / paper / live; how the exchange is swapped; in-process vs server)

### Takeaway
All four run the same strategy class in every mode, and all simulators are **in-process**, not separate servers. They differ in where the swap happens. **Freqtrade** keeps the real ccxt-backed `Exchange` object and branches on `dry_run` inside the order methods (`create_dry_run_order`). Backtesting uses a separate `Backtesting` driver with `LocalTrade`, not the live `FreqtradeBot` loop. **OctoBot** swaps in a full `ExchangeSimulator` + `TraderSimulator` stack that feeds the same channel architecture. **Hummingbot** paper trading wraps the real connector's `OrderBookTracker` in a `PaperTradeExchange` (`<exchange>_paper_trade`), while v2 backtesting replaces executors with vectorized executor simulators. **Jesse** uses a `Sandbox` exchange object in backtests. Paper and live trading are a closed-source licensed plugin.

### Cited Findings
- Freqtrade dry-run: "Only Read-Only operations … are performed in dry-run mode", "Wallets (`/balance`) are simulated based on `dry_run_wallet`", and "Orders are simulated, and will not be posted to the exchange". — [docs/configuration.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/configuration.md). The DB defaults to `sqlite:///tradesv3.dryrun.sqlite` in dry-run. — [configuration.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/configuration.md)
- Freqtrade swap point: `Exchange.create_dry_run_order(...)` builds a ccxt-shaped order dict (`"id": f"dry_run_{side}_{pair}_{uuid4()}"`) and stores it in `self._dry_run_open_orders`. `fetch_dry_run_order` serves it back. Public data calls such as `fetch_l2_order_book` still hit the real exchange. — [freqtrade/exchange/exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)
- Freqtrade backtesting is a separate engine (`freqtrade/optimize/backtesting.py`) using `LocalTrade`, in-memory wallets (`self.wallets.update()`) and `disable_database_use`. Strategy callbacks (`custom_exit`, `custom_stoploss`, `adjust_trade_position`, `bot_loop_start`) are invoked by this engine. — [backtesting.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)
- Freqtrade: "backtesting will **never** replace running a strategy in dry-run mode". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- OctoBot: "OctoBot will simulate trades using the exact same process as with the real trading mode. … The only difference with a real trader is in the starting portfolio". The starting portfolio "is also **used for backtesting**". — [OctoBot-Docs Usage/Simulator.md](https://github.com/Drakkar-Software/OctoBot-Docs/blob/stable/Usage/Simulator.md)
- OctoBot components: `ExchangeSimulator` (implementations), `ExchangeSimulatorConnector` / `ExchangeSimulatorAdapter`, `TraderSimulator`, `BlockchainWalletSimulator`, and `*UpdaterSimulator` channel producers. — [OctoBot-Trading exchanges/](https://github.com/Drakkar-Software/OctoBot-Trading/tree/master/octobot_trading/exchanges)
- Hummingbot paper: `create_paper_trade_market(exchange_name, trading_pairs)` takes the real connector's `order_book_tracker` (from a non-trading connector instance) and returns `PaperTradeExchange(tracker, connector_class, exchange_name)`. Connectors are registered as `f"{e}_paper_trade"`. — [hummingbot/connector/exchange/paper_trade/__init__.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/connector/exchange/paper_trade/__init__.py), [hummingbot/client/settings.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/client/settings.py)
- Hummingbot: the default `paper_trade_exchanges` are Binance, KuCoin, Kraken and Gate.io. "To choose a different connector and go live, simply choose the exchange name without the `paper_trade` suffix". API keys are not required for some strategies in paper mode. — [hummingbot-site docs/client/global-configs/paper-trade.md](https://github.com/hummingbot/hummingbot-site/blob/main/docs/client/global-configs/paper-trade.md), [client_config_map.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/client/config/client_config_map.py)
- Hummingbot v2: the Dashboard backtests controller configs and can then "upload the configuration for deployment". The same controller runs live, but backtest execution uses executor simulators instead of the real executors. — [hummingbot-site docs/dashboard/backtest.md](https://github.com/hummingbot/hummingbot-site/blob/main/docs/dashboard/backtest.md), [backtesting_engine_base.py](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/strategy_v2/backtesting/backtesting_engine_base.py)
- Jesse: "Live and paper trading functionality is supported by Jesse via an official plugin". The package "is pre-built and the access is limited to those with an active license". Paper trading is enabled via a "Paper Trade" toggle on the Live page. — [jesse docs/livetrade.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/livetrade.md)
- Jesse backtests use `jesse/exchanges/sandbox/Sandbox.py` (`market_order`, `limit_order`, `stop_order`, `cancel_order`). — [Sandbox.py](https://github.com/jesse-ai/jesse/blob/master/jesse/exchanges/sandbox/Sandbox.py)

### Inferences
- Parity is strongest in OctoBot, where the same order objects, portfolio and channel consumers run in every mode, and weakest in Hummingbot v2, where the backtest uses different executor code from live. Freqtrade sits in between: one strategy API, but a separate backtest loop from the live bot loop. This separation is a documented source of divergence ("Stoploss is evaluated before ROI … more trades with the `stoploss` exit reason comparing to … Dry Run/Live").
- The Freqtrade and Hummingbot paper modes are "real public data + simulated private endpoints" layered on the real exchange client. This maps directly to a CCXT design: a wrapper that forwards `fetch*` public calls and intercepts `createOrder`, `cancelOrder`, `fetchOrder`, `fetchBalance` and `fetchPositions` into a local matching engine.

### Gaps
- I could not inspect Jesse's paper-trading matching logic because the plugin is closed-source.

## 5. Paper trading: how simulated orders match against live data

### Takeaway
Freqtrade dry-run matches against the **live L2 order book** (top 20 levels). Market orders walk the book with a 5% slippage cap. Limit orders fill fully when the best opposite price crosses them, and are converted to market orders if placed more than 1% through the spread. Hummingbot paper matches against the **live order book plus the live public trade stream**. Market orders are delayed 5 s and then walk the book via `simulate_buy/sell`. Limit orders fill fully when the opposite best price crosses or a public trade prints through them. OctoBot's simulator fills against **live recent trades and prices**. Jesse's paper engine is closed; its changelog shows several 2026 fixes to its limit and stop execution.

### Cited Findings
- Freqtrade: "Market orders fill based on orderbook volume the moment the order is placed, with a maximum slippage of 5%". "Limit orders fill once the price reaches the defined level - or time out based on `unfilledtimeout`". Limit orders are "converted to market orders if they cross the price by more than 1%". With `stoploss_on_exchange` the stop price "is assumed to be filled". Open dry orders survive restarts "with the assumption that they were not filled while being offline". — [docs/configuration.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/configuration.md)
- Freqtrade code: `get_dry_market_fill_price` walks `orderbook['asks'|'bids']` to compute a volume-weighted average price, capped at `worst_rate = rate*(1±0.05)`. `_dry_is_price_crossed` compares the limit to `asks[0][0]` / `bids[0][0]` (with `offset`). A limit fill sets `filled = amount` (a full fill) and charges `maker` fees, or `taker` if filled immediately. Stoploss dry orders raise if they "would trigger immediately". — [exchange.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)
- Hummingbot: `TRADE_EXECUTION_DELAY = 5.0`. Market orders are queued and executed once `create_timestamp <= now - 5s` via `c_execute_buy/sell`, which call `order_book.simulate_buy(amount)` and build fees with `build_trade_fee`. — [paper_trade_exchange.pyx](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/connector/exchange/paper_trade/paper_trade_exchange.pyx)
- Hummingbot limit matching has two paths. (a) `c_process_crossed_limit_orders` runs every tick and triggers limit orders "when the opposite side of the order book has crossed the limit order's price". (b) `OrderBookTradeListener` runs `c_match_trade_to_limit_orders`, which triggers limit orders "when incoming market orders have crossed the limit order's price", based on public trade events from a `CompositeOrderBook`. Processing uses the order's full `getQuantity()`. — [paper_trade_exchange.pyx](https://github.com/hummingbot/hummingbot/blob/master/hummingbot/connector/exchange/paper_trade/paper_trade_exchange.pyx)
- Hummingbot paper balances default to BTC 1, USDT 100000 and similar, and are set via `balance paper [asset] [amount]`. — [paper-trade.md](https://github.com/hummingbot/hummingbot-site/blob/main/docs/client/global-configs/paper-trade.md)
- OctoBot: "The trader simulator will use the exchanges' last trades to figure out if the current orders would have been filled or not". — [OctoBot-Docs Usage/Simulator.md](https://github.com/Drakkar-Software/OctoBot-Docs/blob/stable/Usage/Simulator.md)
- Jesse paper fixes: "Fixed paper trading order execution simulation bug where orders were not being executed" (1.13.6, 23 Feb 2026). "Paper trading limit and stop orders now execute correctly after a temporary market-data connection gap" (3.0.0, 1 Aug 2026). — [jesse docs/changelog.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/changelog.md)

### Inferences
- The Hummingbot trade-print matching path is the only one of the four that uses public trades to fill resting passive orders in paper mode, which matters for market makers. Even so, it fills the whole order on any print through the price, regardless of print size or queue.
- Hummingbot's `PaperTradeExchange` extends `ExchangeBase` (spot) and the default list is spot exchanges. This suggests perpetual paper trading is not supported by this connector. It is not confirmed in the docs; search results only mention testnets for some perp venues ([Hyperliquid page](https://hummingbot.org/exchanges/hyperliquid/)).

### Gaps
- I did not confirm whether Freqtrade dry-run models funding and liquidation for futures (`dry_run_liquidation_price` exists in exchange.py, but funding accrual in dry-run was not traced).

## 6. Known weaknesses and criticisms

### Takeaway
The recurring complaints are backtest-vs-dry/live divergence (Freqtrade has many issues on this), look-ahead from vectorized indicators and resampling, recursive-indicator warm-up differences, no historical metadata or pairlists, optimistic full fills with no queue model, missing or constant funding in simulations (Jesse 0, OctoBot constant), and closed or fragile paper engines (Jesse is licensed-only; a Hummingbot paper-trade bug report from Jan 2025 remains open).

### Cited Findings
- Freqtrade divergence issues: #1198 (2018, "No trades in dryrun - hundreds in backtest"); #7248 (2022, huge difference traced to resampling 1m→1h); #7502 and #7768 (2022); #8451 (2023, backtest 1% DD / 70% winrate vs dry 10% DD / 35%); #12662 and #12675 (inconsistent trade behavior); #12894 (Mar 2026, signals differ with a 30m informative pair despite lookahead-analysis reporting no bias). — [#1198](https://github.com/freqtrade/freqtrade/issues/1198), [#7248](https://github.com/freqtrade/freqtrade/issues/7248), [#7502](https://github.com/freqtrade/freqtrade/issues/7502), [#7768](https://github.com/freqtrade/freqtrade/issues/7768), [#8451](https://github.com/freqtrade/freqtrade/issues/8451), [#12662](https://github.com/freqtrade/freqtrade/issues/12662), [#12675](https://github.com/freqtrade/freqtrade/issues/12675), [#12894](https://github.com/freqtrade/freqtrade/issues/12894) (issue list via web search; only #12894's body was read. It is labelled closed, but the fetched page showed no maintainer explanation)
- Freqtrade's own acknowledgements: the intra-candle limitation ("will always be biased in one way or the other"), stoploss-before-ROI bias, no historic limits or precision, dynamic pairlists not reproducible, liquidation fees not tracked, and missing funding making backtests "inaccurate". — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md), [docs/leverage.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/leverage.md)
- Freqtrade backtest result caching can "silently skip changes to modules strategies import", which needs `--cache none`. — [docs/backtesting.md](https://github.com/freqtrade/freqtrade/blob/develop/docs/backtesting.md)
- Hummingbot's own commentary (Bot Pod ep. 4): market-making backtests cannot know queue priority, and path dependency means that "if just one fill happens differently … everything after that diverges". Backtesting should be a "parameter research tool rather than a prediction engine". — [hummingbot.substack.com Bot Pod Episode 4](https://hummingbot.substack.com/p/the-bot-pod-episode-4-backtesting) (via search snippet; not fully fetched)
- Hummingbot paper-trade bug report #7370 (7 Jan 2025): "Paper trade mode broken?" on master, open with no identified cause. — [hummingbot#7370](https://github.com/hummingbot/hummingbot/issues/7370)
- Jesse: 3.1.0 (2 Sep 2026) "Backtest simulations now accurately handle gaps in historical data", which implies earlier versions did not. The dashboard's warm-up import suggestion "can suggest a date that is not early enough" on gapped data. — [changelog.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/changelog.md), [traditional-markets/backtesting.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/traditional-markets/backtesting.md)
- Jesse's FAQ attributes differences from other tools partly to metric formulas (e.g. 252 vs 365 annualization). — [Jesse Help Center FAQ](https://jesse.trade/help/faq/jesses-backtest-results-differ-from-backtesting-with-another-tool-whats-the-reason) (search snippet)
- Jesse's marketing claim that its engine "is the most accurate available" is not independently verified. — [docs/backtest/index.md](https://github.com/jesse-ai/docs/blob/master/docs/docs/backtest/index.md)
- OctoBot: the ccxt-based history collector gathers only OHLCV, and funding is constant in backtests. Missing candles mark the exchange "unreachable" rather than being filled. — [history_collector.py](https://github.com/Drakkar-Software/OctoBot-Tentacles/blob/master/Backtesting/collectors/exchanges/exchange_history_collector/history_collector.py), [exchange_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchanges/implementations/exchange_simulator.py), [ohlcv_updater_simulator.py](https://github.com/Drakkar-Software/OctoBot-Trading/blob/master/octobot_trading/exchange_data/ohlcv/channel/ohlcv_updater_simulator.py)
- OctoBot-Trading's last commit was 1 Feb 2026 and OctoBot-Backtesting's was 3 Jan 2026 (from the clones), which suggests slower recent development than Jesse and Hummingbot (both committed in Sep 2026). — [OctoBot-Trading commits](https://github.com/Drakkar-Software/OctoBot-Trading/commits/master), [OctoBot-Backtesting commits](https://github.com/Drakkar-Software/OctoBot-Backtesting/commits/master)

### Inferences
Summary of what a high-end CCXT simulator could do better, based on the gaps above:
1. Record point-in-time `markets` (precision, limits, status and delisting).
2. Make the intrabar path model explicit and configurable (Freqtrade-style low-first, or Jesse-style O→L→H→C by candle color), with gap-at-open fills.
3. Offer optional trades or L2 replay, with queue-position and partial-fill models, which none of the four has.
4. Use historical funding and mark-price candles plus liquidation with fees (only Freqtrade does funding/mark; nobody charges liquidation fees).
5. Run one order-matching engine shared by backtest and paper modes, as OctoBot does, so that backtest-vs-paper divergence comes only from the data.
6. Keep deterministic event ordering across symbols, as Jesse does with its atomic timestamp events.
7. Build look-ahead prevention in (only past bars delivered) rather than detecting it afterwards.

### Gaps
- There are few independent third-party benchmarks comparing these engines' fidelity. I found none that is reliable.
- OctoBot's and Jesse's GitHub issue trackers were not searched specifically for divergence reports, given the tool-call budget.
